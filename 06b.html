02 Auftrag

Ausgangslage

In 06A hast du auf Papier zwei Kästen gezeichnet. Den einen hast du aus deinem Code abgelesen. Den anderen hast du entworfen, und zwar für etwas, das es in deiner App noch gar nicht gibt.

Heute holst du diesen zweiten Kasten ein. Er wird eine Java-Klasse, und danach bekommt der Ergebnisbereich ein Feld, in das man seinen Namen tippt.

Teil A, dein Datenmodell wird Code 14 Minuten

A1Die Klasse HighscoreEntry. 6 Min

Leg dein Arbeitsblatt aus 06A daneben. Der Kasten, den du in A4 gezeichnet hast, wird jetzt eine Klasse.

Neue Java-Klasse im Paket ch.wiss.m335.quiz.model, neben Question.

Schreib sie selbst, aus deiner Zeichnung. Es gibt hier keinen Codeblock zum Abtippen. Du hast alles, was du brauchst: drei Felder mit Datentyp, ein Konstruktor, drei Getter, Javadoc.

Eine Vorgabe, die du nicht aus deiner Zeichnung ablesen kannst: alle drei Felder sind private final.

final heisst, der Wert wird im Konstruktor gesetzt und danach nie mehr geändert. Also gibt es keine Setter. Ein Ergebnis, das einmal in der Rangliste steht, ändert sich nicht mehr. Das ist der Unterschied zu Question, wo du Fragen ab Tag 4 bearbeiten wirst.

So prüfst du A1.

  • Drei Felder, alle private final.
  • Ein Konstruktor mit drei Parametern, in derselben Reihenfolge wie die Felder.
  • Drei Getter, keine Setter.
  • Javadoc am Klassenkopf, an jedem Feld und am Konstruktor mit @param.
  • Das Projekt lässt sich bauen. Die Klasse wird noch von niemandem benutzt, das ist richtig so.

A2Die Rangliste ablegen. 8 Min

Jetzt braucht deine Klasse einen Platz zum Liegen. Der Ort ist derselbe wie beim besten Wert aus 05D, also die SharedPreferences. Nur passt dort kein Objekt hinein und schon gar keine Liste, sondern nur Text.

Das Format kennst du. JSON hast du in 294 gegen den json-server und in 295 gegen Spring Boot benutzt. Neu ist nur, wie man JSON in Java baut statt es geliefert zu bekommen. Das sind vier Aufrufe:

// schreiben
JSONObject o = new JSONObject();
o.put("titel", "Sport");      // Feld hinein
JSONArray a = new JSONArray();
a.put(o);                        // Objekt in die Liste
String text = a.toString();       // die ganze Liste als Text

// lesen, genau umgekehrt
JSONArray a2 = new JSONArray(text);
JSONObject o2 = a2.getJSONObject(0);
String titel = o2.getString("titel");

Mehr ist es nicht. Leg jetzt die Klasse HighscoreStorage im Paket ch.wiss.m335.quiz.data an, neben ScoreStorage. Gebaut wie diese: privater Konstruktor, nur statische Methoden, dieselbe Ablage m335_quiz, ein eigener Schlüssel highscores.

Das Lesen bekommst du

getAll ist neu genug, dass du es nicht raten sollst. Übernimm es:

public static List<HighscoreEntry> getAll(Context context) {
    List<HighscoreEntry> entries = new ArrayList<>();
    String text = prefs(context).getString(KEY_HIGHSCORES, "[]");

    try {
        JSONArray array = new JSONArray(text);
        for (int i = 0; i < array.length(); i++) {
            JSONObject object = array.getJSONObject(i);
            entries.add(new HighscoreEntry(
                    object.getString(FIELD_NAME),
                    object.getInt(FIELD_SCORE),
                    object.getString(FIELD_CATEGORY)));
        }
    } catch (JSONException e) {
        // Kaputter Text, zum Beispiel nach einem misslungenen Umbau.
        // Lieber eine leere Liste als ein Absturz beim Start.
        Log.e(TAG, "highscores unreadable, starting empty", e);
    }

    return entries;
}

Die drei Konstanten FIELD_NAME, FIELD_SCORE und FIELD_CATEGORY legst du dazu an, mit den Werten "name", "score" und "category". Warum als Konstante und nicht als Text an Ort und Stelle: der Schlüssel muss beim Lesen und beim Schreiben exakt derselbe sein. Ein Tippfehler an einer der zwei Stellen kompiliert und schlägt erst zur Laufzeit zu.

Das Schreiben baust du selbst

saveAll ist die Umkehrung von getAll. Wo oben getString steht, steht unten put. Wo oben aus einem JSONObject ein HighscoreEntry wird, wird unten aus einem HighscoreEntry ein JSONObject.

Du hast alles, was du brauchst. Schreib es.

Und dann noch add, die Methode, die deine GameActivity gleich aufrufen wird. Sie hat vier Zeilen und du weisst, welche:

public static void add(Context context, HighscoreEntry entry) {
    ... hol die ganze Liste ...

Zähl mit, während du schreibst. Wie oft hast du am Ende von A1 und A2 das Wort name hingeschrieben?

Einmal als Feld in HighscoreEntry. Einmal als Konstante FIELD_NAME. Einmal beim Lesen. Und jetzt nochmals beim Schreiben.

Und jetzt stell dir vor, du willst ein viertes Feld dazu, ein Datum. Wie viele Stellen musst du anfassen? Was passiert, wenn du eine davon vergisst?

Schau dir zum Schluss deine eigene add an. Sie hat vier Zeilen, und in dreien davon steckt dieselbe Sache: die ganze Liste wird gelesen und die ganze Liste wird zurückgeschrieben, obwohl sich nur ein einziger Eintrag ändert.

Bei drei Einträgen merkt das niemand. Bei dreitausend schon.

Genau diesen Umweg hast du im Ausblick von 05D gelesen. Heute hast du ihn selbst gebaut, und darum ist er ab jetzt keine Behauptung mehr.

Das ist der teuerste Code, den du in diesem Modul schreibst, gemessen an dem, was er leistet. Merk dir das Gefühl. Am Tag 4 machst du dasselbe mit einer Zeile.

B2Der Ergebnisbereich braucht eine ScrollView. 4 Min

Der Bereich ist gewachsen: Punktzahl, Namensfeld, drei Knöpfe, Bestätigung und die Fragenliste. Dazu schiebt die Tastatur beim Tippen den halben Bildschirm hoch.

// vorher
LinearLayout llResult          // 0dp hoch, an allen vier Ankern
  └─ ScrollView svQuestionList // nur die Fragenliste scrollte

// jetzt
ScrollView svResult            // 0dp mal 0dp, an allen vier Ankern
  └─ LinearLayout llResult     // wrap_content, der ganze Bereich scrollt
       └─ LinearLayout llQuestionList   // ohne eigene ScrollView

Konkret: eine ScrollView mit der id svResult aussen herum, die vier Anker und android:visibility="gone" wandern von llResult dorthin. llResult wird match_parent mal wrap_content. Die innere svQuestionList verschwindet, das llQuestionList darin bleibt.

Zwei ScrollViews ineinander sind fast immer ein Fehler. Beide wollen die Wischgeste haben, und das Ergebnis ist ein Bereich, der sich nur mit Mühe bewegen lässt. Wenn der äussere Bereich ohnehin scrollen muss, nimmt man dem inneren die ScrollView weg.

Und jetzt eine Zeile im Java, die leicht vergessen geht. In showState wird der Ergebnisbereich umgeschaltet. Umgeschaltet wird ab jetzt svResult statt llResult. Dieselbe Regel wie in 05C: ein Container, der etwas versteckt, muss sich selbst verstecken.

B3Die Tastatur braucht Platz. 3 Min

Starte die App, spiel eine Runde zu Ende und tipp ins Namensfeld. Die Tastatur kommt hoch. Schau, was mit deinem Inhalt passiert.

Die Tastatur legt sich darüber. Sie schiebt nichts hoch. Bei diesem Bildschirm geht es gerade noch, weil das Feld oben steht. Bei einem Formular mit fünf Feldern wäre das untere nicht mehr erreichbar.

Und jetzt das Verwirrende: im AndroidManifest.xml steht bei deiner GameActivity seit dem ersten Tag genau die Zeile, die das verhindern sollte.

android:windowSoftInputMode="adjustResize"

Sie ist da, sie ist richtig, und sie wirkt trotzdem nicht. Der Grund steht drei Zeilen weiter oben in deiner eigenen onCreate.

Der Block, den du seit 01B mit dir herumträgst

Ganz am Anfang von onCreate steht dieser Abschnitt. Er kam mit der Projektvorlage, du hast ihn nie angefasst, und heute gibt es zum ersten Mal einen Grund, ihn zu lesen:

ViewCompat.setOnApplyWindowInsetsListener(findViewById(R.id.clGame), (v, insets) -> {
    Insets systemBars = insets.getInsets(WindowInsetsCompat.Type.systemBars());
    v.setPadding(...);
    return insets;
});

Deine App zeichnet bis an den Bildschirmrand, das macht EdgeToEdge.enable(this) in der Zeile darüber. Wer das tut, bekommt vom System keinen Platz mehr geschenkt, sondern muss ihn selbst freilassen. Genau das macht dieser Block: er fragt, wie viel Rand die Systemleisten brauchen, und setzt so viel Innenabstand.

Und die Tastatur steht nicht in dieser Frage drin. systemBars() sind Statusleiste und Navigationsleiste, mehr nicht. Die Tastatur ist ein eigener Typ, und du fragst nie nach ihr.

Die Reparatur ist eine Zeile:

Insets systemBars = insets.getInsets(
        WindowInsetsCompat.Type.systemBars() | WindowInsetsCompat.Type.ime());

Das Zeichen dazwischen ist ein senkrechter Strich. Er heisst hier und, nicht oder: gib mir den Rand für die Systemleisten und für die Tastatur.

Starte neu und tipp nochmals ins Feld. Jetzt schiebt sich der Inhalt hoch und du kommst an den Speichern-Knopf, während die Tastatur offen ist.

Der Satz, den du dir merkst: wer selbst bis an den Rand zeichnet, muss sich auch selbst um die Ränder kümmern. Das gilt für die Statusleiste, für die Navigationsleiste und für die Tastatur.

adjustResize im Manifest ist deswegen nicht falsch. Es ist die Ansage, was passieren soll. Der Insets-Block ist die Stelle, an der es passiert.

So prüfst du Teil B.

  • Die App startet und eine Runde lässt sich spielen.
  • Am Ende der Runde steht das Namensfeld da, mit dem Hinweistext Dein Name.
  • Beim Antippen wandert der Hinweistext nach oben und wird klein.
  • Die Tastatur zeigt unten rechts einen Haken.
  • Unter dem Namensfeld steht der Knopf, die Bestätigung ist noch unsichtbar.
  • Der Knopf tut beim Antippen nichts. Das ist nach Teil B der richtige Zustand, nicht ein Fehler.
  • Der ganze Ergebnisbereich lässt sich wischen, auch im Querformat.
  • Bei offener Tastatur kommst du an den Speichern-Knopf. Wischen ist erlaubt, aber er darf nicht unerreichbar sein.

C2Die Prüfung. 5 Min

Zwei Methoden. Die erste liest den Text aus dem Feld, die zweite prüft ihn.

private String currentName() {
    // Kommt in C4 nochmals dran.
    return etPlayerName.getText() == null ? "" : etPlayerName.getText().toString();
}
private boolean isNameValid() {
    String name = currentName();

    if (name.isEmpty()) {
        tilPlayerName.setError(getString(R.string.error_name_required));
        return false;
    }
    if (name.length() < MIN_NAME_LENGTH) {
        tilPlayerName.setError(getString(R.string.error_name_too_short));
        return false;
    }

    tilPlayerName.setError(null);
    return true;
}

Die wichtigste Zeile ist die drittletzte. setError(null) im gültigen Fall.

Ohne sie bleibt die rote Meldung stehen, auch wenn die Eingabe inzwischen stimmt. Dieselbe Regel wie beim Zurücksetzen der Antwort-Buttons in 03C: was dein Code setzt, muss dein Code auch wieder löschen.

Warum getText() auf null geprüft wird: bei einem TextInputEditText kann es tatsächlich null liefern. Android Studio warnt dich, eine KI oft nicht.

C3Das Eintragen und die Sperre. 4 Min

private void onSaveScoreClicked() {
    if (scoreSaved) {
        return;
    }
    if (!isNameValid()) {
        return;
    }

    String name = currentName();
    HighscoreStorage.add(this, new HighscoreEntry(name, score, selectedCategory));

    scoreSaved = true;
    updateSaveArea();

    Log.d(TAG, "highscore saved for " + name);
}
private void updateSaveArea() {
    btnSaveScore.setEnabled(!scoreSaved);
    etPlayerName.setEnabled(!scoreSaved);
    tvSaved.setVisibility(scoreSaved ? View.VISIBLE : View.GONE);
    if (scoreSaved) {
        tilPlayerName.setError(null);
    }
}

Und zum Schluss das Zurücksetzen aus dem Überblick. In onStartClicked, gleich nachdem die Kategorie feststeht: scoreSaved auf false, das Feld leeren, updateSaveArea() aufrufen.

Dieselbe Lektion wie in 03C, an einer anderen Stelle. Dort mussten die vier Antwort-Buttons nach dem Antippen gesperrt werden, sonst gab es zwei Punkte für eine Frage. Hier muss der Speichern-Knopf gesperrt werden, sonst steht derselbe Spieler fünfmal in der Rangliste.

Die Frage, die du dir ab jetzt bei jeder verändernden Aktion stellst: was passiert bei einem zweiten Klick?

C4Schau genau hin. 2 Min

Starte die App und spiel eine Runde zu Ende. Probier jetzt der Reihe nach:

  1. Auf den Knopf, ohne etwas einzutippen. Was steht unter dem Feld?
  2. Jo eintippen und nochmals drücken. Was steht jetzt dort?
  3. Drei Leerzeichen eintippen und drücken. Was passiert?

Schritt 3 ist die Stelle. Nicht reparieren, erst anschauen. Schau danach in der Rangliste nach, was gespeichert wurde. Der Weg zur Datei steht im Blatt Wo deine App ihre Daten ablegt.

Und dann überleg dir, warum deine Prüfung das durchgelassen hat, obwohl sie doch die Länge misst.

Danach reparierst du es. Es ist eine Änderung an genau einer Zeile, in currentName.

Repariere an beiden Stellen oder an keiner. Wer nur beim Prüfen trimmt und beim Speichern nicht, hat einen Namen mit Leerzeichen in der Rangliste. Genau darum steht die Reparatur in currentName und nicht in isNameValid: so benutzen beide denselben Wert.

Die Regel für immer: jede Texteingabe eines Benutzers wird getrimmt. Ausnahmslos. Das gilt auch in der Leistungsbeurteilung.

C5Kommentare nachziehen. 2 Min

Deine GameActivity hat heute vier Methoden, fünf Felder und eine Konstante dazubekommen. Der Klassenkommentar oben stammt aus 05D und weiss davon nichts.

Geh drei Dinge durch:

  1. Jede neue Methode bekommt ein Javadoc mit einem Satz, was sie tut. isNameValid zusätzlich ein @return.
  2. Jedes neue Feld bekommt eine Zeile. Bei scoreSaved lohnt sich ein zweiter Satz, warum es die Sperre überhaupt gibt.
  3. Der Klassenkommentar nennt oben drei Bereiche. Einer davon heisst seit heute anders. Und ein Absatz zu 06B fehlt.

Rahmen für den neuen Absatz, in eigenen Worten füllen:

* Neu in 06B: ... hier zwei bis drei Zeilen, was der
* Ergebnisbereich jetzt kann und wohin der Eintrag geht ...

Das Argument ist Aufwand, nicht Note. Vier Methoden jetzt zu kommentieren dauert drei Minuten. Elf Methoden am Tag 5 nachträglich zu dokumentieren dauert eine Stunde.

So prüfst du das Ganze.

  1. Spiel eine Runde zu Ende. Im Ergebnisbereich steht ein Feld Dein Name.
  2. Ohne Eingabe auf den Knopf. Unter dem Feld erscheint Bitte gib deinen Namen ein. Nichts springt.
    Kommt hier gar keine Meldung, fehlt der Listener am Knopf. Siehe C1. Das ist nicht dasselbe wie Punkt 6, und auch nicht dasselbe wie der Zustand nach Teil B.
  3. Jo eintippen, nochmals drücken. Jetzt steht dort Mindestens drei Zeichen.
  4. Drei Leerzeichen eintippen. Es muss immer noch die Fehlermeldung kommen.
  5. Sara eintippen und drücken. Die Fehlermeldung verschwindet, die Bestätigung erscheint, Feld und Knopf sind gesperrt.
  6. Nochmals auf den Knopf. Es passiert nichts.
  7. Spiel eine zweite Runde und trag dich mit dem Haken auf der Tastatur ein, ohne den Knopf zu berühren. Dasselbe muss passieren.
  8. Der Speichern-Knopf ist in der zweiten Runde wieder frei und das Feld leer.
  9. Im Logcat unter tag:Modul335 steht nach jedem Eintrag highscore saved for ... und highscore added, total=....
  10. In shared_prefs/m335_quiz.xml steht jetzt neben bestScore ein string namens highscores mit dem JSON-Text darin.

Punkt 10 lohnt sich wirklich. Jetzt stehen zwei Einträge in derselben Datei nebeneinander: ein schlichter int und ein langer JSON-Text.

Der Unterschied zwischen ein Wert und eine Liste zu Fuss ist damit auf dem Bildschirm sichtbar und nicht nur behauptet. Genau das war die Entscheidung, die du in 06A Teil B auf Papier getroffen hast.

Übungen 2 Minuten

Übung 1, eine dritte Prüfung

Ein Name, der nur aus Ziffern besteht, ist kein Name. 1234 kommt heute durch, denn es sind vier Zeichen.

Ergänz isNameValid um diese Prüfung, mit einer eigenen Fehlermeldung in strings.xml. Du brauchst dafür kein neues Werkzeug.

So prüfst du: 1234 wird abgelehnt, Sara2 geht durch. Die Reihenfolge der drei Prüfungen darf sich nicht ändern.

Übung 2, erklären

Erklär einem Lerngspänli in zwei Sätzen, warum setError auf das TextInputLayout gehört und nicht auf das TextInputEditText. Beide Aufrufe kompilieren, beide zeigen etwas an.

So prüfst du: Wenn dein Gegenüber danach nicht sagen kann, wo die Meldung jeweils erscheint, war es zu allgemein.

Zusatzaufgabe für Schnelle

Den Knopf sperren statt meckern

Zuerst die Pflichtaufgabe fertig und lauffähig. Dann erst hier weiter.

Auftrag: Statt beim Klick zu meckern, sperr den Speichern-Knopf, solange die Eingabe ungültig ist. Er wird erst frei, wenn genug Zeichen im Feld stehen.

Und die Frage, die dazugehört: Welche der beiden Varianten ist benutzerfreundlicher, und warum? Es gibt kein eindeutig richtig, beide kommen in echten Apps vor. Deine Begründung ist die Aufgabe, nicht der Code.

Keine Musterlösung. KI darfst du benutzen, aber du musst deine Lösung erklären können.
