User Stories mit Akzeptanzkriterien 6 Punkte

Die Prüfung verlangt drei Stories mit Akzeptanzkriterien. Eine Story hat drei Teile: Als wer, möchte ich was, damit wozu. Ohne das damit ist es keine Story. Sie ist so klein, dass man sie in einem Arbeitsblock bauen und danach abhaken kann.

Ein Akzeptanzkriterium ist messbar, wenn eine fremde Person zum selben Urteil kommt wie du. Die Form: wenn ich X mache, steht Y auf dem Bildschirm. Ein gutes Kriterium sagt auch, was nicht passieren darf. Schreib pro Story zwei Kriterien, so wie in 07A.

Als          User
möchte ich   einen Artikel zusammen mit dem Laden erfassen,
damit        ich im Geschäft sehe, was ich dort mitnehmen muss.

Kriterium 1  Wenn ich Artikel und Laden mit je mindestens 4 Zeichen
             eintippe und speichere, steht der Eintrag danach auf der
             Startseite in der Liste.
Kriterium 2  Wenn der Artikel weniger als 4 Zeichen hat, wird nicht
             gespeichert, und direkt beim Feld erscheint eine Meldung.

Urteilswörter wie korrekt, übersichtlich oder benutzerfreundlich. Ersetze jedes durch das, was man auf dem Bildschirm sieht.

Das Datenmodell 3 Punkte

Ein Kasten pro Art von Datensatz, der Name in der Einzahl und mit grossem Anfangsbuchstaben. Jede Zeile hat einen Datentyp. Die Feldnamen sind englisch und dieselben wie später im Code. Klassendiagramm oder ERD geben dieselben Punkte.

Das Feld id ist der Schlüssel. Er wird gebraucht, sobald ein einzelner Eintrag geändert oder gelöscht wird. Ins Modell gehört nur, was den Neustart der App überleben muss und sich nicht ausrechnen lässt. Der Betrag ist Menge mal Preis und bleibt darum draussen. Keine Normalisierung, die Prüfung verlangt KISS.

Menge und Preis dürfen leer bleiben. Darum sind sie Integer und Double und nicht int und double, denn nur die Wrapper-Klassen können null sein. Eine eigene Markierung im Diagramm braucht es dafür nicht, der Typ zeigt die Absicht. int und double gehen auch, dann steht neben dem Modell der Satz 0 heisst nicht eingetragen.

Als Klassendiagramm, mit den Feldern und den Java-Typen:

+----------------------------------+
|          ShoppingItem            |
+----------------------------------+
| PK id: int                       |
| article: String                  |
| shop: String                     |
| quantity: Integer                |
| pricePerUnit: Double             |
+----------------------------------+

Dasselbe als ERD, mit den Spalten der Tabelle und den SQL-Typen. Die Spalte heisst hier so wie in @ColumnInfo:

            ShoppingItem
+------------------------------------+
| PK  id               INTEGER       |
|     article          TEXT          |
|     shop             TEXT          |
|     quantity         INTEGER       |
|     price_per_unit   REAL          |
+------------------------------------+

Die Persistenz begründen 2 und 1 Punkt

Drei Teile. Zwei Möglichkeiten nennen, zum Beispiel SharedPreferences und eine lokale Datenbank mit Room. Dich für eine entscheiden. In zwei Sätzen begründen: der erste sagt, was für deine Wahl spricht, der zweite, was gegen die andere spricht.

Die Begründung nennt eine Eigenschaft deiner Daten, am besten eine Zahl oder eine Tätigkeit wie ändern oder filtern. Die zweite Möglichkeit überhaupt zu nennen, ist ein eigener Punkt im Raster.

Ich wähle die lokale Datenbank.

Ein einzelner Eintrag wird angetippt, geändert und wieder gespeichert,
und dafür brauche ich einen Schlüssel je Eintrag und einen gezielten
Zugriff. Mit SharedPreferences müsste ich für jede Änderung die ganze
Liste als Text lesen und komplett zurückschreiben.

Urteile über die Technik wie eine Datenbank ist besser oder das ist der moderne Weg. Sie beschreiben keine Bedingung deiner App und geben keinen Punkt.

Die Vorlage und der Insets-Block

Die Vorlage schreibt in onCreate einen Block, der Platz für Status- und Navigationsleiste schafft. Er sucht das Root-Element über seine id, in einer neuen Activity heisst sie main, und setzt dort das Padding.

EdgeToEdge.enable(this);

Das Dao

Ein Interface mit @Dao und sechs Methoden: anlegen, ändern, löschen, alle holen, eine holen, zählen. In @Query steht der Tabellenname, nicht der Klassenname. Room baut die Methoden dahinter beim Bauen der App.

@Dao
public interface ShoppingItemDao {
    @Insert
    long insert(ShoppingItem item);
    @Update
    void update(ShoppingItem item);
    @Delete

    @Query("SELECT * FROM shopping_items ORDER BY shop, article")
    List<ShoppingItem> getAll();
    @Query("SELECT * FROM shopping_items WHERE id = :id")
    ShoppingItem findById(int id);
    @Query("SELECT COUNT(*) FROM shopping_items")
    int count();
}

Die Datenbank und der Startbestand

Eine abstrakte Klasse mit @Database, genau einem Feld instance und der Methode getInstance. allowMainThreadQueries ist in diesem Kurs eine bewusste Entscheidung. Der Startbestand füllt die Tabelle nur, wenn sie leer ist.

@Database(entities = {ShoppingItem.class}, version = 1, exportSchema = false)
public abstract class ShoppingDatabase extends RoomDatabase {

    private static ShoppingDatabase instance;

    public abstract ShoppingItemDao shoppingItemDao();

    public static synchronized ShoppingDatabase getInstance(Context context) {
        if (instance == null) {
            Context appContext = context.getApplicationContext();
            instance = Room.databaseBuilder(appContext, ShoppingDatabase.class, DB_NAME)
                    .allowMainThreadQueries()
                    .build();
            seedIfEmpty();
        }
        return instance;
    }

    private static void seedIfEmpty() {
        ShoppingItemDao dao = instance.shoppingItemDao();
        int existing = dao.count();
        if (existing > 0) {
            return;
        }
        dao.insert(newItem("Vollkornbrot", "Migros", 2, 3.80));
        dao.insert(newItem("Zahnpasta", "Coop", null, null));
    }
}

Ohne die Prüfung mit count() kommen bei jedem Start neue Einträge dazu. Nach dem Ergänzen zusätzlich Clear storage, sonst bleiben die doppelten stehen.

onCreate und onResume

onCreate richtet ein: Layout, findViewById, Listener. onResume läuft jedes Mal, wenn der Bildschirm erscheint, beim ersten Start direkt nach onCreate und nach jeder Rückkehr von einem anderen Bildschirm. Daten, die ein anderer Bildschirm ändern kann, lädst du darum dort und nur dort.

@Override
protected void onResume() {
    super.onResume();
    loadItems();

Nur in onCreate geladen: ein neuer Eintrag erscheint erst nach einem Neustart. An beiden Stellen geladen: die Liste wird bei jedem Start zweimal gebaut.

Fehleingaben abfangen 4 Punkte

  • Zuerst alle alten Meldungen mit setError(null) entfernen.
  • Alle Felder prüfen und das Ergebnis in einer Variablen sammeln, nicht beim ersten Fehler zurückkehren.
  • Die Meldung steht am TextInputLayout, nicht in einem Toast.
  • Pflichtfelder mit trim und length. Optionale Zahlenfelder mit parseInt oder parseDouble in einem try.
private boolean isValid() {
    tilArticle.setError(null);
    tilPrice.setError(null);

    boolean valid = true;

    if (text(etArticle).length() < MIN_LENGTH) {
        tilArticle.setError(getString(R.string.error_too_short, MIN_LENGTH));
        valid = false;

    String price = text(etPrice);
    if (!price.isEmpty()) {
        try {
            Double.parseDouble(price);

            tilPrice.setError(getString(R.string.error_number));
            valid = false;

    return valid;
}

row.setOnClickListener(v -> {

if (item.getQuantity() != null) {

Javadoc 2 Punkte
