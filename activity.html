Die Activity von innen

Modul 335 Mobile Applikationen, Grundlagen. Wer deine Activity startet, was onCreate ist, wann etwas ein Feld sein muss, und was this bedeutet. Lesezeit rund 10 Minuten. Fassung 1 vom 15.08.2026.

Jeder Auftrag lässt dich in onCreate schreiben, und keiner sagt dir, was das eigentlich ist. Du legst Felder an, holst Views, hängst Klicks an und rufst am Schluss eine Methode auf. Das funktioniert, aber es fühlt sich nach Rezept an.

Diese Seite erklärt das Rezept. Danach weisst du, warum die Zeilen in dieser Reihenfolge stehen und was passiert, wenn du eine davon vergisst.

1. Wer deine Activity startet

Du erzeugst deine Activity nie selbst. Es gibt nirgends ein new MainActivity() in deinem Projekt. Such ruhig danach.

Stattdessen macht es Android. Der Ablauf ist ungefähr so:

1. Du tippst auf das App-Symbol
2. Android liest das AndroidManifest.xml und sucht die Start-Activity
3. Android erzeugt ein Objekt deiner Klasse MainActivity
4. Android ruft onCreate(...) darauf auf
5. Dein Code läuft

Darum steht deine Activity im Manifest. Ohne den Eintrag dort findet Android sie nicht, und die App startet mit einem Absturz, obwohl der Code fehlerfrei übersetzt.

Das ist der Grund für das @Override über onCreate. Du erfindest die Methode nicht, du ersetzt eine, die es schon gibt. Android kennt onCreate und ruft sie auf. Deine Fassung hängt sich in diesen Aufruf ein. Das super.onCreate(savedInstanceState) in der ersten Zeile gibt der ursprünglichen Fassung die Gelegenheit, ihre Arbeit trotzdem zu machen. Lösch es nie.

2. onCreate, die eine Methode, die du kennst

onCreate läuft einmal, wenn der Bildschirm aufgebaut wird. Nicht bei jedem Klick, nicht bei jeder Frage, einmal.

Daraus folgt alles Weitere. Was mehr als einmal passieren muss, kann nicht in onCreate stehen. Es braucht eine eigene Methode mit einem eigenen Auslöser.

Gehört in onCreateGehört nicht hinein
Das Layout setzen mit setContentView Alles, was bei jedem Klick passiert
Views holen mit findViewById Alles, was sich mit den Daten ändert
Anfangswerte sichern, solange nichts überschrieben ist Alles, was der Benutzer auslöst
Klick-Behandlungen anhängen
Daten laden
Eine letzte Zeile, die alles startet

onCreate richtet ein. Es zeigt nicht an.

Anzeigen macht eine eigene Methode, die onCreate am Schluss aufruft. Dieselbe Methode kann dann später nochmals laufen, wenn sich etwas geändert hat.

Wenn du eine Zeile in onCreate stehen hast und nicht sagen kannst, in welche der obigen Gruppen sie gehört, ist sie dort meistens falsch.

Es gibt noch weitere solche Methoden, etwa onStart, onPause und onDestroy. Android ruft sie auf, wenn dein Bildschirm sichtbar wird, in den Hintergrund gerät oder verschwindet. Du brauchst sie im Moment nicht. Und Android kann eine Activity unter bestimmten Umständen ganz neu aufbauen. Wann das passiert und was es für deine Daten bedeutet, ist ein eigenes Thema am Tag 3.

3. Feld oder lokale Variable

Diese Entscheidung triffst du in jedem Auftrag, meistens ohne darüber nachzudenken.

Lokale Variable

Steht in einer Methode. Entsteht beim Aufruf, ist danach weg.

Nimm sie, wenn der Wert nur in dieser einen Methode gebraucht wird.

Feld

Steht ausserhalb aller Methoden, direkt in der Klasse. Lebt so lange wie das Objekt.

Nimm es, wenn zwei Methoden denselben Wert brauchen.

public class MainActivity extends AppCompatActivity {

    // Feld. Beide Methoden unten brauchen es.
    private TextView tvScore;

    protected void onCreate(Bundle savedInstanceState) {
        ...
        tvScore = findViewById(R.id.tvScore);

        // Lokale Variable. Nur hier gebraucht, danach weg.
        int abstand = 16;
        ...
    }

    private void showScore() {
        tvScore.setText(...);   // geht nur, weil tvScore ein Feld ist
    }
}

Die Prüffrage: braucht das noch jemand ausser dieser einen Methode? Wenn nein, ist es eine lokale Variable. Android Studio hilft dir dabei und meldet gelb Field can be converted to a local variable, wenn ein Feld nur an einer Stelle gebraucht wird. Das ist keine Fehlermeldung, sondern ein Hinweis, den du prüfen sollst.

4. findViewById, und warum ein Feld leer bleibt

Ein Feld anzulegen erzeugt nichts. Es macht nur einen Platz für etwas, das später kommt.

private TextView tvScore;   // Platz da, Inhalt: null

Das null steht nicht da, aber es gilt. Ein Feld vom Typ einer Klasse ist am Anfang immer null. Erst diese Zeile füllt es:

tvScore = findViewById(R.id.tvScore);   // jetzt zeigt es auf die echte View

findViewById durchsucht das Layout, das setContentView vorher aufgebaut hat, und liefert die View mit dieser id zurück.

Ein Feld für eine View und sein findViewById gehören zusammen. Wer das eine schreibt, schreibt das andere gleich dazu.

Vergisst du die zweite Zeile, passiert genau das:

java.lang.NullPointerException: Attempt to invoke virtual method
  'void android.widget.TextView.setText(java.lang.CharSequence)'
  on a null object reference

Gelesen als Satz: du hast setText auf etwas aufgerufen, das nichts ist. Das Feld gibt es, gefüllt wurde es nie.

Die häufigste falsche Erklärung dafür. "Die View war noch nicht fertig geladen, mein Code war zu schnell."

Nein. Java läuft von oben nach unten und wartet auf jede Zeile, bis sie fertig ist. Es gibt kein zu früh und kein zu langsam. Wenn etwas null ist, wurde es nie gefüllt. Such nicht nach einer Verzögerung, such nach der fehlenden Zeile.

5. this und der Context

Sobald du eine View im Code erzeugst statt im XML, willst du plötzlich ein this mitgeben:

TextView row = new TextView(this);

Was this ist

this ist das Objekt, in dem die Methode gerade läuft. Steht die Methode in MainActivity, ist this genau dieses eine MainActivity-Objekt, das Android beim Start erzeugt hat.

Warum das passt

Der Konstruktor verlangt gar keine Activity. Er verlangt einen Context:

public TextView(Context context)

Dass deine Activity trotzdem hineinpasst, liegt an der Vererbung:

MainActivity
└─ AppCompatActivity
└─ FragmentActivity
└─ ComponentActivity
└─ Activity
└─ ContextThemeWrapper
└─ ContextWrapper
└─ Context

Eine Activity ist ein Context. Darum darfst du sie überall einsetzen, wo ein Context verlangt wird. Das ist kein Android-Trick, das ist normale Java-Vererbung, dieselbe Regel wie bei List<String> x = new ArrayList<>().

Woher du das im Alltag weisst

WegWieWas du siehst
Parameter-InfoCursor in die Klammer, Strg und PTextView(Context context)
Zur Quelle springenStrg und Klick auf TextViewAlle Konstruktoren im Original
VererbungsbaumCursor auf MainActivity, Strg und HDie Kette bis hinunter zu Context
Einfach probierentippenPasst es nicht, ist es sofort rot

Der letzte Weg ist der ehrlichste. Java prüft die Typen beim Übersetzen. Hier kannst du nicht still danebenliegen.

Warum eine View überhaupt einen Context braucht

Schau dir diese Zeile an:

row.setTextSize(14);

14 was? 14 sp. Wie viele Pixel das auf diesem Gerät sind, hängt von der Bildschirmdichte ab und von der Schriftgrösse, die der Benutzer in den Systemeinstellungen gewählt hat. Die TextView weiss das nicht von selbst. Sie fragt ihren Context.

Dasselbe gilt fürs Theme: welche Schriftart, welche Textfarbe, welcher Standardabstand. All das steht im Theme, und das Theme hängt am Context.

Eine View kann sich nicht selbst zeichnen. Sie braucht jemanden, der ihr sagt, wie gross, in welcher Farbe und in welcher Schrift. Dieser Jemand ist der Context.

Bei einer View aus dem XML passiert genau dasselbe, nur unsichtbar. setContentView liest das Layout und ruft für jedes Element denselben Konstruktor auf, mit derselben Activity als Context.

Nimm nicht getApplicationContext(). Es übersetzt und läuft, aber der Application-Context hat kein Theme. Deine erzeugten Views sähen dann anders aus als der Rest der App. Für alles Sichtbare nimmst du die Activity, also this.

6. Listener, und was sie mit this machen

Ein Listener ist eine Anweisung für später. Du sagst nicht "tu das jetzt", sondern "tu das, wenn jemand tippt".

btnNext.setOnClickListener(v -> onNextClicked());

Diese Zeile ruft onNextClicked nicht auf. Sie hinterlegt sie. Darum steht sie in onCreate, obwohl der Klick erst viel später kommt. Einmal anhängen, beliebig oft ausgelöst.

Eine Falle, die dich später einmal trifft. In einer Lambda wie oben bleibt this die Activity. Das ist einer der Gründe, warum wir Lambdas nehmen.

Schreibst du stattdessen eine anonyme innere Klasse, also new View.OnClickListener() { ... }, dann ist this dort der Listener und nicht mehr die Activity. Du bräuchtest dann MainActivity.this. Wenn dir eine KI so einen Block vorschlägt und danach etwas nicht mehr geht, ist das oft der Grund.

7. Von oben nach unten, immer

Java arbeitet eine Methode Zeile für Zeile ab und wartet bei jeder, bis sie fertig ist. Es gibt keine Zeile, die nebenher läuft, und keine, die überholt.

Das klingt selbstverständlich und wird trotzdem regelmässig vergessen, sobald etwas null ist. Die Reihenfolge in onCreate ist darum nicht beliebig:

1. setContentView baut das Layout auf
2. findViewById geht nur, wenn 1 gelaufen ist
3. Anfangszustand sichern geht nur, wenn 2 gelaufen ist
4. Listener anhängen geht nur, wenn 2 gelaufen ist
5. Daten laden
6. anzeigen geht nur, wenn alles davor gelaufen ist

Jede Stufe braucht die davor. Darum stürzt es ab, wenn du findViewById vor setContentView schreibst, und darum steht die anzeigende Methode ganz am Schluss.

8. Wenn etwas null ist, die Suchreihenfolge

Der häufigste Absturz der ganzen Woche. Geh diese vier Fragen der Reihe nach durch, dann findest du ihn in unter einer Minute.

NrFrageWenn nein
1Steht im Logcat, welche Methode und welche Zeile es war?Such die erste Zeile mit Caused by und darunter deinen eigenen Dateinamen
2Gibt es zu diesem Feld ein findViewById?Das ist meist schon die Antwort. Zeile ergänzen
3Stimmt die id im findViewById mit der im XML überein?Zeichen für Zeichen vergleichen. Gross und klein zählt
4Steht das findViewById nach dem setContentView?Nach oben schauen. Vorher gibt es das Layout noch nicht

Was du in dieser Liste nicht findest: irgendetwas mit Warten, Verzögern oder Timing. Wenn dir jemand vorschlägt, den Aufruf "später" oder "in einem Handler" zu machen, damit die View fertig ist, dann ist das die falsche Spur. Die View ist fertig. Dein Feld ist leer.

9. Prüfe dich selbst

  1. Such in deinem Projekt nach new MainActivity(). Warum findest du nichts, und wer erzeugt die Activity stattdessen?
  2. Du hast ein Feld tvScore angelegt, aber das findViewById vergessen. Beschreib in einem Satz, was beim Start passiert und warum.
  3. Warum darfst du this einsetzen, wenn ein Konstruktor einen Context verlangt? Antworte mit einem Satz über Vererbung.
  4. Nenn zwei Dinge, die eine TextView von ihrem Context erfahren muss, bevor sie sich zeichnen kann.
  5. Erkläre einem Lerngspänli, warum eine Zeile mit setOnClickListener in onCreate stehen darf, obwohl der Klick erst zehn Minuten später kommt.

Die vier Sätze dieser Seite

  • Android erzeugt deine Activity und ruft onCreate auf, einmal.
  • onCreate richtet ein, angezeigt wird woanders.
  • Ein Feld und sein findViewById gehören zusammen.
  • Eine View kann sich nicht selbst zeichnen, sie braucht einen Context.
