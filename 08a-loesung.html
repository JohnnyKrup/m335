Antworten zu den Denkfragen

1. Die Datei liegt in assets und nicht in res. Was verlierst du, was gewinnst du?

Du verlierst die Prüfung durch den Compiler. Bei R.layout.activity_admin ist ein Tippfehler rot, noch bevor du startest. Bei getAssets().open("questions_m335.json") ist der Name nur ein Text, und ein Tippfehler fällt erst zur Laufzeit auf. Deshalb steht er als Konstante da und deshalb wird der Fehlerfall geloggt.

Du gewinnst dafür eine Datei, die unverändert bleibt. res ist ein System aus Kategorien, Sprachen und Bildschirmgrössen, und Android sucht dort selbst aus, was es nimmt. Eine JSON-Datei will genau so ankommen, wie sie hineingelegt wurde, mit ihrem Namen und ihrem Inhalt. Die Faustregel: res für alles, was die App darstellt, assets für alles, was die App liest.

2. Was passiert, wenn du die id aus der Datei übernimmst?

Deine dreissig Fragen bekommen die Nummern 1 bis 30. Room merkt sich dabei nicht, dass es schon eine 30 gibt, denn du hast die Nummern ja selbst gesetzt und den Zähler nie benutzt. Die erste Frage, die jemand in 08B selbst anlegt, bekommt darum wieder die 1.

Und dann passiert genau das, was @Insert in dieser Lage tut: die bestehende Frage mit der 1 wird ersetzt. Der Benutzer legt eine Frage an, und eine andere verschwindet. Nichts stürzt ab, und der Zähler bleibt bei 30. Das ist die schwierigste Sorte Fehler, weil das Symptom an einer ganz anderen Stelle auftaucht als die Ursache.

Die Regel dahinter: eine id aus einer fremden Datei ist die id des anderen Systems, nicht deine. Wer sie übernimmt, übernimmt auch die Verantwortung dafür, dass sie eindeutig bleibt.

3. Wann hört onCreate auf zu reichen?

Heute reicht es, weil niemand die Fragen ändern kann. Du öffnest die Liste, sie lädt einmal, und solange du drin bist, ändert sich nichts.

In 08B ändert sich das. Dort tippst du auf den Plus-Knopf, legst eine Frage an und kommst zurück. Die AdminActivity wurde dabei nicht neu gebaut, sie war nur im Hintergrund. onCreate läuft also nicht nochmals, onResume schon. Mit onCreate würdest du deine neue Frage erst nach einem Neustart der App sehen.

Das ist der dritte Fall derselben Sache. Der erste war der Bestwert in 05D, der zweite die Rangliste in 06C. Der Unterschied: dort war es Vorsorge, in 08B ist es zum ersten Mal wirklich nötig.

QuestionAdapter.java, die ganze Klasse

package ch.wiss.m335.quiz;

import android.content.Context;
import android.view.LayoutInflater;
import android.view.View;
import android.view.ViewGroup;
import android.widget.TextView;

import androidx.annotation.NonNull;
import androidx.recyclerview.widget.RecyclerView;

import java.util.ArrayList;
import java.util.List;

import ch.wiss.m335.quiz.data.QuestionEntity;

/**
 * Füllt den RecyclerView mit den Zeilen der Fragenliste.
 *
 * Die Vorlage ist der HighscoreAdapter aus 06C und 07B. Der Aufbau ist
 * derselbe, nur die Daten sind andere. Das ist der Punkt: ein Adapter ist
 * immer gleich gebaut, egal was in der Liste steht.
 *
 * onCreateViewHolder baut eine leere Zeile. Das passiert selten.
 * onBindViewHolder füllt eine vorhandene Zeile. Das passiert bei jedem
 * Scrollen, viele Male pro Sekunde.
 *
 * Daraus folgt dieselbe Regel wie in 06C: in onBindViewHolder gehört
 * nichts, was Zeit kostet. Kein findViewById, keine Abfrage, kein Aufbau
 * von Objekten. Und vor allem kein Zugriff auf die Datenbank.
 *
 * Der Adapter zeigt nur an. Woher die Fragen kommen, entscheidet die
 * AdminActivity. Was beim Antippen geschehen soll, auch. Darum meldet der
 * Adapter den Klick weiter, statt ihn selbst zu behandeln.
 */
public class QuestionAdapter extends RecyclerView.Adapter<QuestionAdapter.QuestionViewHolder> {

    /**
     * Wird gerufen, wenn jemand eine Zeile antippt.
     *
     * Ein eigenes Interface mit genau einer Methode. Die Activity sagt
     * damit: gib mir Bescheid, den Rest mache ich selbst.
     */
    public interface OnQuestionClickListener {
        void onQuestionClick(QuestionEntity question);
    }

    /**
     * Die Fragen, die gerade angezeigt werden.
     *
     * Die Liste gehört dem Adapter. Ausgetauscht wird ihr Inhalt nur über
     * setQuestions, damit das notifyDataSetChanged nie vergessen geht.
     */
    private final List<QuestionEntity> questions = new ArrayList<>();

    /** Wer über Klicks informiert werden will. */
    private final OnQuestionClickListener listener;

    /**
     * @param listener die Activity, die auf Klicks reagiert
     */
    public QuestionAdapter(OnQuestionClickListener listener) {
        this.listener = listener;
    }

    /**
     * Hält die Views einer Zeile fest.
     *
     * Das ist der Sinn des ViewHolder: findViewById läuft einmal pro Zeile
     * und nicht bei jedem Scrollen.
     */
    static class QuestionViewHolder extends RecyclerView.ViewHolder {

        /** Der Fragetext, oben in der Zeile. */
        final TextView tvQuestionText;

        /** Kategorie und Schwierigkeit, kleiner darunter. */
        final TextView tvQuestionMeta;

        /**
         * Sucht die zwei TextViews einmal und merkt sie sich.
         *
         * @param itemView die frisch gebaute Zeile
         */
        QuestionViewHolder(@NonNull View itemView) {
            super(itemView);
            tvQuestionText = itemView.findViewById(R.id.tvQuestionText);
            tvQuestionMeta = itemView.findViewById(R.id.tvQuestionMeta);
        }
    }

    /**
     * Baut eine neue, leere Zeile aus item_question.xml.
     *
     * Das dritte Argument von inflate ist false. Mit true würde die Zeile
     * sofort an den Parent gehängt, und der RecyclerView bekäme eine
     * IllegalStateException mit dem Text "The specified child already has a
     * parent".
     *
     * @param parent   der RecyclerView, der die Zeile später einhängt
     * @param viewType wird hier nicht gebraucht, es gibt nur eine Zeilenart
     * @return ein ViewHolder mit den zwei TextViews darin
     */
    @NonNull
    @Override
    public QuestionViewHolder onCreateViewHolder(@NonNull ViewGroup parent, int viewType) {
        View row = LayoutInflater.from(parent.getContext())
                .inflate(R.layout.item_question, parent, false);
        return new QuestionViewHolder(row);
    }

    /**
     * Füllt eine vorhandene Zeile mit den Daten einer Frage.
     *
     * @param holder   die Zeile, die gefüllt wird
     * @param position der Platz in der angezeigten Liste, beginnend bei 0
     */
    @Override
    public void onBindViewHolder(@NonNull QuestionViewHolder holder, int position) {
        QuestionEntity question = questions.get(position);
        Context context = holder.itemView.getContext();

        holder.tvQuestionText.setText(question.getText());
        holder.tvQuestionMeta.setText(context.getString(R.string.question_meta_format,
                question.getCategory(), question.getDifficulty()));

        // Der Listener wird bei jedem Binden neu gesetzt, und das ist
        // richtig so. Die Zeile wird beim Scrollen wiederverwendet und
        // zeigt danach eine andere Frage.
        holder.itemView.setOnClickListener(v -> listener.onQuestionClick(question));
    }

    /** @return wie viele Zeilen die Liste hat */
    @Override
    public int getItemCount() {
        return questions.size();
    }

    /**
     * Tauscht die angezeigten Fragen aus.
     *
     * notifyDataSetChanged zeichnet die ganze Liste neu. Das ist grob, aber
     * verständlich und für dreissig Zeilen völlig ausreichend.
     *
     * @param newQuestions die Fragen, die angezeigt werden sollen
     */
    @SuppressWarnings("NotifyDataSetChanged")
    public void setQuestions(List<QuestionEntity> newQuestions) {
        questions.clear();
        questions.addAll(newQuestions);
        notifyDataSetChanged();
    }
}

Das question im Listener ist eine lokale Variable, und das geht nur, weil sie sich nicht mehr ändert. Java verlangt für einen Lambda-Ausdruck, dass die benutzte Variable effektiv final ist. Sie wird einmal gesetzt und nie wieder, also passt es.

Wer stattdessen questions.get(position) in den Listener schreibt, baut sich einen Fehler ein: position ist die Position von jetzt, und der Klick kommt später, wenn die Zeile vielleicht schon eine andere Frage zeigt.

Das @SuppressWarnings("NotifyDataSetChanged") ist kein Muss. Android Studio schlägt vor, statt notifyDataSetChanged die feineren Methoden zu benutzen, die nur einzelne Zeilen melden. Bei dreissig Zeilen bringt das nichts, und die Zeile sagt ehrlich: wir wissen davon und nehmen den groben Weg.

AdminActivity.java, die ganze Klasse

package ch.wiss.m335.quiz;

import android.os.Bundle;
import android.util.Log;
import android.view.View;
import android.widget.TextView;

import androidx.activity.EdgeToEdge;
import androidx.appcompat.app.AppCompatActivity;
import androidx.core.graphics.Insets;
import androidx.core.view.ViewCompat;
import androidx.core.view.WindowInsetsCompat;

import androidx.recyclerview.widget.RecyclerView;

import java.util.List;

import ch.wiss.m335.quiz.data.QuestionEntity;
import ch.wiss.m335.quiz.data.QuizDatabase;

/**
 * Zeigt alle Fragen, die in der Datenbank stehen.
 *
 * Die Vorlage ist die AboutActivity, der Aufbau der Liste kommt aus der
 * HighscoreActivity von 06C und 07B. Dieselben drei Bausteine:
 * Zeilenlayout, Adapter, LayoutManager. Neu sind zwei Dinge.
 *
 * Erstens kommen die Daten aus der Datenbank statt aus SharedPreferences.
 * Der Weg dahin ist immer derselbe: QuizDatabase.getInstance, dann
 * questionDao, dann die Abfrage.
 *
 * Zweitens gibt es einen leeren Zustand. Eine leere Fläche sagt dem
 * Benutzer nichts. Sie sieht gleich aus, wenn keine Daten da sind, und
 * wenn etwas kaputt ist. Ein Text, der den Unterschied benennt, kostet
 * zwei Zeilen und spart viel Sucherei.
 *
 * Sortiert wird hier nicht. Das erledigt schon das ORDER BY im Dao. In der
 * HighscoreActivity steht ein Collections.sort, das gehört hier bewusst
 * nicht hin.
 */
public class AdminActivity extends AppCompatActivity
        implements QuestionAdapter.OnQuestionClickListener {

    /** Log-Tag für das ganze Modul 335. */
    private static final String TAG = "Modul335";

    /** Der Titel oben. Er trägt die Anzahl Fragen. */
    private TextView tvAdminTitle;

    /** Der Text, der erscheint, wenn keine Frage da ist. */
    private TextView tvEmpty;

    /** Die Liste der Fragen. */
    private RecyclerView rvQuestions;

    /** Der Adapter, der die Zeilen füllt. */
    private QuestionAdapter adapter;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        EdgeToEdge.enable(this);
        setContentView(R.layout.activity_admin);

        // 16dp eigener Rand, in Pixel umgerechnet über die Dichte des Geräts.
        final int extraPadding = Math.round(16 * getResources().getDisplayMetrics().density);

        // Wichtig: der eigene Rand wird zu den System-Insets dazugerechnet.
        // Type.ime() braucht es hier nicht, dieser Bildschirm hat kein
        // Eingabefeld.
        ViewCompat.setOnApplyWindowInsetsListener(findViewById(R.id.clAdmin), (v, insets) -> {
            Insets systemBars = insets.getInsets(WindowInsetsCompat.Type.systemBars());
            v.setPadding(
                    systemBars.left + extraPadding,
                    systemBars.top + extraPadding,
                    systemBars.right + extraPadding,
                    systemBars.bottom + extraPadding);
            return insets;
        });

        tvAdminTitle = findViewById(R.id.tvAdminTitle);
        tvEmpty = findViewById(R.id.tvEmpty);
        rvQuestions = findViewById(R.id.rvQuestions);

        // Ohne LayoutManager bleibt die Liste leer. Keine Exception, kein
        // Eintrag unter unserem Tag, nur eine leere Fläche.
        rvQuestions.setLayoutManager(new LinearLayoutManager(this));

        adapter = new QuestionAdapter(this);
        rvQuestions.setAdapter(adapter);

        Log.d(TAG, "AdminActivity onCreate");
    }

    /**
     * Lädt die Fragen jedes Mal neu, wenn der Bildschirm erscheint.
     *
     * Dieselbe Überlegung wie bei der Rangliste: onCreate läuft nur einmal,
     * onResume bei jeder Rückkehr. Ab 08B wird das wichtig, denn dann kommt
     * man von einem Formular hierher zurück.
     */
    @Override
    protected void onResume() {
        super.onResume();

        List<QuestionEntity> questions = QuizDatabase.getInstance(this).questionDao().getAll();

        adapter.setQuestions(questions);
        tvAdminTitle.setText(getString(R.string.title_admin_format, questions.size()));
        showEmptyState(questions.isEmpty());

        Log.d(TAG, "questions loaded, total=" + questions.size());
    }

    /**
     * Reagiert auf einen Klick in der Liste.
     *
     * Heute nur ein Log-Eintrag. In 08C öffnet diese Methode das Formular
     * zum Bearbeiten.
     *
     * @param question die angetippte Frage
     */
    @Override
    public void onQuestionClick(QuestionEntity question) {
        Log.d(TAG, "question clicked, id=" + question.getId());
    }

    /**
     * Schaltet zwischen Liste und leerem Zustand um.
     *
     * Es ist immer genau eines von beiden zu sehen. Darum steht das
     * Umschalten in einer einzigen Methode und nicht an zwei Stellen.
     *
     * @param empty true, wenn keine Frage da ist
     */
    private void showEmptyState(boolean empty) {
        tvEmpty.setVisibility(empty ? View.VISIBLE : View.GONE);
        rvQuestions.setVisibility(empty ? View.GONE : View.VISIBLE);
    }
}

Der rvQuestions ist hier ein Feld, in der HighscoreActivity ist er eine lokale Variable. Der Unterschied hat einen Grund: dort spricht ihn nach onCreate niemand mehr an, hier braucht ihn showEmptyState.

Die Regel: ein Feld nur für das, was mehr als eine Methode braucht. Ein Feld, das nur an einer Stelle vorkommt, behauptet etwas, das nicht stimmt.

Teil B, der Startbestand

Was in der QuizDatabase dazukommt

Der Rest deiner QuizDatabase steht im Lösungsmaterial von 07C. Hier stehen nur die neuen Teile.

Wenn dir die Aufteilung auf drei Klassen immer noch unklar ist, lies das Grundlagenblatt Room verstehen aus 07C. Es sagt in einem Abschnitt, warum Question und QuestionEntity nebeneinander liegen, und was QuizDatabase überhaupt tut.

Die Konstante:

/** Der Startbestand, liegt unter app/src/main/assets. */
private static final String ASSET_NAME = "questions_m335.json";

Der Aufruf in getInstance:

public static synchronized QuizDatabase getInstance(Context context) {
    if (instance == null) {
        Context appContext = context.getApplicationContext();

        instance = Room.databaseBuilder(appContext, QuizDatabase.class, DB_NAME)
                .allowMainThreadQueries()
                .build();

        seedIfEmpty(appContext);

        // Erst nach dem Seed, damit die Zahl den Endstand meldet. In 07C
        // stand hier eine Null, ab jetzt sind es dreissig.
        Log.d(TAG, "database opened, name=" + DB_NAME
                + ", questions=" + instance.questionDao().count());
    }
    return instance;
}

Die Log-Zeile ist gewandert, und das ist die einzige Änderung an bestehendem Code in diesem Auftrag. In 07C stand sie direkt nach dem build() und meldete null. Dort war das die Aussage: die Tabelle entsteht erst beim ersten Zugriff.

Ab heute ist der erste Zugriff der Startbestand. Bliebe die Zeile oben, würde sie für immer null melden, obwohl dreissig Zeilen darin stehen. Und du hättest sie beim Prüfen der Entdeckungsstelle nicht als Kontrolle, denn beim doppelten Seed meldet sie sechzig.

Das Lesen aus assets: steht vollständig im Auftrag, B2.

Und die Methode, die du selbst geschrieben hast:

/**
 * Füllt die Tabelle beim allerersten Start mit dem Startbestand.
 *
 * Die Bedingung count() > 0 ist der Kern dieser Methode. Ohne sie kämen
 * bei jedem Start dreissig Fragen dazu, und nach fünf Starts stünden
 * hundertfünfzig in der Liste.
 *
 * Die id aus der Datei wird nicht gelesen. Room vergibt eine eigene. Sonst
 * würde die erste selbst angelegte Frage mit der Frage Nummer 1 aus der
 * Datei zusammenstossen.
 *
 * @param appContext der Context der App, für den Zugriff auf assets
 */
private static void seedIfEmpty(Context appContext) {
    QuestionDao dao = instance.questionDao();

    int existing = dao.count();
    if (existing > 0) {
        Log.d(TAG, "seed skipped, count=" + existing);
        return;
    }

    try {
        JSONArray array = new JSONArray(readAsset(appContext));

        for (int i = 0; i < array.length(); i++) {
            JSONObject object = array.getJSONObject(i);
            JSONArray answers = object.getJSONArray("answers");

            QuestionEntity question = new QuestionEntity();
            question.setText(object.getString("text"));
            question.setAnswer1(answers.getString(0));
            question.setAnswer2(answers.getString(1));
            question.setAnswer3(answers.getString(2));
            question.setAnswer4(answers.getString(3));
            question.setCorrectAnswer(object.getString("correctAnswer"));
            question.setCategory(object.getString("category"));
            question.setDifficulty(object.getString("difficulty"));

            dao.insert(question);
        }

        Log.d(TAG, "seed done, count=" + dao.count());

    } catch (JSONException e) {
        // Die Datei ist da, aber sie passt nicht zum erwarteten Aufbau.
        Log.e(TAG, "seed failed, json not readable", e);
    }
}

Deine Version darf anders aussehen. Eine Schleife mit for (int i ...) über array.length() ist der übliche Weg, weil JSONArray kein Iterable ist. Wer die Schlüsselnamen als Konstanten führt, wie du es in 06B in der HighscoreStorage gemacht hast, macht es sogar besser.

Was nicht abweichen darf: die Prüfung ganz oben, kein setId, und ein catch, der loggt.

Warum dao.count() am Schluss nochmals gefragt wird, statt mitzuzählen. Eine eigene Zählvariable sagt aus, wie oft insert aufgerufen wurde. count() sagt aus, wie viele Zeilen wirklich in der Tabelle stehen. Die zwei sind fast immer gleich, und wenn nicht, willst du genau das wissen.

Die Stelle aus B3, aufgelöst

Nach dem zweiten Start stehen sechzig Fragen da, nach dem dritten neunzig.

Die Ursache ist eine fehlende Bedingung. getInstance baut die Datenbank auf, wenn instance noch null ist. Beim Beenden der App verschwindet der ganze Prozess, also auch das statische Feld. Beim nächsten Start ist es wieder null, die Datenbank wird neu aufgebaut, und seedIfEmpty läuft erneut.

Die Datei ist dabei nie das Problem. Sie enthält immer dieselben dreissig Fragen. Was fehlt, ist die Frage, ob sie schon einmal gelesen wurde.

Warum ausgerechnet count() und nicht ein Merker in den SharedPreferences. Ein Merker sagt aus, was die App einmal getan hat. count() sagt aus, wie die Daten gerade wirklich aussehen.

Die zwei gehen auseinander, sobald jemand die App-Daten löscht oder ein Backup zurückspielt. Dann steht im Merker schon gemacht und in der Tabelle nichts. Frag die Daten, nicht dein Gedächtnis. Das ist übrigens genau der Fehler, der in diesem Modul beim Planen auch schon passiert ist.

Und warum die Methode trotzdem so heissen darf. Nach der Reparatur hält der Name sein Versprechen: sie füllt, wenn leer. Vorher war er eine Behauptung. Ein Name, der mehr verspricht als der Rumpf hält, ist die teuerste Art von Kommentar, denn man liest ihn hundertmal und den Rumpf einmal.

Lösungen zu den Übungen

Die Texte nachziehen. about_tech behauptete, die Fragen stünden fest im Code. Das war seit Teil B falsch, und es steht auf dem Bildschirm Über die App, den jeder anschaut. Ein Text, den die App selbst zeigt, veraltet genauso wie ein Kommentar, nur sieht ihn jemand.

Der leere Zustand bekommt seinen Grund. Eine mögliche Version steht oben bei den Strings. Wichtig sind drei Dinge im Satz: dass keine Frage da ist, dass der Startbestand der Grund dafür ist, und wo man nachschauen kann.

Der kurze Satz aus dem Block war nicht falsch, er war nur unvollständig. Ein leerer Zustand, der den wahrscheinlichsten Grund kennt, soll ihn nennen. Und wenn du die Datei zum Prüfen umbenennst, siehst du deinen eigenen Satz genau in der Lage, für die er geschrieben ist.

Kommentare nachziehen. Eine mögliche Version steht oben im Code. Wichtig ist nicht der Wortlaut, sondern dass drei Dinge im Klassenkommentar der AdminActivity vorkommen: dass der Bildschirm zwei Gesichter hat, woher die Daten kommen, und warum in onResume geladen wird.

Und die zwei Klassen, die du nur nebenbei angefasst hast. In der MainActivity stand, ein Eintrag sei noch gesperrt und die Tabelle werde erst in 08A gefüllt. In der QuestionBank stand, eine Datenbank komme erst noch. Beides waren richtige Sätze, bis heute Nachmittag.

Das ist die teuerste Sorte, und du hast sie heute an vier Stellen gesehen: ein Text wird nicht falsch, weil jemand ihn falsch geschrieben hat, sondern weil der Code darunter weitergewachsen ist. Kein Werkzeug meldet das.

Und die Zahlwörter im Adapter. Sie stehen an zwei Stellen, im Konstruktor des ViewHolder und im @return von onCreateViewHolder. Dort steht vier, wenn du die Hausaufgabe aus 07B gemacht hast, und sonst noch drei. Beide Sätze stammen aus dem HighscoreAdapter und waren dort richtig. Genau daran erkennst du die teure Sorte: sie werden nicht falsch, weil jemand sie falsch geschrieben hat, sondern weil sie in eine andere Klasse gewandert sind.

Übung 1, der leere Zustand in der Rangliste. Dieselben zwei Zeilen wie hier, nur an einer anderen Stelle. In activity_highscore.xml kommt eine TextView dazu, in applyFilter die Umschaltung am Ende:

boolean empty = shown.isEmpty();
tvHighscoreEmpty.setVisibility(empty ? View.VISIBLE : View.GONE);

Der Satz darf hier konkreter sein als bei den Fragen, denn du weisst, warum nichts da ist: In dieser Kategorie hast du noch nicht gespielt. Ein leerer Zustand, der den Grund kennt, soll ihn auch nennen.

Übung 2, den Startbestand verändern. Der Zähler bleibt bei 30, weil seedIfEmpty die Datei gar nicht mehr liest. Die Tabelle ist nicht leer, also steigt die Methode nach der ersten Zeile aus.

Damit deine Frage erscheint, musst du die App-Daten löschen. Danach ist die Tabelle leer, die Datei wird gelesen, und es sind einunddreissig.

Der Punkt der Übung liegt aber woanders: so verhält sich jede App mit einem Startbestand. Die Datei in assets ist eine Erstausstattung und keine laufende Quelle. Wer sie ändert, erreicht damit nur Geräte, auf denen die App noch nie lief. Alle anderen brauchen einen anderen Weg, und der heisst in echten Apps Migration.

Übung 3, erklären. Die kürzeste richtige Antwort: Leeren und neu schreiben würde funktionieren, aber es würde alles wegwerfen, was der Benutzer selbst angelegt oder geändert hat. Zählen und aussteigen fasst Bestehendes nicht an.

Ab 08B ist das nicht mehr theoretisch. Dort legt jemand eigene Fragen an, und die stehen in derselben Tabelle.

Zur Zusatzaufgabe steht hier bewusst nichts. Ein Hinweis trotzdem, weil die Begründung mehr wert ist als der Code: du hast die Liste in onResume ohnehin schon vollständig geladen. Eine zweite Abfrage holt dieselben Daten ein zweites Mal aus derselben Tabelle. Bei dreissig Zeilen ist beides schnell, aber nur eines von beiden ist ehrlich.
