Teil A, der beste Wert 17 Minuten

A1Das Paket data und die Klasse ScoreStorage.

Rechtsklick auf ch.wiss.m335.quiz, dann New, dann Package, Name data. Darin Rechtsklick, New, Java Class, Name ScoreStorage.

Dann den Inhalt:

package ch.wiss.m335.quiz.data;

import android.content.Context;
import android.content.SharedPreferences;

/**
 * Speichert den besten Punktestand dauerhaft auf dem Gerät.
 *
 * (HIER: zwei bis drei Zeilen, was SharedPreferences sind
 *  und wie lange sie halten)
 */
public final class ScoreStorage {

    /** Der Name der XML-Datei im Ordner der App. */
    private static final String PREFS_NAME = "m335_quiz";

    /** Der Schlüssel, unter dem der beste Wert liegt. */
    private static final String KEY_BEST_SCORE = "bestScore";

    /** Bedeutet: es wurde noch nie eine Runde beendet. */
    public static final int NO_SCORE_YET = -1;

    /** Diese Klasse wird nie erzeugt, sie hat nur statische Methoden. */
    private ScoreStorage() {
    }

    /**
     * Liest den besten Punktestand.
     *
     * @param context irgendein Context, meistens die Activity
     * @return der beste Wert, oder NO_SCORE_YET wenn noch keiner da ist
     */
    public static int getBestScore(Context context) {
        return prefs(context).getInt(KEY_BEST_SCORE, NO_SCORE_YET);
    }

    /**
     * Speichert den Punktestand, falls er besser ist als der bisherige.
     *
     * @param context irgendein Context
     * @param score   der Punktestand der eben beendeten Runde
     * @return true, wenn ein neuer Bestwert gespeichert wurde
     */
    public static boolean saveIfBetter(Context context, int score) {
        if (score <= getBestScore(context)) {
            return false;
        }
        prefs(context).edit().putInt(KEY_BEST_SCORE, score).apply();
        return true;
    }

    /**
     * Öffnet die Ablage der App.
     *
     * @param context irgendein Context, meistens die Activity
     * @return die Ablage dieser App
     */
    private static SharedPreferences prefs(Context context) {
        return context.getSharedPreferences(PREFS_NAME, Context.MODE_PRIVATE);
    }
}

Die drei Zeilen, an denen alles hängt.

edit() gibt dir einen Editor. Der sammelt nur. Erst apply() gibt den Auftrag zum Schreiben ab. Ohne apply() passiert gar nichts, und nichts warnt dich.

getInt(schluessel, vorgabe) liefert die Vorgabe zurück, wenn der Schlüssel nicht da ist. Auch dann, wenn du ihn falsch geschrieben hast. Genau darum stehen Name und Schlüssel als Konstante an einer Stelle.

MODE_PRIVATE heisst: nur diese App darf lesen. Die alten Modi MODE_WORLD_READABLE und MODE_WORLD_WRITEABLE sind seit Android 7 gesperrt.

Warum eine eigene Klasse und nicht drei Zeilen in der Activity. So stehen der Name der Ablage und der Schlüssel an genau einem Ort. Wer sie in zwei Activities einzeln hinschreibt, hat beim ersten Tippfehler zwei getrennte Ablagen und merkt es nicht.

Und der Vergleich ist der Wert besser steckt in saveIfBetter. Damit kann ihn keine Aufrufstelle vergessen. Dasselbe Muster wie isCorrect in Question: das Verhalten gehört dorthin, wo die Daten liegen.

A2Die Runde speichert ihr Ergebnis.

In GameActivity.java, in der Methode showResult, nach dem Aufruf von publishResult():

// Der beste Wert wird hier gespeichert und nicht im Menü.
// Hier entsteht das Ergebnis.
boolean isNewBest = ScoreStorage.saveIfBetter(this, score);

Und die Log-Zeile am Ende derselben Methode wird länger, damit du den Rückgabewert siehst:

Log.d(TAG, "round finished, score=" + score + " newBest=" + isNewBest);

Der Import kommt mit Alt und Enter.

Warum hier und nicht im Menü. Das Menü bekommt das Ergebnis zwar über den Rückkanal aus 05B. Aber Android darf eine Activity im Hintergrund jederzeit abräumen, wenn der Speicher knapp wird. Dann wird das Menü beim Zurückkommen neu gebaut, und auf den Rückkanal ist kein Verlass.

Dieselbe Regel wie beim setResult in 05B: tu es dort, wo das Ergebnis entsteht.

Sag in einem Satz, was zwischen Schritt 3 und Schritt 5 anders war. Nicht am Bildschirm, sondern in deinem Code. Genau danach fragt der Wissenscheck.

Nicht reparieren, nur schauen. Repariert wird in A5.

Der Wert ist gespeichert, da liegt der Fehler nicht. Schau im Device Explorer nach, wenn du es nicht glaubst. Der Weg dorthin steht im Blatt Wo deine App ihre Daten ablegt.

Wenn du zwischendurch nochmals bei null anfangen willst, etwa weil du dich verklickt hast, dann löschst du die Daten deiner App. Das geht im Emulator, nicht in Android Studio:

Im laufenden Emulator die App-Übersicht öffnen, dann Settings, Apps, WissQuiz, Storage and cache, Clear storage. Genauso gut geht es, die App im Emulator zu deinstallieren.

Beim ersten Durchgang brauchst du das nicht. Vor heute hat deine App noch nie etwas gespeichert.

Nimm nicht Wipe Data aus dem Device Manager. Das steht in Android Studio im Menü hinter den drei Punkten neben deinem Gerät, und es klingt nach dem Richtigen. Es setzt aber den ganzen Emulator zurück, also auch alle anderen Apps darauf, und es dauert lange.

Die Regel: Clear storage trifft deine App, Wipe Data trifft das ganze Gerät. Mehr dazu im Blatt Wo deine App ihre Daten ablegt, Abschnitt 4.

A5Gelesen wird in onResume.

Nimm den Aufruf showBestScore(); aus onCreate wieder heraus. Er kommt in eine eigene Methode, direkt unter onCreate:

/**
 * Läuft jedes Mal, wenn dieser Bildschirm in den Vordergrund kommt.
 *
 * Also nach dem Start, nach der Rückkehr aus der GameActivity und nach
 * dem Wechsel aus einer anderen App.
 */
@Override
protected void onResume() {
    super.onResume();
    showBestScore();
}

Run. Spiel eine Runde, geh zurück. Der beste Wert steht jetzt sofort richtig da.

Warum das der Unterschied ist

MethodeLäuft wannWie oft, wenn du einmal spielst und zurückkommst
onCreatewenn die Activity entstehteinmal, ganz am Anfang
onResumewenn die Activity in den Vordergrund kommtzweimal, beim Start und beim Zurückkommen

Deine MainActivity wird beim Zurückkommen aus dem Spiel nicht neu gebaut. Sie war die ganze Zeit da, nur verdeckt. Darum lief onCreate nicht, und darum stand oben noch der alte Text.

Diese Sorte Fehler ist die schlimmste. Sie tritt nicht immer auf. Wenn Android das Menü im Hintergrund abräumt, wird es beim Zurückkommen neu gebaut, dann läuft onCreate doch, und dann stimmt der Wert plötzlich. Auf einem Gerät mit wenig Speicher würdest du den Fehler nie sehen.

Die Regel dahinter: Frag nicht, wo ein Aufruf gut aussieht. Frag, wann er laufen muss. Wenn die Antwort jedes Mal beim Anzeigen lautet, gehört er nicht in onCreate.

So prüfst du Teil A.

  • In onCreate steht kein Aufruf von showBestScore mehr. Er steht nur noch in onResume.
  • Beim allerersten Start steht oben Noch kein Bestwert. Dasselbe nach Clear storage.
  • Nach einer Runde mit 3 Punkten steht oben Bester Wert: 3 Punkte, und zwar sofort beim Zurückkommen.
  • Eine schlechtere Runde ändert die untere Zeile, die obere bleibt.
  • Eine bessere Runde ändert beide.
  • App ganz beenden und neu starten: der beste Wert steht noch da.
  • Im Device Explorer liegt unter shared_prefs die Datei m335_quiz.xml mit deinem Wert.
  • Im Logcat steht nach jeder Runde round finished, score=x newBest=true oder false, und bei jeder Rückkehr best score read, value=x.

Teil B, was der Neubau überlebt 18 Minuten

B1Zuerst muss das Menü ins Querformat passen.

Dreh dein Gerät im Menü einmal, bevor du irgendetwas baust. Die Knöpfe im Emulatorrahmen machen das, oder Strg und F11.

Der unterste Knopf ist weg. Das Menü ist länger als der Bildschirm im Querformat, und ein LinearLayout schneidet einfach ab, was nicht mehr passt. Es scrollt nicht von selbst.

Wenn sich gar nichts dreht: im Emulator ist die automatische Drehung ausgeschaltet. Zieh die Statusleiste herunter und schalte Auto-rotate ein. Oder unter Settings, Display, Auto-rotate screen.

Das kennst du schon. Genau dieselbe Sache hattest du in 04A beim Fragebereich. Die Lösung ist dieselbe: eine ScrollView um den ganzen Inhalt.

In activity_main.xml legst du eine ScrollView um das LinearLayout llMenu:

     nicht unten abgeschnitten wird. -->

    android:layout_width="0dp"
    android:layout_height="0dp"
    app:layout_constraintBottom_toBottomOf="parent"
    app:layout_constraintEnd_toEndOf="parent"
    app:layout_constraintStart_toStartOf="parent"
    app:layout_constraintTop_toTopOf="parent">

    <!-- hier hinein kommt dein llMenu, unverändert bis auf die
         vier Zeilen unten -->

</ScrollView>

Und am LinearLayout llMenu ändern sich vier Zeilen. Die Anker braucht es nicht mehr, denn jetzt sitzt es in der ScrollView und nicht mehr direkt im ConstraintLayout:

WegNeu

Die Höhe bleibt wrap_content. Das ist wichtig: der Inhalt der ScrollView darf so hoch werden, wie er will.

Eine ScrollView hat genau ein Child. Nicht zwei, nicht fünf. Darum steckt der Inhalt in einem LinearLayout, und das ist dieses eine Child. Wer zwei Elemente direkt hineinlegt, bekommt ScrollView can host only one direct child.

Und die Höhe ist der ganze Trick. Die ScrollView selbst ist 0dp hoch, also genau so hoch wie der Bildschirm. Ihr Inhalt ist wrap_content, also so hoch wie nötig. Genau aus dieser Differenz entsteht das Scrollen.

Run, drehen, nach unten wischen. Alle vier Knöpfe sind erreichbar.

Warum das hierher gehört und nicht in Teil A. Gleich prüfst du, was der Neubau beim Drehen überlebt. Wenn du dabei nur die Hälfte des Bildschirms siehst, prüfst du nichts. Erst muss das Werkzeug funktionieren, dann kannst du damit messen.

Und der Aufbau ist derselbe wie in 05C: zuerst aufräumen, dann das eigentliche Thema.

B2Jetzt nochmals drehen. Und diesmal die zwei Zeilen anschauen.

Spiel eine Runde, geh ins Menü zurück, und dreh erst dann.

Eine Zeile bleibt stehen, die andere ist leer.

Beim Drehen wird deine Activity abgeräumt und neu gebaut. Android tut das, weil sich das Layout ändern kann. Ein neues Objekt heisst neue Felder, und die stehen auf ihrem Anfangswert.

Der beste Wert übersteht das trotzdem. Er lebt nicht in einem Feld, sondern in einer Datei, und onResume liest ihn nach dem Neubau sofort wieder.

B3Der Zettel für den Neubau.

Android bietet dir für genau diesen Fall ein Bundle an. Zwei Schlüssel zuerst, zu den anderen Konstanten in MainActivity:

/** Schlüssel für die Punkte der letzten Runde im Bundle. */
private static final String KEY_LAST_SCORE = "lastScore";

/** Schlüssel für die Anzahl Fragen der letzten Runde im Bundle. */
private static final String KEY_LAST_TOTAL = "lastTotal";

Und die Methode, unter onResume:

/**
 * Legt die Werte weg, die den Neubau dieser Activity überstehen sollen.
 *
 * @param outState der Zettel, den der Neubau später zurückbekommt
 */
@Override
protected void onSaveInstanceState(@NonNull Bundle outState) {
    super.onSaveInstanceState(outState);
    outState.putInt(KEY_LAST_SCORE, lastScore);
    outState.putInt(KEY_LAST_TOTAL, lastTotal);

    Log.d(TAG, "state saved, lastScore=" + lastScore + "/" + lastTotal);
}

Der Import von NonNull kommt mit Alt und Enter, es ist der aus androidx.annotation.

Der beste Wert gehört hier nicht hinein. Er liegt in der Datei und wird in onResume ohnehin neu gelesen. Dieselbe Information an zwei Orten zu halten, geht beim nächsten Umbau schief: einer wird geändert, der andere vergessen.

B4Den Zettel wieder lesen.

Der Zettel kommt genau dort zurück, wo du ihn seit 01B jeden Tag siehst und noch nie gebraucht hast: als Parameter von onCreate.

In onCreate, nach den findViewById-Zeilen und vor dem Aufruf von showLastScore():

// Der Neubau bringt seinen Zettel mit. Beim allerersten Start ist er
// null, dann bleiben die Felder auf ihrem Anfangswert.
if (savedInstanceState != null) {
    lastScore = savedInstanceState.getInt(KEY_LAST_SCORE, NO_ROUND_YET);
    lastTotal = savedInstanceState.getInt(KEY_LAST_TOTAL, 0);

    Log.d(TAG, "state restored, lastScore=" + lastScore + "/" + lastTotal);
}

Die Prüfung auf null ist Pflicht. Beim allerersten Start gibt es keinen Zettel, dann ist der Parameter null. Ohne die Prüfung stürzt die App beim Start ab, und zwar immer.

Und die Reihenfolge zählt. Erst die Felder füllen, dann anzeigen. Wer showLastScore() vorher aufruft, zeigt den alten Anfangswert an und danach nie mehr etwas anderes.

B5Nochmals drehen. Und dann die Bilanz.

Run. Spiel eine Runde, geh ins Menü, dreh das Gerät. Beide Zeilen bleiben stehen.

Und jetzt beende die App ganz und starte sie neu. Der beste Wert steht noch da, die letzte Runde ist wieder leer.

Damit hat dein Menü drei Arten von Gedächtnis nebeneinander:

WomitDrehenApp beendenDeinstallierenWofür
Ein Feld in der Klasseneinneinneinalles, was nur während einer Runde gilt
Feld plus BundlejaneinneinZustand, den der Neubau nicht verlieren darf
SharedPreferencesjajaneineinzelne Werte, die dem Benutzer gehören

Der Aufbau des Bildschirms ist kein Zufall. Zwei Zeilen, zwei Speicher, ein Unterschied, den du in vier Sekunden vorführen kannst. Merk dir die Reihenfolge der Prüfung: erst drehen, dann beenden. Wer nur dreht, sieht den Unterschied nicht, denn das Drehen überstehen beide.

So prüfst du Teil B.

  • Im Querformat sind alle vier Knöpfe erreichbar, notfalls nach dem Wischen.
  • Im Hochformat sieht das Menü aus wie vorher. Die ScrollView darf nichts verschieben.
  • Drehen im Menü: beide Zeilen bleiben, wie sie waren.
  • App ganz beenden und neu starten: der beste Wert bleibt, die letzte Runde ist auf Noch keine Runde gespielt zurück.
  • Ganz frischer Start nach Clear storage: kein Absturz, obwohl es keinen Zettel gibt.
  • Im Logcat steht beim Drehen zuerst state saved und danach state restored mit denselben Zahlen.
  • In onSaveInstanceState steht nichts über den besten Wert.

onResumeder Block mit dem wann. Das ist der wichtigste Kommentar dieses Auftrags
onSaveInstanceStateder Block mit @param, samt dem Satz, was hier bewusst nicht hineingehört
ScoreStorageKlassenkommentar plus je ein Block auf den drei Methoden

Lies deine Kommentare am Schluss ganz durch. Ein Rest wie das Wort HIER, das Wort WEG oder eine leere Klammer fällt in einem Javadoc-Block nie auf, weil nichts ihn meldet.

Warum das ein eigener Schritt ist und keine Fleissarbeit. Kommentare veralten still. Kein Compiler warnt, die App läuft, und alles sieht in Ordnung aus.

Hier ist es besonders heikel, weil der alte Satz nicht komplett falsch ist, sondern nur noch für eine der zwei Zeilen gilt. Ein halb richtiger Kommentar ist am gefährlichsten, denn er klingt beim Lesen plausibel.

So prüfst du Teil C.

  • Im Klassenkommentar der MainActivity steht, dass es zwei Zeilen mit verschieden langem Gedächtnis gibt.
  • Im Klassenkommentar steht, warum in onResume gelesen wird.
  • onResume, onSaveInstanceState, showBestScore, tvBestScore und die zwei Schlüssel haben je einen Kommentar.
  • ScoreStorage hat einen Klassenkommentar, der sagt, wie lange die Werte halten.
  • Nirgends steht mehr das Wort HIER, das Wort WEG oder eine leere Klammer.

Übungen 6 Minuten

Ohne Vorlage. Die Lösungen findest du im Material 05D Lösung - Der beste Wert bleibt.

Übung 1, Runden zählen

Speichere zusätzlich, wie viele Runden insgesamt schon gespielt wurden, und zeig die Zahl im Menü an. Der Zähler gehört in ScoreStorage, nicht in die Activity.

So prüfst du: Nach drei Runden steht dort eine 3. Nach dem Beenden und Neustart der App steht sie immer noch da und zählt weiter.

Übung 2, den neuen Bestwert feiern

Der Rückgabewert von saveIfBetter landet bisher nur im Logcat. Nutze ihn: wenn eine Runde einen neuen Bestwert bringt, soll das im Ergebnisbereich stehen.

So prüfst du: Die erste Runde bringt immer einen neuen Bestwert. Eine schlechtere Runde danach bringt keinen, und dann steht der Text auch nicht da.

Übung 3, erklären

Erkläre einem Lerngspänli, warum der beste Wert in onResume gelesen wird und nicht in onCreate.

So prüfst du: Dein Gegenüber kann sagen, was am Bildschirm passiert, wenn man es doch in onCreate macht, und warum der Fehler manchmal nicht auftritt.

Zusatzaufgabe für Schnelle

Zuerst die Pflichtaufgabe fertig und lauffähig. Dann erst hier weiter.

Auftrag: Speichere zusätzlich, wann der beste Wert erreicht wurde, und zeig es im Menü an.

Und die Frage, die dazugehört: Überleg dir vorher, in welcher Form du das Datum ablegst, damit man später auch danach sortieren könnte. Warum ist ein Datum als Text nicht dasselbe wie ein Datum als Zahl?

Keine Musterlösung. KI darfst du benutzen, aber du musst deine Lösung erklären können.
