Antworten zu den Denkfragen

1. Ein Bildschirm oder zwei?

Dafür, zwei zu bauen: jeder Bildschirm wäre für sich einfacher. Kein if, kein showMode, keine Verzweigung beim Speichern.

Dagegen, und darum machen wir es nicht: die elf Felder wären zweimal da. Jede Änderung müsste zweimal gemacht werden, und beim ersten Mal, wo jemand nur eine der zwei Stellen anfasst, laufen die zwei auseinander. In 08C kommen zwei neue Prüfregeln dazu. In einem zweiten Bildschirm hättest du sie vermutlich vergessen.

Der Unterschied zwischen den zwei Fällen sind genau drei Zeilen, in showMode zwei und in onSaveClicked eine. Elf Felder gegen drei Zeilen ist ein klarer Fall.

2. Die zwei Regeln für die optionalen Antworten

Regel eins, die Lücke. Antwort 4 gefüllt und Antwort 3 leer ergibt im Spiel einen leeren Knopf zwischen zwei gefüllten. Erlaubt sind zwei, drei oder vier Antworten, aber immer von oben her ohne Loch.

Regel zwei, der Knopf oben. Der Radiobutton lässt sich auf ein leeres Feld stellen. Dann wäre die richtige Antwort ein leerer Text. Im Spiel gäbe es dann keine richtige Antwort mehr, und der Spieler kann die Frage nicht lösen.

Wenn du in 08B nur eine der zwei hattest, war es fast immer die Lücke. Die zweite fällt schwerer, weil sie zwei Bedienelemente verbindet, die weit auseinander stehen: den Knopf oben und ein Feld weiter unten.

3. Die Rangliste und die gelöschte Frage

Es passiert gar nichts, und das ist ein echtes Problem. Deine Rangliste steht in SharedPreferences und speichert den Kategorienamen als Text. Sie weiss nichts von der Fragen-Tabelle. Löschst du alle Fragen einer Kategorie, bleiben die Ranglisten-Einträge stehen.

Was passieren sollte, hängt davon ab, was du willst. Drei Möglichkeiten, alle vertretbar:

  • Nichts tun. Ein Ranglisteneintrag ist eine Erinnerung an eine gespielte Runde und wird nicht falsch, nur weil die Frage weg ist.
  • Die Einträge mitlöschen. Dann bräuchte es eine Verbindung zwischen den zwei Ablagen, die es heute nicht gibt.
  • Beides in dieselbe Datenbank legen und Room die Verbindung machen lassen. Das ist die saubere Lösung, und genau darum wird in einer echten App selten die Hälfte der Daten in SharedPreferences abgelegt.

In der Leistungsbeurteilung stellt sich dieselbe Frage bei den Noten: sie gehören zum Modul und dürfen nicht ohne es weiterleben.

4. Welche Stellen sich in der GameActivity ändern

Sechs Stellen, und keine davon ist Logik. Ein Import, vier Typen, ein Aufruf. Dazu die neue Zeile für die Sichtbarkeit, die aber nichts mit dem Datenzugriff zu tun hat.

Warum es so wenig ist: deine QuestionEntity hat seit 07C dieselben Methoden nach aussen wie Question, also getText, getAnswers, getCategory und isCorrect. Das war damals eine bewusste Entscheidung, und heute zahlt sie sich aus.

Das ist der Punkt der ganzen Übung. Wer beim Bauen einer neuen Klasse darauf achtet, dass sie von aussen gleich aussieht wie die alte, kann die Datenquelle später austauschen, ohne alles neu zu schreiben. Wäre getAnswers in der Entity anders gebaut, wäre B3 ein halber Nachmittag geworden statt zwölf Minuten.

@Override

QuestionEditActivity.java, die ganze Klasse

Das ist der Endstand nach B2. Vergleich Methode für Methode, nicht Zeile für Zeile.

package ch.wiss.m335.quiz;

import android.os.Bundle;
import android.util.Log;
import android.view.View;
import android.widget.ArrayAdapter;
import android.widget.Button;
import android.widget.RadioGroup;
import android.widget.Spinner;
import android.widget.TextView;

import androidx.activity.EdgeToEdge;
import androidx.appcompat.app.AlertDialog;
import androidx.appcompat.app.AppCompatActivity;
import androidx.core.graphics.Insets;
import androidx.core.view.ViewCompat;
import androidx.core.view.WindowInsetsCompat;

import com.google.android.material.textfield.TextInputEditText;
import com.google.android.material.textfield.TextInputLayout;

import java.util.Arrays;
import java.util.List;

import ch.wiss.m335.quiz.data.QuestionEntity;
import ch.wiss.m335.quiz.data.QuizDatabase;
import ch.wiss.m335.quiz.model.QuestionBank;

/**
 * Das Formular für eine Frage. Es legt neue an und ändert bestehende.
 *
 * Seit 08C hat der Bildschirm zwei Aufgaben. Welche davon gilt, entscheidet
 * ein einziger Wert: die id im Intent. Ist keine da, bleibt questionId auf 0
 * und der Bildschirm legt an. Kommt eine mit, lädt er die Frage und
 * schreibt sie mit update zurück.
 *
 * Genau darum heisst die Klasse seit 08B QuestionEditActivity und nicht
 * QuestionNewActivity. Der Name hat den zweiten Fall schon vorgesehen.
 *
 * Der Unterschied zwischen den zwei Fällen steckt an drei Stellen und
 * sonst nirgends. Im Titel oben, im Löschen-Knopf unten, und in der einen
 * Verzweigung in onSaveClicked. Alles andere ist für beide Fälle gleich.
 *
 * Die Prüflogik ist dieselbe Idee wie beim Namensfeld in 06B. setError
 * gehört auf das TextInputLayout und nicht auf das TextInputEditText.
 */
public class QuestionEditActivity extends AppCompatActivity {

    /**
     * Log-Tag für das ganze Modul 335.
     *
     * Bewusst nicht "M335". Diese Zeichenfolge steckt auch im Paketnamen
     * ch.wiss.m335.quiz. Das Suchfeld im Logcat sucht im Freitext über alle
     * Spalten, und damit träfe "M335" jede Zeile unserer App statt nur die
     * selbst geschriebenen.
     */
    private static final String TAG = "Modul335";

    /**
     * Der Schlüssel für die id im Intent.
     *
     * Die Konstante steht hier und nicht in der AdminActivity. Wer den
     * Bildschirm öffnet, muss den Schlüssel kennen. Wer ihn liest, auch.
     * Steht er an einer Stelle, können die zwei nicht auseinanderlaufen.
     */
    public static final String EXTRA_QUESTION_ID = "question_id";

    /** So viele Zeichen muss ein Fragetext mindestens haben. */
    private static final int MIN_TEXT_LENGTH = 10;

    /**
     * Die drei Schwierigkeitsstufen, genau so wie sie in den Daten stehen.
     *
     * Der Text aus dem Spinner wandert unverändert in die Spalte
     * difficulty. Ein grosses L in "Leicht" würde eine zweite Schreibweise
     * in die Tabelle bringen, und danach passt kein Vergleich mehr.
     */
    private static final List<String> DIFFICULTIES = Arrays.asList("leicht", "mittel", "schwer");

    /**
     * Die id der Frage, die bearbeitet wird. 0 heisst neue Frage.
     *
     * Room vergibt seine ids ab 1, also kann 0 nie eine echte Frage meinen.
     * Damit braucht es kein zweites Feld, das den Zustand merkt.
     */
    private int questionId = 0;

    /** Der Titel oben. Er sagt, welcher der zwei Fälle gerade gilt. */
    private TextView tvEditTitle;

    /** Das Eingabefeld für den Fragetext, mit seinem Rahmen. */
    private TextInputLayout tilQuestionText;

    /** Das Eingabefeld für den Fragetext. */
    private TextInputEditText etQuestionText;

    /** Die vier Rahmen der Antwortfelder, in der Reihenfolge 1 bis 4. */
    private TextInputLayout[] answerLayouts;

    /** Die vier Antwortfelder, in derselben Reihenfolge. */
    private TextInputEditText[] answerFields;

    /** Die Auswahl, welche der vier Antworten die richtige ist. */
    private RadioGroup rgCorrect;

    /** Die Kategorie der Frage. Ohne den Eintrag Alle. */
    private Spinner spnEditCategory;

    /** Die Schwierigkeit der Frage. */
    private Spinner spnEditDifficulty;

    /** Der Knopf, der die Frage löscht. Nur beim Bearbeiten sichtbar. */
    private Button btnDeleteQuestion;

    /**
     * Die Kategorien in der Reihenfolge, in der sie im Spinner stehen.
     *
     * Als Feld, weil loadQuestion die Position eines Textes darin sucht.
     * Ohne die Liste müsste man sie dem Adapter wieder abfragen.
     */
    private List<String> categories;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        EdgeToEdge.enable(this);
        setContentView(R.layout.activity_question_edit);

        // 16dp eigener Rand, in Pixel umgerechnet über die Dichte des Geräts.
        final int extraPadding = Math.round(16 * getResources().getDisplayMetrics().density);

        // Type.ime() ist die Tastatur. Dieser Bildschirm ist nach der
        // GameActivity der zweite mit Eingabefeldern, und hier sind es
        // gleich fünf. Ohne Type.ime() legt sich die Tastatur über das
        // Feld, in das gerade getippt wird.
        ViewCompat.setOnApplyWindowInsetsListener(findViewById(R.id.clQuestionEdit), (v, insets) -> {
            Insets systemBars = insets.getInsets(
                    WindowInsetsCompat.Type.systemBars() | WindowInsetsCompat.Type.ime());
            v.setPadding(
                    systemBars.left + extraPadding,
                    systemBars.top + extraPadding,
                    systemBars.right + extraPadding,
                    systemBars.bottom + extraPadding);
            return insets;
        });

        tvEditTitle = findViewById(R.id.tvEditTitle);
        tilQuestionText = findViewById(R.id.tilQuestionText);
        etQuestionText = findViewById(R.id.etQuestionText);
        rgCorrect = findViewById(R.id.rgCorrect);
        spnEditCategory = findViewById(R.id.spnEditCategory);
        spnEditDifficulty = findViewById(R.id.spnEditDifficulty);
        btnDeleteQuestion = findViewById(R.id.btnDeleteQuestion);

        // Die vier Antwortfelder in ein Array. Danach läuft jede Prüfung
        // in einer Schleife statt vier Mal untereinander. Dasselbe Muster
        // wie bei den vier Antwort-Buttons in der GameActivity.
        answerLayouts = new TextInputLayout[]{
                findViewById(R.id.tilAnswer1),
                findViewById(R.id.tilAnswer2),
                findViewById(R.id.tilAnswer3),
                findViewById(R.id.tilAnswer4)
        };
        answerFields = new TextInputEditText[]{
                findViewById(R.id.etAnswer1),
                findViewById(R.id.etAnswer2),
                findViewById(R.id.etAnswer3),
                findViewById(R.id.etAnswer4)
        };

        categories = realCategories();

        spnEditCategory.setAdapter(new ArrayAdapter<>(this,
                android.R.layout.simple_spinner_dropdown_item, categories));
        spnEditDifficulty.setAdapter(new ArrayAdapter<>(this,
                android.R.layout.simple_spinner_dropdown_item, DIFFICULTIES));

        findViewById(R.id.btnSaveQuestion).setOnClickListener(v -> onSaveClicked());
        findViewById(R.id.btnCancelQuestion).setOnClickListener(v -> finish());
        btnDeleteQuestion.setOnClickListener(v -> onDeleteClicked());

        // Die id kommt aus dem Intent. Ist keine da, liefert getIntExtra den
        // zweiten Wert zurück, also 0. Damit steht der Fall Anlegen ohne
        // eine einzige Abfrage fest.
        questionId = getIntent().getIntExtra(EXTRA_QUESTION_ID, 0);

        // Die Reihenfolge zählt. Die Adapter müssen stehen, bevor
        // loadQuestion eine Position darin auswählt.
        showMode();
        if (questionId > 0) {
            loadQuestion();
        }

        Log.d(TAG, "QuestionEditActivity onCreate, id=" + questionId);
    }

    /**
     * Liefert die Kategorien ohne den Eintrag Alle.
     *
     * Alle ist eine Angabe für eine Spielrunde und keine Eigenschaft einer
     * einzelnen Frage. Wer es hier anbieten würde, bekäme Fragen mit der
     * Kategorie Alle. Die tauchen danach in keiner echten Kategorie auf und
     * sind praktisch verloren.
     *
     * @return die vier echten Kategorien
     */
    private List<String> realCategories() {
        List<String> all = QuestionBank.categories();
        return all.subList(1, all.size());
    }

    /**
     * Holt die Frage aus der Datenbank und schreibt sie in die Felder.
     *
     * Genau die Gegenrichtung von onSaveClicked. Dort wandern die Felder in
     * ein Objekt, hier wandert ein Objekt in die Felder.
     *
     * Findet findById nichts, ist die Frage inzwischen gelöscht worden. Der
     * Bildschirm schliesst sich dann, statt ein leeres Formular zu zeigen,
     * das beim Speichern nichts bewirken würde.
     */
    private void loadQuestion() {
        QuestionEntity question = QuizDatabase.getInstance(this).questionDao().findById(questionId);

        if (question == null) {
            Log.d(TAG, "question not found, id=" + questionId);
            finish();
            return;
        }

        etQuestionText.setText(question.getText());

        String[] answers = question.getAnswers();
        for (int i = 0; i < answerFields.length; i++) {
            answerFields[i].setText(answers[i]);
        }

        // Vom Text zurück zum Knopf. selectedAnswerIndex geht die andere
        // Richtung, vom Knopf zum Text.
        for (int i = 0; i < answers.length; i++) {
            if (answers[i].equals(question.getCorrectAnswer())) {
                rgCorrect.check(radioIdOf(i));
                break;
            }
        }

        // Ein Spinner nimmt keinen Text entgegen, sondern eine Position.
        // Ohne diese zwei Zeilen bliebe er auf dem ersten Eintrag stehen,
        // und das Speichern schriebe die falsche Kategorie zurück.
        selectValue(spnEditCategory, categories, question.getCategory());
        selectValue(spnEditDifficulty, DIFFICULTIES, question.getDifficulty());

        Log.d(TAG, "question loaded, id=" + questionId);
    }

    /**
     * Stellt den Bildschirm auf Anlegen oder auf Bearbeiten.
     *
     * Genau eine Methode schaltet um, so wie showState in der GameActivity
     * und showEmptyState in der AdminActivity. Wären es zwei Stellen,
     * könnte der Titel Bearbeiten sagen, während der Löschen-Knopf fehlt.
     */
    private void showMode() {
        boolean editing = questionId > 0;

        tvEditTitle.setText(editing ? R.string.title_question_edit : R.string.title_question_new);
        btnDeleteQuestion.setVisibility(editing ? View.VISIBLE : View.GONE);
    }

    /**
     * Prüft die Eingaben und schreibt die Frage in die Datenbank.
     *
     * Erst prüfen, dann bauen, dann speichern. Wer in der anderen
     * Reihenfolge arbeitet, hat halbe Objekte im Speicher und muss sie
     * wieder wegwerfen.
     */
    private void onSaveClicked() {
        if (!isFormValid()) {
            Log.d(TAG, "save rejected, form not valid");
            return;
        }

        QuestionEntity question = new QuestionEntity();
        question.setText(textOf(etQuestionText));
        question.setAnswer1(textOf(answerFields[0]));
        question.setAnswer2(textOf(answerFields[1]));
        question.setAnswer3(textOf(answerFields[2]));
        question.setAnswer4(textOf(answerFields[3]));

        // Die richtige Antwort wird als Text gespeichert und nicht als
        // Nummer. So bleibt QuestionEntity von aussen gleich wie frueher
        // die Klasse Question, und isCorrect vergleicht zwei Texte.
        question.setCorrectAnswer(textOf(answerFields[selectedAnswerIndex()]));

        question.setCategory((String) spnEditCategory.getSelectedItem());
        question.setDifficulty((String) spnEditDifficulty.getSelectedItem());

        // Die eine Verzweigung, um die es in 08C geht. Beim Anlegen bleibt
        // die id auf 0 und Room vergibt eine neue. Beim Bearbeiten wird sie
        // gesetzt, denn ohne id findet update keine Zeile und tut nichts.
        if (questionId > 0) {
            question.setId(questionId);
            QuizDatabase.getInstance(this).questionDao().update(question);
            Log.d(TAG, "question updated, id=" + questionId);
        } else {
            long newId = QuizDatabase.getInstance(this).questionDao().insert(question);
            Log.d(TAG, "question inserted, id=" + newId);
        }

        // Zurück zur Liste. finish schliesst nur diesen Bildschirm, die
        // AdminActivity darunter lebt weiter und bekommt onResume.
        finish();
    }

    /**
     * Fragt nach und löscht die Frage.
     *
     * Löschen lässt sich nicht rückgängig machen. Darum die Rückfrage.
     * Sie steht bewusst nicht im Dialog selbst, sondern der Dialog fragt und
     * löscht erst, wenn der Benutzer den zweiten Knopf drückt.
     *
     * setCancelable bleibt auf dem Standard true. Wer neben den Dialog
     * tippt, hat damit abgebrochen, und das ist die harmlose Richtung.
     */
    private void onDeleteClicked() {
        new AlertDialog.Builder(this)
                .setTitle(R.string.dialog_delete_title)
                .setMessage(R.string.dialog_delete_message)
                .setNegativeButton(R.string.dialog_delete_keep, null)
                .setPositiveButton(R.string.dialog_delete_confirm, (dialog, which) -> deleteQuestion())
                .show();
    }

    /**
     * Löscht die Frage wirklich und schliesst den Bildschirm.
     *
     * Room löscht über die id. Die anderen Felder darf das Objekt leer
     * lassen, sie werden nicht angeschaut.
     */
    private void deleteQuestion() {
        QuestionEntity question = new QuestionEntity();
        question.setId(questionId);

        QuizDatabase.getInstance(this).questionDao().delete(question);
        Log.d(TAG, "question deleted, id=" + questionId);

        finish();
    }

    /**
     * Prüft alle Felder und zeigt die Fehler dort an, wo sie entstehen.
     *
     * Wichtig ist die Bauart: die Methode setzt valid auf false und prüft
     * weiter. Sie steigt nicht mit return aus. Wer nach dem ersten Fehler
     * aussteigt, zwingt den Benutzer, mehrmals auf Speichern zu tippen, um
     * mehrere Fehler zu sehen.
     *
     * Und jede Regel räumt ihre eigene Meldung wieder weg. Ohne das else
     * mit setError(null) bleibt eine rote Meldung stehen, obwohl das Feld
     * inzwischen stimmt.
     *
     * Seit 08C sind Antwort 3 und 4 optional, und darum hängen zwei neue
     * Regeln daran. Sie liessen sich anhängen, ohne die alten anzufassen.
     * Genau dafür war der Umbau aus 08B da.
     *
     * Eine Sache ist neu: auf Antwort 3 und 4 zeigen zwei Regeln. Das else
     * der einen würde die Meldung der anderen löschen. Darum werden diese
     * zwei Felder einmal geräumt und danach nur noch gesetzt.
     *
     * @return true, wenn alle Eingaben brauchbar sind
     */
    private boolean isFormValid() {
        boolean valid = true;

        if (textOf(etQuestionText).length() < MIN_TEXT_LENGTH) {
            tilQuestionText.setError(getString(R.string.error_question_text));
            valid = false;
        } else {
            tilQuestionText.setError(null);
        }

        // Antwort 1 und 2 sind weiterhin Pflicht. Eine Frage mit nur einer
        // Antwort ist keine Frage.
        for (int i = 0; i < 2; i++) {
            if (textOf(answerFields[i]).isEmpty()) {
                answerLayouts[i].setError(getString(R.string.error_answer_required));
                valid = false;

Und warum kein Enum?

Das ist die naheliegende Frage, und sie ist gut. Fünf feste Texte, die sich nie ändern, sind der Lehrbuchfall für ein Enum. Du hast sogar schon eines im Projekt, seit 05C:

private enum GameState { CHOOSE_CATEGORY, QUESTION, RESULT }

Der Unterschied zwischen den beiden ist die Lektion.

Deine Kategorie verlässt das Programm ständig. Sie steht als Text in der Spalte category, sie steht in jedem Ranglisten-Eintrag, und sie steht in questions_m335.json. An achtzehn Stellen in deinem Code wird sie als String weitergereicht.

Mit einem Enum bräuchte jede dieser Grenzen eine Umwandlung. Und die Rückrichtung ist die gefährliche: valueOf("Sport") wirft eine IllegalArgumentException, sobald ein Wert kommt, den das Enum nicht kennt.

Was das praktisch heisst: ein Tippfehler in questions_m335.json würde deine App beim Start zum Absturz bringen. Heute bekommst du stattdessen eine Frage mit einer komischen Kategorie, und die App läuft weiter.

Bei Daten von aussen ist das fast immer die bessere Wahl. Ein Datenfehler soll ein Datenfehler bleiben und nicht zum Absturz werden.

Dazu kommt Alle. Im Enum wäre es ein Wert, der nie in der Datenbank stehen darf. Genau der Fremdkörper, den dein realCategories() heute wegschneidet. Eine Ausnahme mitten im Typ ist schlechter als eine Ausnahme in einer Methode.

Machbar wäre es trotzdem, und in einer App, die du jahrelang pflegst, wäre es vertretbar. Man gibt dem Enum ein Feld mit dem Anzeigetext, und Room bekommt einen @TypeConverter, der zwischen Enum und Text übersetzt. Beim Lesen fängt man den unbekannten Wert ab.

Das ist mehr Code als das, was du heute hast, und es löst kein Problem, das du hast. Und die Leistungsbeurteilung arbeitet ohnehin mit freien Texten: Modulnummer und Modultitel.

Der Merksatz zum Mitnehmen: ein Enum ist richtig, solange der Wert im Programm bleibt. Sobald er in eine Datei, eine Datenbank oder über das Netz geht, wird aus dem Typ eine Übersetzungsaufgabe. Dann muss sich der Aufwand lohnen.
