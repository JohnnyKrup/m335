03D Lösung, Die Datenklasse Question

Lösungsmaterial zum Auftrag 03D. Modul 335, Tag 2 Vormittag. Fassung 3 vom 14.08.2026.

Zum Durchlesen brauchst du etwa 15 Minuten. Das ist ein Richtwert. Such dir die Stelle, die du brauchst.

Antworten zu den Denkfragen

Diese vier Fragen kommen im 03CD Wissenscheck als Quizfragen wieder. Der deckt 03C und 03D zusammen ab.

Frage 1, was unterscheidet den Fragetext von der Beschriftung eines Knopfs?

Wer ihn ändert. Das ist das ganze Kriterium.

BeschriftungDaten
BeispielWeiter, Abbrechen, PunkteDer Fragetext, die vier Antworten
Wer ändert sieder Entwickler, beim Übersetzender Benutzer, oder ein Server
Wohinstrings.xmlins Objekt, später in die Datenbank

Die Faustregel: was der Benutzer ändern könnte, sind Daten. Was der Entwickler übersetzt, ist Beschriftung.

Warum das zählt: Am Tag 4 legt der Benutzer selbst neue Fragen an. Stünden sie in strings.xml, ginge das gar nicht, denn Ressourcen sind zur Laufzeit unveränderlich. Sie werden beim Bauen fest in die App gepackt.

Frage 2, wo gehört die Prüfung hin?

In die Klasse Question. Eine Frage weiss selbst, was auf sie die richtige Antwort ist.

Die Activity muss das nicht wissen. Sie fragt nach: currentQuestion.isCorrect(givenAnswer).

Der Test, ob du es richtig herum hast: Stell dir vor, du zeigst dieselbe Frage auf einem zweiten Bildschirm an. Steht die Prüfung in der Activity, musst du sie kopieren. Steht sie in der Frage, kommt sie mit.

Warum das zählt: Genau das passiert am Tag 3, wenn der Spielbildschirm in eine eigene Activity umzieht. Question zieht einfach mit, ohne dass du etwas anfassen musst.

Frage 3, vier Felder oder ein Array?

Ein Array. Zwei Gründe.

  • Du kannst darüber laufen. Vier Felder answer1 bis answer4 zwingen dich zu vier Zeilen Code, jedes Mal wenn du sie brauchst. Ein Array erlaubt eine Schleife.
  • Die Anzahl ist nicht in Stein gemeisselt. Am Tag 4 gibt es Fragen mit nur zwei oder drei Antworten. Mit einem Array ist das eine Längenprüfung, mit vier Feldern ein Umbau.

Die Gegenrede, die es auch gibt: vier Felder sind selbstdokumentierend, ein Array nicht. Bei einer Datenbank wird das später wieder ein Thema, dort stehen wirklich vier Spalten. Beide Wege sind vertretbar, aber im Java-Code gewinnt das Array.

Frage 4, woran misst du den Nutzen, wenn nichts anders aussieht?

An der Anzahl Stellen, die eine Änderung kostet.

Eine andere Frage einbauenStellen
Vor dem Umbau, mit strings.xml6
Nach dem Umbau, mit dem Objekt1

Sechs, weil fünf Einträge in strings.xml geändert werden müssen und dazu die Zeile mit der richtigen Antwort im Code.

Warum das zählt: Das ist das Mass, mit dem Entwickler Lösungen vergleichen. Nicht "sieht es schöner aus", sondern "was kostet die nächste Änderung". Genau danach wird in der Leistungsbeurteilung gefragt, wenn du deine Lösung begründen musst.

Die zwei Beobachtungsstellen

B2, wie weit ein Text streut

Was du siehst: Du löschst sechs Einträge in strings.xml, und es werden sieben Stellen rot. Sechs im Layout und eine im Java-Code.

WoWas
activity_main.xmlsechs android:text-Zeilen: tvCategory, tvQuestion, vier Buttons
MainActivity.javadie Zeile correctAnswer = getString(R.string.q1_answer3);

Was die Beobachtung zeigt: Ein Text, den du an einer Stelle definierst, wird an sieben Stellen benutzt. Solange er stimmt, merkst du das nie. Sobald er sich ändert, sind es sieben Stellen, an denen etwas schiefgehen kann.

Nach dem Umbau ist es umgekehrt: die Texte stehen an einer Stelle und werden von einer Methode verteilt.

Die häufigste Fehlbeobachtung ist "nur das Layout wird rot". Die Java-Zeile übersieht man leicht, weil sie ganz woanders steht.

C1, was eine Änderung kostet

Was du siehst: Eine andere Frage einzubauen kostet genau eine Stelle, nämlich den new Question(…)-Aufruf. Layout unberührt, strings.xml unberührt, alle fünf Methoden unberührt.

Vor dem Umbau wären es sechs gewesen.

Das ist der ganze Sinn dieses Auftrags. Deine App sieht nach 45 Minuten Arbeit genau gleich aus wie vorher. Was sich geändert hat, siehst du nicht auf dem Bildschirm, sondern erst bei der nächsten Änderung.

Merk dir diesen Satz: eine gute Struktur erkennt man nicht am Ergebnis, sondern an den Kosten der nächsten Änderung.

Die fertige Question

Datei app/src/main/java/ch/wiss/m335/quiz/model/Question.java.

package ch.wiss.m335.quiz.model;

/**
 * Eine einzelne Quizfrage.
 *
 * Diese Klasse hat bewusst dieselben Felder wie der Fragen-Export des
 * WISS-Quiz aus Modul 295. Dadurch kann die App später Fragen direkt
 * vom Server übernehmen, ohne dass etwas umbenannt werden muss.
 *
 * Noch ohne Datenbank. Die Fragen stehen fest im Code.
 */
public class Question {

    /** Der Fragetext, zum Beispiel "Was ist die Hauptstadt der Schweiz?". */
    private String text;

    /** Die vier möglichen Antworten in der Reihenfolge der Buttons. */
    private String[] answers;

    /** Die richtige Antwort als Text. Muss in answers enthalten sein. */
    private String correctAnswer;

    /** Kategorie: Sport, Technologie, Geographie oder Geschichte. */
    private String category;

    /** Schwierigkeit: "leicht", "mittel" oder "schwer". */
    private String difficulty;

    /**
     * Erzeugt eine neue Frage.
     *
     * @param text          der Fragetext
     * @param answers       genau vier Antworten
     * @param correctAnswer die richtige Antwort, muss in answers vorkommen
     * @param category      die Kategorie
     * @param difficulty    die Schwierigkeit
     */
    public Question(String text, String[] answers, String correctAnswer,
                    String category, String difficulty) {
        this.text = text;
        this.answers = answers;
        this.correctAnswer = correctAnswer;
        this.category = category;
        this.difficulty = difficulty;
    }

    /**
     * Prüft, ob eine angetippte Antwort richtig ist.
     *
     * Wir vergleichen den Text und nicht die Position. Dadurch bleibt die
     * Prüfung auch dann korrekt, wenn die Antworten gemischt angezeigt werden.
     *
     * @param givenAnswer die Antwort, die der Spieler angetippt hat
     * @return true, wenn die Antwort richtig ist
     */
    public boolean isCorrect(String givenAnswer) {
        return correctAnswer.equals(givenAnswer);
    }

    /** @return der Fragetext */
    public String getText() {
        return text;
    }

    /** @return die vier Antworten */
    public String[] getAnswers() {
        return answers;
    }

    /** @return die richtige Antwort als Text */
    public String getCorrectAnswer() {
        return correctAnswer;
    }

    /** @return die Kategorie */
    public String getCategory() {
        return category;
    }

    /** @return die Schwierigkeit */
    public String getDifficulty() {
        return difficulty;
    }
}

Zu getCorrectAnswer. Deine Activity braucht diesen Getter nirgends, weil sie isCorrect benutzt. Er steht trotzdem drin, denn am Tag 4 zeigt der Ergebnisbildschirm die richtige Antwort an. Ein Getter auf ein Feld, das es sowieso gibt, kostet nichts.

Aufpassen musst du beim Gegenteil: wenn deine Activity getCorrectAnswer() holt und den Vergleich selbst macht, hast du das Verhalten wieder aus der Datenklasse herausgezogen. Dann könntest du isCorrect auch weglassen.

Lösungen zu den Übungen

Übung 1, die Schwierigkeit anzeigen

Der einfachste Weg hängt sie an die Kategorie an:

tvCategory.setText(currentQuestion.getCategory() + " (" + currentQuestion.getDifficulty() + ")");

Sauberer wäre eine eigene TextView im Layout und ein Format in strings.xml, etwa <string name="category_format">%1$s, %2$s</string>. Dann steht die Schreibweise mit Klammern nicht im Java-Code.

Der Punkt der Übung: Du musstest an Question nichts ändern. Das Feld war schon da, obwohl es niemand brauchte. Genau darum steht es drin.

Übung 2, eine Frage prüfen

/**
 * Prüft, ob diese Frage vollständig ist.
 *
 * @return true, wenn genau vier Antworten da sind und die richtige
 *         Antwort unter ihnen vorkommt
 */
public boolean isValid() {
    if (answers == null || answers.length != 4) {
        return false;
    }
    for (String answer : answers) {
        if (correctAnswer.equals(answer)) {
            return true;
        }
    }
    return false;
}

Beachte zwei Dinge. Erstens steht die Prüfung in der Klasse, aus demselben Grund wie isCorrect. Zweitens prüft sie zuerst auf null, sonst stürzt die Längenabfrage ab, bevor sie false zurückgeben kann.

Warum das später wichtig wird: Am Tag 4 tippt der Benutzer selbst Fragen ein. Dann brauchst du genau so eine Prüfung, bevor gespeichert wird.

Übung 3, erklären

Eine gute Erklärung nennt den Grundsatz und einen Beleg.

"Eine Frage weiss selbst, was auf sie die richtige Antwort ist. Die Activity muss das nicht wissen, sie fragt nach. Wenn ich dieselbe Frage auf einem zweiten Bildschirm zeige, kommt die Prüfung mit. Stünde sie in der Activity, müsste ich sie kopieren."

Als zweite Methode, die aus demselben Grund hineingehört: eine Prüfung auf Vollständigkeit wie in Übung 2, oder eine Methode, die die Antworten gemischt zurückgibt.

Zur Zusatzaufgabe steht hier bewusst nichts. Die Frage danach ist der eigentliche Inhalt: warum funktioniert die Auswertung nach dem Mischen weiter, ohne dass du isCorrect anfasst?

Das sind Antworten, die uns bei diesem Thema schon begegnet sind. Nicht jede KI macht jeden dieser Fehler. Die Liste ist eine Prüfliste, keine Anklage.

So prüfst du das Ganze

  1. Die App startet und sieht aus wie nach 03C.
  2. Oben links steht die Kategorie, oben rechts Punkte 0, darunter Frage und vier Antworten.
  3. Richtig antworten färbt grün und zählt einen Punkt.
  4. Falsch antworten färbt rot und gleichzeitig grün.
  5. Nach dem ersten Klick reagiert kein Button mehr.
  6. strings.xml hat zwei Einträge.
  7. Du tauschst die Frage aus und musst nur eine Stelle anfassen.

Punkt 7 ist der eigentliche Test. Alles davor lief schon gestern. Was heute dazugekommen ist, siehst du erst, wenn du etwas änderst.

Was im nächsten Auftrag dazukommt

Eine Frage ist jetzt ein Objekt. Der nächste Schritt liegt auf der Hand: mehrere Objekte in einer Liste, ein Weiter-Knopf, und eine Runde über fünf Fragen.

Ab dann zählt der Punktestand wirklich, und die Sperre der Buttons muss vor jeder neuen Frage wieder aufgehoben werden. Deine Übung 2 aus 03C war der Vorlauf dazu.
