Antworten zu den Denkfragen

1. Warum stecken zwei Elemente ineinander, ein Rahmen und ein Feld?

Weil sie zwei verschiedene Aufgaben haben. Das TextInputEditText nimmt Text entgegen, mehr nicht. Das TextInputLayout darum herum kümmert sich um alles, was man über dem Text sieht: den Hinweistext, der beim Tippen nach oben wandert und klein wird, den Rahmen, die Fehlermeldung darunter, und den Platz dafür.

Gäbe es nur ein Element, müsste es beides können. Genau das war die alte Lösung, und die sieht man noch: EditText.setError zeigt eine kleine Sprechblase, weil ein EditText keinen Platz unter sich hat, in den es schreiben könnte.

Das Muster heisst Container und Child und begegnet dir in Material Design an mehreren Stellen. Merksatz: der Container übernimmt die Darstellung, das Child die Funktion.

2. HighscoreEntry hat drei final-Felder, Question hat Setter. Woran liegt das?

Daran, was mit den Daten geschieht, nachdem sie entstanden sind.

Und der Grund, warum das mehr ist als Geschmack: final macht aus einer Absicht eine Zusage, die der Compiler durchsetzt. Wer versucht, einen Eintrag nachträglich zu ändern, bekommt einen Fehler statt eines stillen Bugs.

Das ist dieselbe Entscheidung wie in 06A A4, nur von der anderen Seite. Dort hast du entschieden, dass der Eintrag keine id braucht, weil man ihn nie einzeln ändert. Hier setzt der Code diese Entscheidung durch.

3. Was müsstest du tun, um genau einen Eintrag zu löschen?

Die ganze Liste lesen, in Objekte verwandeln, den einen herausnehmen, alles zurück in Text verwandeln, alles zurückschreiben.

Und du müsstest zuerst eine Frage beantworten, die du gar nicht beantworten kannst: welcher ist der eine? Es gibt kein Feld, das einen Eintrag eindeutig macht. Zwei Spieler können Sara heissen und beide 4 Punkte in Sport haben.

Das ist genau die Frage aus dem Ausblick von 05D, und heute hast du den Code dazu vor dir. Schau in add: dort steht wörtlich getAll, dann entries.add, dann saveAll. Die ganze Liste, für einen einzelnen Eintrag.

Beim Anhängen ist das harmlos. Beim Löschen bräuchtest du zusätzlich einen Schlüssel. Ab Tag 4 hat die Datenbank beides, und dao.delete(entity) ist eine Zeile.

package ch.wiss.m335.quiz.data;

import android.content.Context;
import android.content.SharedPreferences;
import android.util.Log;

import org.json.JSONArray;
import org.json.JSONException;
import org.json.JSONObject;

import java.util.ArrayList;
import java.util.List;

import ch.wiss.m335.quiz.model.HighscoreEntry;

/**
 * Speichert die Rangliste in SharedPreferences.
 *
 * SharedPreferences kennen nur einfache Werte. Eine Liste passt dort nicht
 * hinein. Also verwandeln wir sie in einen JSON-Text und wieder zurück.
 *
 * Dieser Umweg ist mit Absicht sichtbar. Zähl die Zeilen: rund vierzig, um
 * eine Liste mit drei Feldern abzulegen und zu holen. Jedes Feld steht
 * viermal da, in der Klasse, beim Schreiben, beim Lesen und als Schlüssel.
 * Ein neues Feld heisst vier Änderungen an vier Orten.
 *
 * Und jetzt die Frage, die alles entscheidet: was tust du, wenn du nur den
 * Eintrag von Sara ändern willst? Antwort: die ganze Liste lesen, im
 * Speicher ändern, die ganze Liste zurückschreiben.
 *
 * Genau darum bekommen die Fragen am Tag 4 eine Datenbank und die
 * Rangliste nicht. Die Regel: ganze kleine Liste am Stück gleich
 * SharedPreferences, einzeln bearbeitbare Datensätze gleich Datenbank.
 */
public final class HighscoreStorage {

    private static final String TAG = "Modul335";

    /** Dieselbe Ablage wie beim besten Wert. */
    private static final String PREFS_NAME = "m335_quiz";

    /** Der Schlüssel, unter dem der ganze JSON-Text liegt. */
    private static final String KEY_HIGHSCORES = "highscores";

    // Die Namen der Felder im JSON. Beim Schreiben und beim Lesen
    // dieselben, darum als Konstante.
    private static final String FIELD_NAME = "name";
    private static final String FIELD_SCORE = "score";
    private static final String FIELD_CATEGORY = "category";

    /** Diese Klasse wird nie erzeugt, sie hat nur statische Methoden. */
    private HighscoreStorage() {
    }

    private static SharedPreferences prefs(Context context) {
        return context.getSharedPreferences(PREFS_NAME, Context.MODE_PRIVATE);
    }

    /**
     * Liest die ganze Rangliste.
     *
     * @param context irgendein Context
     * @return alle Einträge in der Reihenfolge des Speicherns, nie null
     */
    public static List<HighscoreEntry> getAll(Context context) {
        List<HighscoreEntry> entries = new ArrayList<>();
        String text = prefs(context).getString(KEY_HIGHSCORES, "[]");

        try {
            JSONArray array = new JSONArray(text);
            for (int i = 0; i < array.length(); i++) {
                JSONObject object = array.getJSONObject(i);
                entries.add(new HighscoreEntry(
                        object.getString(FIELD_NAME),
                        object.getInt(FIELD_SCORE),
                        object.getString(FIELD_CATEGORY)));
            }
        } catch (JSONException e) {
            // Kaputter Text, zum Beispiel nach einem misslungenen Umbau.
            // Lieber eine leere Liste als ein Absturz beim Start.
            Log.e(TAG, "highscores unreadable, starting empty", e);
        }

        return entries;
    }

    /**
     * Hängt einen Eintrag an die Rangliste an.
     *
     * Beachte, was hier passiert: es wird die ganze Liste gelesen, ein
     * Eintrag ergänzt und die ganze Liste zurückgeschrieben. Einen
     * einzelnen Eintrag anzufügen geht mit SharedPreferences nicht.
     *
     * @param context irgendein Context
     * @param entry   der neue Eintrag
     */
    public static void add(Context context, HighscoreEntry entry) {
        List<HighscoreEntry> entries = getAll(context);
        entries.add(entry);
        saveAll(context, entries);
        Log.d(TAG, "highscore added, total=" + entries.size());
    }

    /**
     * Schreibt die ganze Rangliste zurück.
     *
     * @param context irgendein Context
     * @param entries die vollständige Liste
     */
    private static void saveAll(Context context, List<HighscoreEntry> entries) {
        JSONArray array = new JSONArray();

        try {
            for (HighscoreEntry entry : entries) {
                JSONObject object = new JSONObject();
                object.put(FIELD_NAME, entry.getName());
                object.put(FIELD_SCORE, entry.getScore());
                object.put(FIELD_CATEGORY, entry.getCategory());
                array.put(object);
            }
        } catch (JSONException e) {
            Log.e(TAG, "highscores not writable", e);
            return;
        }

        prefs(context).edit().putString(KEY_HIGHSCORES, array.toString()).apply();
    }
}

Stell die zwei Schleifen nebeneinander. In getAll steht object.getString(FIELD_NAME), in saveAll steht object.put(FIELD_NAME, ...). Dieselbe Konstante, entgegengesetzte Richtung.

Wenn du das siehst, hast du das Muster. Es ist überall dasselbe, egal ob JSON, XML oder eine Datei: lesen und schreiben sind Spiegelbilder, und beide müssen dieselben Namen benutzen.

Was add wirklich tut

Vier Zeilen, und drei davon sind der ganze Punkt dieses Auftrags.

entries = getAll(context);      // ALLE lesen
entries.add(entry);             // einen ändern
saveAll(context, entries);      // ALLE zurückschreiben

Es gibt keinen anderen Weg. SharedPreferences kennen einen Schlüssel und einen Wert. Der Wert ist hier der ganze Text mit der ganzen Liste darin. Man kann nicht einen Teil davon anfassen.

Bei drei Einträgen ist das egal. Bei dreitausend nicht. Und beim Ändern oder Löschen eines einzelnen Eintrags käme dazu, dass du gar nicht sagen kannst, welcher gemeint ist. Es gibt kein eindeutiges Feld.

Genau das hast du in 06A auf Papier entschieden. Dort stand: eine kurze Liste, die immer als Ganzes gelesen und geschrieben wird, passt in SharedPreferences. Heute hast du gesehen, was "als Ganzes" im Code bedeutet.

B3, die Tastatur und der Insets-Block

Das ist die Stelle, an der zwei Dinge zusammenkommen, die seit dem ersten Tag im Projekt stehen und sich bis heute nie in die Quere kamen.

// AndroidManifest.xml, bei der GameActivity, seit 01B
android:windowSoftInputMode="adjustResize"

// GameActivity.onCreate, aus der Projektvorlage, bis heute nie angefasst
EdgeToEdge.enable(this);
ViewCompat.setOnApplyWindowInsetsListener(findViewById(R.id.clGame), (v, insets) -> {
    Insets systemBars = insets.getInsets(WindowInsetsCompat.Type.systemBars());
    v.setPadding(systemBars.left, systemBars.top, systemBars.right, systemBars.bottom);
    return insets;
});

adjustResize sagt dem System: mach das Fenster kleiner, wenn die Tastatur kommt. Solange die App den Platz vom System zugeteilt bekommt, genügt das.

Mit EdgeToEdge.enable gilt das nicht mehr. Die App zeichnet ab da bis an den Bildschirmrand, unter die Statusleiste und unter die Navigationsleiste. Wer das tut, bekommt keinen Platz mehr geschenkt, sondern muss ihn selbst freilassen. Der Insets-Block ist genau diese Stelle. Er fragt, wie viel Rand gebraucht wird, und setzt so viel Innenabstand.

Gefragt wird bisher nur nach systemBars(). Das sind Statusleiste und Navigationsleiste. Die Tastatur ist ein eigener Typ und kommt in der Frage nicht vor. Also lässt die App keinen Platz für sie frei, und die Tastatur legt sich über den Inhalt.

Die Reparatur ist eine Zeile:

Insets systemBars = insets.getInsets(
        WindowInsetsCompat.Type.systemBars() | WindowInsetsCompat.Type.ime());

Der senkrechte Strich verbindet zwei Typen zu einer Frage. Gelesen wird er hier als und: gib mir den Rand für die Systemleisten und für die Tastatur.

Der Merksatz: wer selbst bis an den Rand zeichnet, muss sich auch selbst um die Ränder kümmern.

adjustResize bleibt trotzdem stehen. Es ist die Ansage, was passieren soll. Der Insets-Block ist die Stelle, an der es passiert. Fehlt die Ansage, hilft auch der Block nichts.

Auf dem Emulator ist dieser Unterschied kaum zu sehen. Der Emulator meldet bei der Tastatur oft gar keine Insets, weil er im Hintergrund eine Hardware-Tastatur mitführt. Der Code ist dann richtig und die Wirkung bleibt aus.

Auf einem echten Gerät ist der Unterschied sofort sichtbar. Wenn es im Emulator nicht wirkt, ist das kein Grund, die Zeile wieder herauszunehmen.

Der Grund ist unangenehm einfach: onSaveScoreClicked ist eine private Methode wie jede andere. Sie heisst nur so, als würde sie von selbst laufen. Ein Knopf ohne Listener ist ein Bild von einem Knopf.

Die Prüffrage für jede neue Methode, die auf einen Klick reagieren soll: ruft sie überhaupt jemand auf? Greppe ihren Namen. Kommt er nur bei der eigenen Deklaration vor, ist sie tot.

Die vier Methoden

/**
 * Trägt das Ergebnis der Runde in die Rangliste ein.
 *
 * Zwei Wächter am Anfang. Der erste verhindert den zweiten Eintrag, der
 * zweite bricht ab, wenn der Name nicht taugt.
 */
private void onSaveScoreClicked() {
    if (scoreSaved) {
        return;
    }
    if (!isNameValid()) {
        return;
    }

    String name = currentName();
    HighscoreStorage.add(this, new HighscoreEntry(name, score, selectedCategory));

    scoreSaved = true;
    updateSaveArea();

    Log.d(TAG, "highscore saved for " + name);
}

/**
 * Prüft das Namensfeld und zeigt bei einem Fehler die Meldung an.
 *
 * setError gehört auf das TextInputLayout, nicht auf das EditText darin.
 * Nur so erscheint die Meldung unter dem Feld.
 *
 * @return true, wenn der Name brauchbar ist
 */
private boolean isNameValid() {
    String name = currentName();

    if (name.isEmpty()) {
        tilPlayerName.setError(getString(R.string.error_name_required));
        return false;
    }
    if (name.length() < MIN_NAME_LENGTH) {
        tilPlayerName.setError(getString(R.string.error_name_too_short));
        return false;
    }

    // Ohne diese Zeile bleibt die alte Fehlermeldung stehen, auch wenn
    // die Eingabe inzwischen stimmt.
    tilPlayerName.setError(null);
    return true;
}

/**
 * Liest den Namen aus dem Feld.
 *
 * getText kann null liefern, darum die Prüfung. Und trim entfernt
 * Leerzeichen am Rand. Drei Leerschläge sind kein Name, sehen aber für
 * length genau so aus wie drei Buchstaben.
 *
 * @return der eingegebene Name ohne Leerzeichen am Rand
 */
private String currentName() {
    return etPlayerName.getText() == null ? "" : etPlayerName.getText().toString().trim();
}

/**
 * Schaltet den Speicherbereich je nachdem, ob schon eingetragen wurde.
 *
 * Genau eine Methode entscheidet darüber, wie beim showState. Wer die
 * Sperre an drei Stellen einzeln setzt, vergisst eine davon.
 */
private void updateSaveArea() {
    btnSaveScore.setEnabled(!scoreSaved);
    etPlayerName.setEnabled(!scoreSaved);
    tvSaved.setVisibility(scoreSaved ? View.VISIBLE : View.GONE);
    if (scoreSaved) {
        tilPlayerName.setError(null);
    }
}

Die Stelle aus C4, aufgelöst

Was passiert ist: drei Leerzeichen kommen durch die Prüfung. In der Rangliste steht ein Eintrag mit einem Namen aus Leerzeichen, also faktisch ohne Namen.

Warum: für length() ist ein Leerzeichen ein Zeichen wie jedes andere. " ".length() ist 3, und 3 ist nicht kleiner als MIN_NAME_LENGTH. Die Prüfung hat genau das getan, was dasteht.

Die Reparatur, eine Zeile:

// vorher
return etPlayerName.getText() == null ? "" : etPlayerName.getText().toString();
// nachher
return etPlayerName.getText() == null ? "" : etPlayerName.getText().toString().trim();

Warum die Reparatur in currentName gehört und nicht in isNameValid. Beide Stellen brauchen den Namen: die Prüfung und das Speichern. Steht das trim in der Prüfung, wird geprüft was getrimmt ist und gespeichert was nicht getrimmt ist.

Das Ergebnis wäre ein Eintrag " Sara " in der Rangliste, der beim Sortieren und beim Suchen anders behandelt wird als "Sara". Und niemand sieht es an, denn Leerzeichen sind unsichtbar.

Die Regel: eine Eingabe wird an genau einer Stelle in ihre gültige Form gebracht, und alle benutzen diese Stelle.

Merke fürs ganze Berufsleben: jede Texteingabe eines Benutzers wird getrimmt. Ausnahmslos. In der Leistungsbeurteilung gilt das für Modulnummer und Modultitel genauso.

Lösungen zu den Übungen

Übung 1, eine dritte Prüfung

Ein neuer String:

<string name="error_name_only_digits">Ein Name besteht nicht nur aus Ziffern.</string>

Und ein dritter Block in isNameValid, vor dem setError(null):

if (name.matches("\\d+")) {
    tilPlayerName.setError(getString(R.string.error_name_only_digits));
    return false;
}

Ohne regulären Ausdruck geht es genauso:

boolean onlyDigits = true;
for (int i = 0; i < name.length(); i++) {
    if (!Character.isDigit(name.charAt(i))) {
        onlyDigits = false;
        break;
    }
}

Die Reihenfolge der drei Prüfungen ist nicht beliebig. Erst leer, dann zu kurz, dann nur Ziffern. Wer mit der Ziffernprüfung anfängt, meldet bei einem leeren Feld eine Meldung, die nicht passt.

Regel: von der gröbsten Bedingung zur feinsten. Dieselbe Reihenfolge brauchst du in der Prüfung bei Nummer und Titel.

Und die Grenze, die du kennen musst: für Personennamen gibt es keinen gültigen regulären Ausdruck. Umlaute, Apostrophe, Bindestriche, chinesische Zeichen, alles kommt vor. Man prüft die Länge und schliesst offensichtlichen Unsinn aus, mehr nicht.

Wer versucht, "richtige" Namen zu erzwingen, sperrt echte Menschen aus.

Übung 2, erklären

Eine gute Erklärung nennt beide Orte.

"setError auf dem TextInputLayout schreibt die Meldung als rote Zeile unter das Feld, wo sie stehen bleibt, bis der Code sie wegräumt. Auf dem TextInputEditText gibt es eine kleine Sprechblase neben dem Feld, die beim ersten Antippen verschwindet."

Und der Satz, der es rund macht: "Der Rahmen ist das Element, das Platz unter dem Feld hat. Das Feld selbst hat keinen, darum muss es sich mit einem schwebenden Fenster behelfen."

Wer nur sagt "das eine ist neuer", hat die Beobachtung. Wer sagt, wo die Meldung jeweils steht und wie lange, hat die Regel.

Zur Zusatzaufgabe steht hier bewusst nichts. Zwei Hinweise trotzdem, weil die Diskussion mehr wert ist als der Code: wer den Knopf sperrt, braucht einen TextWatcher oder doOnTextChanged. Und das beste Gegenargument gegen die Sperre lautet: ein gesperrter Knopf sagt nicht, warum er gesperrt ist.

So prüfst du das Ganze

  1. Vorbereitung: Clear storage im Emulator unter Settings, Apps, WissQuiz, Storage. Nicht Wipe Data.
  2. Spiel eine Runde zu Ende. Im Ergebnisbereich steht ein Feld Dein Name.
  3. Tipp ins Feld. Der Hinweistext wandert nach oben, die Tastatur zeigt unten rechts einen Haken, der erste Buchstabe wird gross.
  4. Bei offener Tastatur muss der Speichern-Knopf erreichbar bleiben, notfalls durch Wischen. Er darf nicht unter der Tastatur verschwinden.
  5. Ohne Eingabe auf den Knopf. Unter dem Feld erscheint Bitte gib deinen Namen ein. Nichts springt.
    Kommt hier gar keine Meldung, fehlt der Listener am Knopf. Das ist nicht dasselbe wie Schritt 9.
  6. Jo eintippen, nochmals drücken. Jetzt steht dort Mindestens drei Zeichen.
  7. Drei Leerzeichen eintippen und drücken. Es muss immer noch eine Fehlermeldung kommen.
  8. Sara eintippen und drücken. Die Meldung verschwindet, die Bestätigung erscheint, Feld und Knopf sind gesperrt.
  9. Nochmals auf den Knopf. Es passiert nichts.
  10. Zweite Runde spielen und mit dem Haken auf der Tastatur eintragen, ohne den Knopf zu berühren. Dasselbe muss passieren, und das Feld war zu Beginn leer.
  11. Im Querformat ins Feld tippen. Der Bereich lässt sich wischen, Feld und Knopf bleiben über der Tastatur erreichbar.
  12. Logcat unter tag:Modul335: highscore saved for Sara und highscore added, total=2.
  13. Die Datei: & $adb shell run-as ch.wiss.m335.quiz cat shared_prefs/m335_quiz.xml. Dort steht neben bestScore jetzt ein string namens highscores.

Wenn im Emulator beim Antippen keine Tastatur erscheint, sondern nur eine kleine schwebende Leiste am Bildschirmrand: öffne deren Menü und wähle Show on-screen keyboard. Der Emulator benutzt sonst die Tastatur deines Computers. Das ist eine Emulator-Eigenheit und kein Fehler in deiner App.

Auf einem echten Gerät im Dunkelmodus ist alles dunkel. Weisse Schrift auf dunklem Grund, das Namensfeld mit hellem Rahmen. Auch das ist kein Fehler. Das Projekt benutzt seit dem ersten Tag Theme.Material3.DayNight, und DayNight heisst genau das: das Thema folgt der Systemeinstellung.

Du hast dafür nichts getan. Das ist der Punkt. Wer eigene Farben fest verdrahtet statt die Farben des Themas zu benutzen, verliert diese Eigenschaft wieder.

Punkt 6 ist die Stelle aus C4. Wer sie überspringt, merkt den Unterschied zwischen "geprüft" und "richtig geprüft" nicht.

Punkt 12 lohnt sich im Unterricht. Zwei Einträge stehen jetzt in derselben Datei nebeneinander, ein schlichter int und ein langer JSON-Text. Der Unterschied zwischen einem Wert und einer Liste zu Fuss ist damit sichtbar.

Was noch nicht funktioniert, und das ist kein Fehler von dir. Dreh das Gerät mitten in einer Runde. Der Bildschirm springt zurück zur Kategoriewahl, die Runde ist weg.

Das ist das bekannte Loch aus 05C, es steht dort als Zusatzaufgabe. 06B macht es weder besser noch schlimmer. Wer es geschlossen hat, sieht heute zusätzlich, dass ein EditText seinen getippten Text von sich aus rettet.
