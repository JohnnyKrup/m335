XML verstehen

Modul 335 Mobile Applikationen, Grundlagen. Was android:, app: und tools: bedeuten und was das Zeichen @ macht. Lesezeit rund 9 Minuten. Fassung 1 vom 14.08.2026.

Wenn dir das beim ersten Mal nicht klar war, liegt das nicht an dir. Die Aufträge zeigen dir XML und du tippst es ab. Warum manche Zeilen mit android: anfangen, andere mit app: und wieder andere mit tools:, sagt dir keiner. Diese Seite holt das nach.

Danach liest du jedes Layout im Modul, ohne raten zu müssen. Du brauchst die Seite ab dem Moment, wo du das erste Layout im Code siehst.

1. Wie ein Layout anfängt

Jedes Layout beginnt mit einem Wurzelelement, und darin stehen ein paar Zeilen mit xmlns. Sie sehen aus wie Webadressen und man überliest sie gern.

<androidx.constraintlayout.widget.ConstraintLayout
    xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:app="http://schemas.android.com/apk/res-auto"
    xmlns:tools="http://schemas.android.com/tools"
    android:id="@+id/clMain" ...

xmlns heisst XML namespace, auf Deutsch Namensraum. Jede dieser drei Zeilen meldet ein Kürzel an. Ab dann darfst du dieses Kürzel als Präfix vor einem Attribut benutzen.

Die Adressen werden nie aufgerufen. Sie sind nur eindeutige Namen, damit sich zwei Anbieter nicht in die Quere kommen. Du tippst sie auch nie selbst, Android Studio schreibt sie hin.

Fehlt die Zeile, ist das Attribut rot. Wer im Layout tools:text benutzt, ohne dass oben xmlns:tools steht, bekommt einen Fehler. Android Studio bietet dann mit Alt und Enter an, die Zeile zu ergänzen. Das ist der ganze Fehler, mehr steckt nicht dahinter.

2. Die drei Präfixe auf einen Blick

android: app: tools:
PräfixWer hat das Attribut erfundenGilt in der laufenden App
android: Android selbst. Das Attribut steckt im Betriebssystem ja
app: eine Bibliothek, die dein Projekt zusätzlich benutzt ja
tools: Android Studio, nur für die Werkstatt nein

android: Was macht meine App?
app: Was macht meine App, aber es kommt aus einer Bibliothek.
tools: Was möchte ich beim Entwickeln sehen?

3. android:, was die Plattform selbst kennt

Das ist der Normalfall. Breite, Höhe, Text, Farbe, Abstand, Sichtbarkeit. Alles, was jedes Android-Gerät seit Jahren versteht, trägt dieses Präfix.

android:layout_width="match_parent"
android:layout_height="wrap_content"
android:text="Weiter"
android:textSize="14sp"
android:visibility="gone"

Wenn du unsicher bist, welches Präfix ein Attribut braucht, tipp die ersten Buchstaben und lass Android Studio vervollständigen. Es schlägt dir den richtigen Namensraum gleich mit vor.

4. app:, was aus einer Bibliothek kommt

Hier kommt die Antwort auf eine Frage, die sich alle stellen: warum heissen die Anker app:layout_constraintTop_toTopOf und nicht android:...?

Weil das ConstraintLayout kein Teil von Android ist. Es ist eine Bibliothek, die Google dazuliefert und die dein Projekt in build.gradle.kts anfordert. Erkennbar ist das schon am Namen des Elements:

// so heisst ein Element, das Android selbst mitbringt
<TextView ... />
<Button ... />
<LinearLayout ... >

// so heisst ein Element aus einer Bibliothek, mit vollem Pfad
<androidx.constraintlayout.widget.ConstraintLayout ... >

Ein Attribut, das es im Betriebssystem gar nicht gibt, kann nicht android: heissen. Also bekommt es den Namensraum app:. Der steht für "aus meiner App und ihren Bibliotheken".

Warum das praktisch wichtig ist. Android ändert sich langsam, denn ein neues Attribut im Betriebssystem erreicht alte Geräte nie. Eine Bibliothek dagegen wird mit deiner App ausgeliefert. Sie läuft darum auch auf einem Gerät von 2019, das vom ConstraintLayout noch nie gehört hat.

Das ist der Grund, warum in modernem Android so viel aus Bibliotheken kommt. Und darum siehst du app: so oft.

Der Trick mit layout_

Schau dir die Attributnamen genau an. Manche fangen mit layout_ an, andere nicht. Das ist kein Zufall.

AttributWen geht es etwas an
android:textSizedas Element selbst. Wie gross ist meine Schrift
android:textdas Element selbst. Was steht auf mir drauf
android:layout_widthden Parent. Wie breit soll er mich machen
android:layout_weightden Parent. Wie viel vom Restplatz kriege ich
app:layout_constraintTop_toTopOfden Parent. Woran soll er mich hängen

Alles, was mit layout_ anfängt, ist eine Nachricht an den Parent. Das erklärt zwei Dinge auf einmal.

  • layout_weight wirkt nur in einem LinearLayout, denn nur das kennt Gewichte. In einem anderen Parent wird es ignoriert.
  • layout_constraint... wirkt nur in einem ConstraintLayout. Steckst du ein Element in ein LinearLayout, sind seine Anker wertlos.

Merk dir den Satz: Anker gehören dem Parent. Wechselt der Parent, wechseln die Regeln.

5. tools:, was nur Android Studio sieht

Und jetzt das dritte Präfix. Es ist das einzige, das nie in der fertigen App landet. Beim Bauen wirft Android Studio alle tools:-Zeilen weg. Auf dem Gerät gibt es sie nicht.

Wozu dann? Weil viele Elemente ihren Inhalt erst zur Laufzeit vom Code bekommen. Im XML steht dann nichts, und die Vorschau in Android Studio zeigt eine leere Fläche. Gestalten kann man so nicht.

tools:text

<TextView
    android:id="@+id/tvName"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    tools:text="Max Mustermann" />

In der Vorschau von Android Studio

Max Mustermann

In der laufenden App, bevor der Code etwas setzt

leer

Du siehst also beim Gestalten, ob der Text umbricht, ob er passt, ob das Layout mit einem langen Namen noch gut aussieht. In der App steht dann der echte Wert, den dein Code hineinschreibt.

tools:visibility

Dasselbe Prinzip für die Sichtbarkeit. Ein Beispiel, das es in fast jeder App gibt, ein Ladeindikator:

<ProgressBar
    android:id="@+id/pbLoading"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    android:visibility="gone"
    tools:visibility="visible" />

Gelesen als Satz: "Zeig mir das Ding im Designer, aber wenn die App wirklich läuft, soll es weg sein."

Der Ladeindikator soll ja nur während des Ladens erscheinen. Stünde er im XML auf sichtbar, dreht er sich beim Start der App sinnlos vor sich hin. Stünde er nur auf gone, könntest du ihn im Layout-Editor gar nicht anfassen und positionieren. Beides zusammen löst das Problem.

Im Java-Code schaltest du ihn dann um:

pbLoading.setVisibility(View.VISIBLE);
// Daten laden ...
pbLoading.setVisibility(View.GONE);

Die drei Werte für visibility

WertSichtbarBraucht PlatzWann
visiblejajader Normalfall
invisibleneinjawenn nichts verrutschen darf, während etwas verschwindet
goneneinneinder Normalfall beim Ausblenden

invisible ist nicht dasselbe wie gone, und der Unterschied kostet Zeit, wenn man ihn nicht kennt. Ein Element auf invisible ist zwar unsichtbar, aber es liegt weiterhin da. Es hält seinen Platz frei, und es fängt Berührungen ab. Wer versucht, auf etwas darunter zu tippen, kommt nicht durch.

Nimm im Zweifel gone. Nimm invisible nur, wenn du willst, dass nichts nachrutscht, zum Beispiel bei einem Fehlertext über einem Eingabefeld.

tools:context

Die Zeile steht ganz oben in jedem Layout, das Android Studio erzeugt.

tools:context=".MainActivity"

Sie sagt der Vorschau, zu welcher Activity dieses Layout gehört. Damit kann Android Studio das richtige Theme anwenden und dir zeigen, wie der Bildschirm wirklich aussehen wird. In der App macht sie nichts. Lass sie stehen.

Es gibt noch mehr tools:-Attribute. Du triffst sie, wenn du sie brauchst, und dann gilt immer dieselbe Regel: alles mit tools: ist nur für dich, nie für den Benutzer.

6. Das Zeichen @, ein Verweis statt eines Werts

Neben den Präfixen gibt es ein zweites Zeichen, das man am Anfang überliest. Vergleich diese zwei Zeilen:

android:text="Weiter"          // der Wert steht direkt da
android:text="@string/btn_next" // hol den Wert woanders

Ein @ heisst immer: der Wert steht nicht hier, sondern in den Ressourcen. Was hinter dem @ steht, sagt dir, wo genau.

SchreibweiseSucht inBeispiel
@string/nameres/values/strings.xml@string/btn_next
@color/nameres/values/colors.xml@color/answer_correct
@drawable/nameres/drawable/@drawable/ic_launcher_background
@layout/nameres/layout/@layout/activity_main
@id/nameden ids in diesem Layout@id/tvCategory

Und was macht das Plus in @+id?

Das Plus heisst lege diese id neu an. Ohne Plus heisst es benutze die id, die es schon gibt.

SchreibweiseBedeutungWo du sie schreibst
@+id/tvScorelege die id tvScore anbei android:id, also bei der Vergabe
@id/tvScorebenutze die id tvScorebei jedem Verweis, zum Beispiel in einem Anker

Die anderen Ressourcen brauchen nie ein Plus, denn dort legst du den Eintrag in seiner eigenen Datei an. Eine id hat keine eigene Datei. Sie entsteht genau dort, wo du sie zum ersten Mal hinschreibst, und darum braucht sie das Plus.

Ein Sonderfall, der verwirrt. Verweist ein Anker auf ein Element, das im XML weiter unten steht, schreibt man dort ebenfalls @+id/.... Der Grund ist einfach: an dieser Stelle gibt es die id noch nicht, sie wird erst weiter unten vergeben. Mit dem Plus legst du sie schon hier an. In Layouts verstehen, Falle 3, steht dasselbe nochmals mit einem Beispiel.

Die Brücke zu Java

Jetzt kommt der Punkt, an dem XML und Java zusammenkommen. Für jeden Eintrag in den Ressourcen erzeugt Android beim Bauen einen Eintrag in einer Klasse namens R. Dieselbe Sache, zwei Schreibweisen:

Im XMLIm Java-Code
@string/btn_nextR.string.btn_next
@color/answer_correctR.color.answer_correct
@layout/activity_mainR.layout.activity_main
@+id/tvScoreR.id.tvScore

Aus dem @ wird ein R., aus dem Schrägstrich ein Punkt. Mehr ist es nicht.

Der Merksatz, der die ganze Woche trägt. Eine id steht an zwei Orten. Im XML wird sie vergeben, im Code wird sie benutzt.

Darum bricht dein Projekt, wenn du eine id im XML umbenennst und die Java-Zeile stehen lässt. Und darum ist cannot resolve symbol im Java-Code fast immer ein Tippfehler im XML oder umgekehrt.

8. Prüfe dich selbst

  1. Warum heisst es android:layout_width, aber app:layout_constraintTop_toTopOf? Antworte mit einem Satz über den Erfinder des Attributs.
  2. Du löschst in einem Layout die Zeile tools:text="Antwort 1". Was ändert sich in der laufenden App? Und was in der Vorschau?
  3. Ein Element steht auf invisible und liegt über einem Button. Warum reagiert der Button nicht?
  4. Nenn zwei Attribute, die mit layout_ anfangen, und sag zu jedem, welcher Parent sie überhaupt versteht.
  5. Erkläre einem Lerngspänli in einem Satz, warum eine id ein Plus braucht und ein Farbverweis nicht.

android: beeinflusst die App.
app: beeinflusst die App, kommt aus einer Bibliothek.
tools: hilft dir beim Entwickeln und wird beim Bauen weggeworfen.
@ heisst: der Wert steht woanders.
@+ heisst zusätzlich: und ich lege ihn hier an.
