Antworten zu den Denkfragen

1. allowMainThreadQueries() ist für dreissig Fragen richtig. Ab wann wäre es falsch?

Es gibt keine feste Grenze in Zeilen. Die richtige Frage ist die nach der Dauer einer einzelnen Abfrage. Der Bildschirm zeichnet alle sechzehn Millisekunden ein neues Bild. Alles, was länger dauert, lässt ein Bild ausfallen.

ein paar tausend Zeilen mit Sortierungeinige Millisekundenimmer noch fast nichts
zehntausende Zeilen, Verknüpfung über mehrere Tabellenhundert Millisekunden und mehrdie Liste ruckelt beim Scrollen
viele Zeilen am Stück schreibenSekundendie App reagiert nicht, Android bietet an, sie zu beenden

Woran du es zuerst merkst: nicht an einer Fehlermeldung, sondern am Scrollen. Die Liste hakt. Im Logcat erscheint dann irgendwann eine Zeile mit Skipped ... frames, und die kommt vom System und nicht von dir.

Der saubere Weg, kurz gezeigt: die Abfrage läuft in einem eigenen Thread, und das Ergebnis wird danach zurück auf den Haupt-Thread geholt. Nur der Haupt-Thread darf Views anfassen.

2. Sechs Methoden, eine läuft. Hättest du die anderen fünf später schreiben sollen?

Beide Seiten haben recht, und darum steht die Frage hier.

Dafür, alles jetztDagegen, nur was gebraucht wird
Ein Dao ist ein Vertrag mit der Tabelle, kein Ablauf. Einen Vertrag liest man ganzUngenutzter Code ist Code, den niemand je getestet hat. Er sieht richtig aus, weil er nie falsch war
Die vier Grundoperationen gehören zusammen. Wer nur die Hälfte hinschreibt, muss dreimal zurückkommenJede Methode kostet Javadoc und Aufmerksamkeit. Fünf davon heute umsonst
Beim Lesen sieht man auf einen Blick, was mit der Tabelle möglich istBeim nächsten Umbau traut sich niemand, eine ungenutzte Methode zu löschen. Sie könnte ja jemand brauchen
Room prüft dein SQL beim Bauen, auch ohne Aufruf. Du hast also heute schon eine RückmeldungBei einem Dao mit zwanzig Methoden weiss niemand mehr, welche echt gebraucht wird

Die Entscheidung für diesen Kurs ist: alles jetzt. Nicht weil das Argument stärker ist, sondern weil das letzte Argument in der rechten Spalte bei sechs Methoden noch nicht greift und du am Nachmittag ohnehin fünf davon brauchst.

Der Unterschied, auf den es wirklich ankommt. Bei einer Activity oder einem Adapter gilt weiterhin: schreib nichts, was niemand aufruft. Dort ist ungenutzter Code ein Ablauf, der nie stattfindet.

Ein Dao ist keine Ablaufbeschreibung. Es ist eine Aufzählung dessen, was mit der Tabelle erlaubt ist. Der Unterschied ist der zwischen einem Rezept und einer Einkaufsliste.

Die Rangliste ist der Grenzfall. Sie liegt in SharedPreferences, aber als JSON-Text in einem einzigen Eintrag. Die Fragen sind der klare Fall. Viele gleichartige Dinge, sortiert angezeigt, einzeln zu ändern und zu löschen. Genau dafür gibt es Tabellen.

package ch.wiss.m335.quiz.data;

import androidx.annotation.NonNull;
import androidx.room.ColumnInfo;
import androidx.room.Entity;
import androidx.room.PrimaryKey;

/**
 * Eine Quizfrage, wie sie in der Datenbank liegt.
 *
 * Die Vorlage ist Question aus dem Paket model. Dieselben Angaben, aber mit
 * drei Unterschieden, und jeder hat einen Grund:
 *
 * Erstens gibt es eine id. Eine Zeile in einer Tabelle braucht eine Nummer,
 * an der man sie wiederfindet. Room vergibt sie selbst.
 *
 * Zweitens stehen die vier Antworten in vier einzelnen Spalten und nicht in
 * einem Array. Eine Tabellenspalte hält einen einzelnen Wert. Ein Array
 * bräuchte einen TypeConverter, und den brauchen wir hier nicht.
 *
 * Drittens gibt es keinen Konstruktor mit Werten, sondern Setter. Room baut
 * die Objekte selbst, wenn es eine Zeile aus der Tabelle liest. Dafür braucht
 * es einen leeren Konstruktor und einen Setter pro Spalte.
 *
 * Question bleibt im Projekt liegen. Leg die zwei Dateien nebeneinander, dann
 * siehst du auf einen Blick, was Room dazu bringt.
 */
@Entity(tableName = "questions")
public class QuestionEntity {

    /** Die Nummer der Zeile. Room vergibt sie beim Einfügen selbst. */
    @PrimaryKey(autoGenerate = true)
    private int id;

    /** Der Fragetext. */
    @NonNull
    @ColumnInfo(name = "text")
    private String text = "";

    /** Erste Antwortmöglichkeit. */
    @NonNull
    @ColumnInfo(name = "answer1")
    private String answer1 = "";

    /** Zweite Antwortmöglichkeit. */
    @NonNull
    @ColumnInfo(name = "answer2")
    private String answer2 = "";

    /** Dritte Antwortmöglichkeit. */
    @NonNull
    @ColumnInfo(name = "answer3")
    private String answer3 = "";

    /** Vierte Antwortmöglichkeit. */
    @NonNull
    @ColumnInfo(name = "answer4")
    private String answer4 = "";

    /** Die richtige Antwort als Text. Muss einer der vier Antworten entsprechen. */
    @NonNull
    @ColumnInfo(name = "correct_answer")
    private String correctAnswer = "";

    /** Kategorie: Sport, Technologie, Geographie oder Geschichte. */
    @NonNull
    @ColumnInfo(name = "category")
    private String category = "";

    /** Schwierigkeit: leicht, mittel oder schwer. */
    @NonNull
    @ColumnInfo(name = "difficulty")
    private String difficulty = "leicht";

    /**
     * Liefert die vier Antworten als Array.
     *
     * Damit sieht diese Klasse von aussen gleich aus wie Question, und der
     * Spielbildschirm muss später nichts anders machen.
     *
     * @return die vier Antworten in fester Reihenfolge
     */
    public String[] getAnswers() {
        return new String[]{answer1, answer2, answer3, answer4};
    }

    /**
     * Prüft, ob eine angetippte Antwort richtig ist.
     *
     * @param givenAnswer die Antwort, die der Spieler angetippt hat
     * @return true, wenn die Antwort richtig ist
     */
    public boolean isCorrect(String givenAnswer) {
        return correctAnswer.equals(givenAnswer);
    }

    /** @return die Nummer der Zeile */
    public int getId() { return id; }

    /** @param id die Nummer der Zeile, wird von Room gesetzt */
    public void setId(int id) { this.id = id; }

    /** @return der Fragetext */
    public String getText() { return text; }

    /** @param text der Fragetext */
    public void setText(@NonNull String text) { this.text = text; }

    /** @return erste Antwort */
    public String getAnswer1() { return answer1; }

    /** @param answer1 erste Antwort */
    public void setAnswer1(@NonNull String answer1) { this.answer1 = answer1; }

    /** @return zweite Antwort */
    public String getAnswer2() { return answer2; }

    /** @param answer2 zweite Antwort */
    public void setAnswer2(@NonNull String answer2) { this.answer2 = answer2; }

    /** @return dritte Antwort */
    public String getAnswer3() { return answer3; }

    /** @param answer3 dritte Antwort */
    public void setAnswer3(@NonNull String answer3) { this.answer3 = answer3; }

    /** @return vierte Antwort */
    public String getAnswer4() { return answer4; }

    /** @param answer4 vierte Antwort */
    public void setAnswer4(@NonNull String answer4) { this.answer4 = answer4; }

    /** @return die richtige Antwort als Text */
    public String getCorrectAnswer() { return correctAnswer; }

    /** @param correctAnswer die richtige Antwort als Text */
    public void setCorrectAnswer(@NonNull String correctAnswer) { this.correctAnswer = correctAnswer; }

    /** @return die Kategorie */
    public String getCategory() { return category; }

    /** @param category die Kategorie */
    public void setCategory(@NonNull String category) { this.category = category; }

    /** @return die Schwierigkeit */
    public String getDifficulty() { return difficulty; }

    /** @param difficulty die Schwierigkeit */
    public void setDifficulty(@NonNull String difficulty) { this.difficulty = difficulty; }
}

package ch.wiss.m335.quiz.data;

import androidx.room.Dao;
import androidx.room.Delete;
import androidx.room.Insert;
import androidx.room.Query;
import androidx.room.Update;

import java.util.List;

/**
 * Der Zugriff auf die Tabelle questions.
 *
 * Ein Dao ist ein Interface. Du schreibst nur hin, was du haben willst, und
 * Room baut die Methode dahinter beim Bauen der App selbst. Genau darum
 * braucht Room den Annotation Processor in build.gradle.kts.
 *
 * Dao heisst Data Access Object. In Modul 294 hat json-server dieselbe Aufgabe
 * über HTTP erledigt. Der Unterschied ist der Ort: dort ein Server im Netz,
 * hier eine Datei auf dem Gerät.
 *
 * Die vier Grundoperationen heissen zusammen CRUD, also Create, Read, Update
 * und Delete. Genau diese vier braucht auch die Leistungsbeurteilung. Sie
 * stehen hier von Anfang an vollständig da, auch wenn zuerst nur count
 * benutzt wird. Ein Dao ist der Vertrag mit der Tabelle, und einen Vertrag
 * schreibt man einmal ganz.
 */
@Dao
public interface QuestionDao {

    /**
     * Legt eine neue Frage an.
     *
     * Die id im übergebenen Objekt wird nicht beachtet. Room vergibt eine
     * eigene und gibt sie zurück.
     *
     * @param question die neue Frage
     * @return die id, die Room vergeben hat
     */
    @Insert
    long insert(QuestionEntity question);

    /**
     * Speichert Änderungen an einer bestehenden Frage.
     *
     * Room erkennt die Frage an ihrer id. Ist die id 0, findet Room keine
     * passende Zeile, und es passiert gar nichts. Das ist der häufigste
     * Fehler beim Bearbeiten.
     *
     * @param question die geänderte Frage, inklusive ihrer id
     */
    @Update
    void update(QuestionEntity question);

    /**
     * Löscht eine Frage.
     *
     * Auch hier zählt nur die id. Die anderen Felder darf Room ignorieren.
     *
     * @param question die zu löschende Frage
     */
    @Delete
    void delete(QuestionEntity question);

    /**
     * Liefert alle Fragen, nach Kategorie und dann nach id sortiert.
     *
     * Die Sortierung steht im SQL und nicht in Java. Die Datenbank kann das
     * besser, und die Liste kommt schon fertig geordnet an.
     *
     * @return alle Fragen, nie null
     */
    @Query("SELECT * FROM questions ORDER BY category, id")
    List<QuestionEntity> getAll();

    /**
     * Liefert eine einzelne Frage.
     *
     * Wird beim Bearbeiten gebraucht, um das Formular zu füllen.
     *
     * @param id die Nummer der Frage
     * @return die Frage, oder null wenn es sie nicht gibt
     */
    @Query("SELECT * FROM questions WHERE id = :id")
    QuestionEntity findById(int id);

    /**
     * Zählt alle Fragen.
     *
     * Beantwortet die Frage, ob überhaupt etwas in der Tabelle steht. Beim
     * Start entscheidet sich daran, ob der Startbestand geladen werden muss.
     *
     * @return Anzahl Fragen in der Tabelle
     */
    @Query("SELECT COUNT(*) FROM questions")
    int count();
}

package ch.wiss.m335.quiz.data;

import android.content.Context;
import android.util.Log;

import androidx.room.Database;
import androidx.room.Room;
import androidx.room.RoomDatabase;

/**
 * Die Datenbank der App.
 *
 * Diese Klasse ist abstract, und trotzdem entsteht daraus ein Objekt. Room
 * schreibt die fehlende Klasse beim Bauen der App selbst und nennt sie
 * QuizDatabase_Impl. Dort steht auch das CREATE TABLE, das du nie geschrieben
 * hast. Room.databaseBuilder liefert dann ein Objekt davon.
 *
 * Es gibt genau eine Datenbank pro App. Darum das Feld instance und die
 * Methode getInstance. Wer bei jedem Zugriff eine neue Datenbank baut,
 * verbraucht Speicher und riskiert, dass zwei Verbindungen gleichzeitig
 * schreiben.
 *
 * allowMainThreadQueries ist eine bewusste Entscheidung für diesen Kurs. Room
 * verbietet Abfragen im Haupt-Thread von sich aus, weil eine langsame Abfrage
 * die Oberfläche einfrieren lässt. Unsere Tabelle hat dreissig Zeilen und
 * liegt auf dem Gerät. Eine Abfrage dauert deutlich unter einer Millisekunde,
 * der Bildschirm zeichnet alle sechzehn Millisekunden. Das merkt niemand. Bei
 * einer echten App mit vielen Daten gehört die Abfrage in einen eigenen
 * Thread.
 *
 * Nach 07C ist die Tabelle leer. Gefüllt wird sie in 08A.
 */
@Database(entities = {QuestionEntity.class}, version = 1, exportSchema = false)
public abstract class QuizDatabase extends RoomDatabase {

    /**
     * Log-Tag für das ganze Modul 335.
     *
     * Bewusst nicht "M335". Diese Zeichenfolge steckt auch im Paketnamen
     * ch.wiss.m335.quiz. Das Suchfeld im Logcat sucht im Freitext über alle
     * Spalten, und damit träfe "M335" jede Zeile unserer App statt nur die
     * selbst geschriebenen.
     */
    private static final String TAG = "Modul335";

    /** Der Dateiname der Datenbank auf dem Gerät. */
    private static final String DB_NAME = "quiz.db";

    /** Die eine Datenbank. Wird beim ersten Zugriff gebaut. */
    private static QuizDatabase instance;

    /**
     * Der Zugriff auf die Tabelle questions.
     *
     * Auch diese Methode ist abstract. Room baut sie selbst.
     *
     * @return das Dao, über das alle Abfragen laufen
     */
    public abstract QuestionDao questionDao();

    /**
     * Liefert die Datenbank und baut sie beim ersten Aufruf.
     *
     * synchronized, damit nicht zwei Aufrufe gleichzeitig je eine Datenbank
     * bauen.
     *
     * getApplicationContext ist wichtig. Eine Activity ist ein kurzlebiges
     * Objekt. Die Datenbank lebt so lange wie die App. Wer eine Activity
     * festhält, hält den ganzen Bildschirm im Speicher fest, auch wenn er
     * längst geschlossen ist.
     *
     * @param context irgendein Context, zum Beispiel eine Activity
     * @return die eine Datenbank der App
     */
    public static synchronized QuizDatabase getInstance(Context context) {
        if (instance == null) {
            Context appContext = context.getApplicationContext();

            instance = Room.databaseBuilder(appContext, QuizDatabase.class, DB_NAME)
                    .allowMainThreadQueries()
                    .build();

            // build() legt die Datei noch nicht an. Das passiert erst beim
            // ersten Zugriff, also bei count() gleich hier darunter.
            Log.d(TAG, "database opened, name=" + DB_NAME
                    + ", questions=" + instance.questionDao().count());
        }
        return instance;
    }
}

Die Stelle aus C2, aufgelöst

count() liefert 0, Antwort Nummer 2. Kein Absturz, obwohl du nie ein CREATE TABLE geschrieben hast.

Was du tustWas Room in dem Moment tut
Room.databaseBuilder(...)merkt sich Name, Klasse und Einstellungen. Sonst nichts
.build()baut das Objekt. Die Datei auf dem Gerät gibt es immer noch nicht
dein count()hier passiert alles: Datei anlegen, CREATE TABLE ausführen, dann zählen

Das CREATE TABLE hast du in C1 selbst gelesen, in QuizDatabase_Impl. Room hat es aus deiner QuestionEntity abgeleitet, mit deinen neun Spalten und ihren Typen.

Der Merksatz: deine Tabelle entsteht beim ersten Zugriff, nicht beim Bauen und nicht beim Öffnen. Und sie entsteht aus deiner Klasse, nicht aus SQL, das du geschrieben hast.

Warum das mehr ist als eine Kuriosität. Am Nachmittag wirst du beim allerersten Start dreissig Fragen in eine Tabelle schreiben, die es in dem Moment noch gar nicht gibt. Dass das funktioniert, hängt genau an dieser Reihenfolge.

Und beim Aufräumen gilt dasselbe rückwärts: wer die App-Daten löscht, löscht die Datei. Beim nächsten Start ist die Tabelle wieder da, und sie ist wieder leer.

Lösungen zu den Übungen

Übung 1a, der Tippfehler im SQL. Der Fehler kommt beim Bauen, nicht beim Start. In der Meldung steht sinngemäss There is a problem with the query: no such table: question, und Android Studio zeigt dir die Zeile im Dao.

Würde das SQL erst beim Start geprüft, bekämst du stattdessen einen Absturz auf dem Gerät. Bei einer Abfrage, die nur selten läuft, sogar erst beim Kunden. Das ist der ganze Grund, warum Room den Umweg über den Annotation Processor geht.

Übung 1b, die harmlose Zeile. Ohne @ColumnInfo heisst die Spalte correctAnswer, also genau wie das Feld. Im CREATE TABLE steht dann `correctAnswer` TEXT NOT NULL statt `correct_answer` TEXT NOT NULL.

Kein Werkzeug meldet das, denn beides ist gültig. Es wird erst teuer, wenn jemand von aussen auf die Tabelle schaut, oder wenn du die Datenbank später von einem anderen Programm lesen lässt. Dort ist correct_answer die übliche Schreibweise, und correctAnswer fällt auf.

Und daran hängt eine allgemeinere Sache. Java und SQL haben verschiedene Gewohnheiten für Namen. In Java schreibt man correctAnswer, in SQL correct_answer. @ColumnInfo ist genau die Stelle, an der du beide bedienen kannst, ohne dass eine Seite nachgeben muss.

Übung 2, die Bremse wieder einbauen. Die App stürzt beim Start ab. Im Logcat steht:

IllegalStateException: Cannot access database on the main thread since
it may potentially lock the UI for a long period of time.

Room sagt dir damit zwei Dinge. Erstens: du greifst gerade auf dem Haupt-Thread zu. Zweitens, und das ist der wichtige Teil: it may potentially lock the UI. Room weiss nicht, wie gross deine Tabelle ist. Es warnt vorsorglich, weil es der häufigere Fall ist.

Wir haben es erlaubt, weil wir die Zahlen kennen. Dreissig Zeilen, lokal, unter einer Millisekunde. Das ist der Unterschied zwischen einer Regel ignorieren und eine Regel begründet aussetzen.

Übung 3, warum ein Interface funktioniert. Weil der fehlende Code beim Bauen entsteht. room-compiler liest deine Annotationen und schreibt eine Klasse, die dein Interface implementiert. Sie heisst QuestionDao_Impl, und du kannst sie mit zweimal Shift öffnen.

Der Zeitpunkt ist die ganze Antwort. Nicht beim Start und nicht beim Schreiben, sondern beim Bauen. Darum steht annotationProcessor in build.gradle.kts und nicht implementation.

Mögliche falsche KI-Rückmeldungen

Das ist eine Prüfliste und keine Anklage. Nicht jede KI macht diese Fehler. Aber wenn du eine gefragt hast, schau die Punkte einmal durch.

So prüfst du das Ganze

  1. App starten. Sie sieht aus wie vorher, kein neuer Knopf, keine neue Zeile.
  2. Logcat unter tag:Modul335: database opened, name=quiz.db, questions=0, darunter MainActivity onCreate.
  3. In die Rangliste und zurück. Die Zeile database opened kommt kein zweites Mal.
  4. App beenden und neu starten. Die Zeile kommt wieder, und es steht wieder questions=0.
  5. Eine Runde spielen. Alles läuft wie vorher.
  6. Database Inspector: die Tabelle questions ist da, leer, mit neun Spalten.
  7. Eine Spalte heisst correct_answer, mit Unterstrich.
  8. Zweimal Shift, QuizDatabase_Impl: dort steht ein CREATE TABLE mit deinen neun Spalten.
  9. Zweimal Shift, QuestionDao_Impl: dort stehen die Rümpfe deiner sechs Methoden.

Punkt 9 ist ein Extra, und er lohnt sich. Dort siehst du, was du dir erspart hast. Für insert allein sind es rund zwanzig Zeilen, die du sonst von Hand schreiben müsstest, für jede der sechs Methoden.

Was noch nicht gut ist, und das mit Absicht

  • Die Tabelle ist leer. Gefüllt wird sie am Nachmittag in 08A, aus einer Datei.
  • Es gibt keinen Bildschirm dafür. Der Knopf Fragen verwalten ist weiterhin grau. Auch das kommt in 08A.
  • Das Spiel holt seine Fragen weiterhin aus QuestionBank. Der Umzug ist noch nicht gemacht.
  • Fünf der sechs Dao-Methoden sind ungenutzt. Sie kommen am Nachmittag und am letzten Kurstag dran.
  • Kein TypeConverter, kein LiveData, kein Flow.
  • Keine Migration. version = 1 bleibt bis zum Kursende. Wer die Tabelle ändert, deinstalliert die App.
  • Die Rangliste bleibt in SharedPreferences. Das ist kein Versäumnis, sondern der Grund, warum du beide Verfahren vergleichen kannst.
  • Question.java bleibt liegen. Als Vergleichsstück zu QuestionEntity.
