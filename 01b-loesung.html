Das fertige activity_main.xml

Der Stand am Ende von Teil B. Nur die eine Zeile mit der id ist neu, alles andere hat die Vorlage erzeugt.

        android:layout_height="wrap_content"

android:text="Hello World!" bleibt stehen und das ist richtig. Der Text aus dem XML wird beim Laden gesetzt. Dein setText im Code läuft danach und überschreibt ihn. Wer die Zeile löscht, sieht keinen Unterschied. Wer sie stehen lässt, sieht im Layout-Editor weiterhin etwas.

Das fertige MainActivity.java

Der Stand am Ende von Teil B und nach der Reparatur in C4. Die zwei neuen Zeilen stehen nach setContentView.

package ch.wiss.m335.helloworld;

import android.os.Bundle;
import android.widget.TextView;              // von Alt und Enter erzeugt
import androidx.activity.EdgeToEdge;
import androidx.appcompat.app.AppCompatActivity;
import androidx.core.graphics.Insets;
import androidx.core.view.ViewCompat;
import androidx.core.view.WindowInsetsCompat;

public class MainActivity extends AppCompatActivity {

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        EdgeToEdge.enable(this);
        setContentView(R.layout.activity_main);

        ViewCompat.setOnApplyWindowInsetsListener(findViewById(R.id.main), (v, insets) -> {
            Insets systemBars = insets.getInsets(WindowInsetsCompat.Type.systemBars());
            v.setPadding(systemBars.left, systemBars.top, systemBars.right, systemBars.bottom);
            return insets;
        });

        // deine zwei neuen Zeilen, nach setContentView
        TextView tvGreeting = findViewById(R.id.tvGreeting);
        tvGreeting.setText("Hallo Anna!");
    }
}

Der Block mit dem Pfeil bleibt unangetastet. Er sorgt dafür, dass dein Inhalt nicht unter der Uhr und nicht unter der Navigationsleiste liegt. Wer ihn löscht, hat am Nachmittag in Block 02 ein Problem, das er nicht mehr zuordnen kann.

Teil C, der Stacktrace

So sieht der Absturz aus. Bei dir stehen andere Zeilennummern und ein anderer Paketname.

SchrittWas du findestWarum
1 Rund die Hälfte der Zeilen beginnt mit android.app. oder com.android. Das ist Android selbst beim Starten der Activity. Nie dein Fehler
2 Caused by: java.lang.NullPointerException: Attempt to invoke virtual method 'void android.widget.TextView.setText(java.lang.CharSequence)' on a null object reference Das ist die echte Ursache. Der obere Teil sagt nur, dass die Activity nicht starten konnte
3 Die erste Zeile mit deinem Paketnamen, etwa at ch.wiss.m335.helloworld.MainActivity.onCreate(MainActivity.java:22) Datei und Zeilennummer. Genau dort steht dein setText

Die Antwort in einem Satz: findViewById stand vor setContentView. Zu diesem Zeitpunkt gab es die Views noch nicht, also lieferte es null. Der Aufruf von setText auf null hat die App zum Absturz gebracht.

Der Satz, der bei jedem Absturz hilft. Die Meldung nennt immer die Methode, die nicht ausgeführt werden konnte, und den Grund. Hier: setText auf null. Wer nur "NullPointerException" liest und aufhört, verschenkt die halbe Information.

Antworten zu den Denkfragen

Diese drei Fragen kommen im 01B Check als Quizfragen wieder. Hier steht die längere Begründung dazu.

Frage 1, was macht setContentView genau?

Es liest die XML-Datei, erzeugt daraus die Java-Objekte der Views und hängt sie an das Fenster der Activity.

Warum das zählt: Vorher gibt es die Views nicht, nachher schon. Das ist der ganze Grund, warum findViewById danach stehen muss. Genau diesen Fehler hast du in Teil C selbst erzeugt.

Frage 2, woher kommt R.id.tvGreeting?

Die R-Klasse wird von Gradle beim Bauen automatisch erzeugt, aus allem, was im Ordner res liegt. Für jede id entsteht eine Konstante mit einer Zahl dahinter.

Warum das zählt: Du schreibst sie nie von Hand und änderst sie nie von Hand. Wenn R.id.tvGreeting rot bleibt, obwohl die id im XML steht, wurde die R-Klasse nur noch nicht neu erzeugt. Build, dann Rebuild Project löst das.

Frage 3, wann wird der Block mit dem Pfeil ausgeführt?

Nicht sofort. Der Block wird nur angemeldet. Ausgeführt wird er erst dann, wenn das System die Fensterausschnitte meldet, also nach dem Zeichnen.

Warum das zählt: Das ist der Unterschied zwischen Anmelden und Ausführen. Genau darauf baut 01C auf. Ein Klick-Listener funktioniert nach demselben Muster: du schreibst den Code jetzt hin, ausgeführt wird er irgendwann später oder nie.

Lösungen der zwei Übungen

Sie gehören zur Hausaufgabe 1.

Übung 1, eine zweite Zeile

Im XML eine zweite TextView neben die erste, ohne android:text. Damit sie nicht übereinander liegen, hängst du sie unter die erste.

<TextView
    android:id="@+id/tvClass"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    android:layout_marginTop="8dp"
    app:layout_constraintTop_toBottomOf="@id/tvGreeting"
    app:layout_constraintStart_toStartOf="parent"
    app:layout_constraintEnd_toEndOf="parent" />

Und im Code, nach den zwei bestehenden Zeilen:

TextView tvClass = findViewById(R.id.tvClass);
tvClass.setText("Klasse ABC");

Begründung: Es ist dasselbe Muster wie in Teil B, nur ein zweites Mal. Wer es hier ohne Vorlage schafft, hat den Weg vom Layout zum Code verstanden und nicht nur abgetippt. Neu ist einzig constraintTop_toBottomOf mit @id ohne Plus. Das kommt am Nachmittag in Block 02 ausführlich.

Übung 2, erklären

Eine mögliche Erklärung: setContentView baut den Bildschirm erst auf. Vorher existiert keine einzige View. findViewById durchsucht die Views, die es schon gibt. Wenn es keine gibt, findet es nichts und liefert null zurück. Es meldet keinen Fehler, es liefert einfach nichts. Der Fehler kommt erst eine Zeile später, wenn man auf diesem Nichts setText aufruft.

Begründung: Der wichtige Punkt ist, dass findViewById selbst nicht abstürzt. Wer das erklären kann, versteht auch, warum die Fehlermeldung auf setText zeigt und nicht auf findViewById. Genau diese Verschiebung zwischen Ursache und Absturzstelle macht Stacktraces am Anfang verwirrend.

Zur Zusatzaufgabe

Dazu gibt es hier bewusst keine Lösung. Die Frage bleibt offen, das ist ihr Zweck.

Hinweise für die Lehrperson

  • Der rote Import ist die erste echte Hürde. Sag den Satz einmal laut für alle: rot heisst nicht Fehler, rot heisst Import fehlt. Das spart ein Dutzend Handmeldungen.
  • Häufigster Fehler in C1: Beim Verschieben wird auch der Block mit dem Pfeil verschoben oder gelöscht. Dann stürzt die App aus einem anderen Grund ab und der Stacktrace zeigt etwas anderes. Darum steht "du ergänzt nur, du löschst nichts" zweimal im Auftrag.
  • Der Nachweis ist die abgeschriebene Caused by-Zeile, nicht der Screenshot. Ein Screenshot beweist nur, dass jemand den Reiter geöffnet hat. Beim Korrigieren also auf die Zeilennummer schauen: sie muss bei jedem anders sein.
  • Der Blockschnitt liegt zwischen Teil B und Teil C. Lass niemanden mit einer abstürzenden App in die Pause gehen. Wer bei Minute 18 noch nicht seinen Namen auf dem Emulator hat, holt Teil C nach der Pause nach.
  • Zum Buch: nur Kapitel 3.6 angeben. Die Abschnitte 3.1 bis 3.4 sind veraltet, und 3.4 nennt Empty Activity. Wer dem folgt, hat kein XML-Layout und kann den Auftrag nicht durchführen.
