02 Auftrag

Ausgangslage

Dein Spielbildschirm hat zwei Bereiche, und vier Zeilen im Code entscheiden darüber, welcher davon zu sehen ist. Sie stehen an zwei verschiedenen Stellen. Das ging bisher gut.

Heute kommt ein dritter Bereich dazu. Vorher räumst du auf, denn mit drei Bereichen und sechs verstreuten Zeilen weiss nach zwei Stunden niemand mehr, was gerade sichtbar ist.

Denkfragen

  1. showState setzt bei jedem Aufruf alle drei Bereiche, auch die, die sich gar nicht ändern. Ist das nicht Verschwendung? Was wäre die Alternative, und was kostet sie?
  2. Die drei Zustände sind ein enum und nicht drei boolean-Felder. Nenne zwei Vorteile.
  3. Die dreissig Fragen ziehen in eine eigene Klasse um, die nie erzeugt wird und nur statische Methoden hat. Warum kein Objekt?
  4. Beim Zusammenstellen der Runde wird eine Kopie gemischt und nicht der Bestand selbst. Was ginge kaputt, wenn du das Original mischst?

Diese vier Fragen kommen im 05CD Wissenscheck wieder. Dasselbe gilt für das, was du in A3 beobachtest.

Der Überblick, bevor Teil A anfängt

Such in deiner GameActivity nach setVisibility. Du findest sechs Aufrufe. Vier davon gehören den zwei Bereichen, zwei dem Weiter-Knopf.

WoWasBleibt oder geht
startRoundllResult auf GONE, svQuestion auf VISIBLEgeht, wird zu showState
showResultsvQuestion auf GONE, llResult auf VISIBLEgeht, wird zu showState
showQuestionbtnNext auf GONEbleibt
onAnswerClickedbtnNext auf VISIBLEbleibt

Der Weiter-Knopf gehört nicht dazu. showState entscheidet über die drei grossen Bereiche, die sich abwechseln. Der Knopf ist ein Detail innerhalb eines Bereichs, er erscheint und verschwindet mitten in derselben Ansicht.

Wer ihn mit hineinnimmt, hat eine Methode, die zwei verschiedene Dinge tut, und muss sie ab dann bei jeder Antwort aufrufen.

Wohin das führt

ConstraintLayout clGame
├─ LinearLayout llCategory   // Zustand 1, neu in Teil B
├─ ScrollView svQuestion     // Zustand 2
└─ LinearLayout llResult       // Zustand 3

Alle drei an denselben vier Ankern, alle gleich gross,
alle übereinander. Genau einer ist sichtbar.

Die Reihenfolge in diesem Auftrag ist Absicht. Zuerst räumst du mit zwei Bereichen auf, dann kommt der dritte dazu. So merkst du selbst, was das Aufräumen gebracht hat: der dritte Zustand kostet dich eine Zeile.

Teil A, aus vier Stellen wird eine 16 Minuten

Was du in A1 brauchst

Baustein oder NameWofür

A1Der enum und die neue Methode.

In GameActivity.java, unter dem Feld QUESTIONS_PER_ROUND:

/** Die Zustände, die dieser Bildschirm kennt. */
private enum GameState { QUESTION, RESULT }

Und die Methode, ans Ende der Klasse. Tipp sie genau so ab, sie ist in dieser Form noch nicht fertig.

/**
 * Schaltet den Bildschirm auf einen Zustand um.
 *
 * Das ist die einzige Stelle, die über Sichtbarkeit entscheidet.
 */
private void showState(GameState state) {
    if (state == GameState.QUESTION) {
        svQuestion.setVisibility(View.VISIBLE);
    }
    if (state == GameState.RESULT) {
        llResult.setVisibility(View.VISIBLE);
    }

    Log.d(TAG, "showState " + state);
}

Ein enum ist ein eigener Typ mit fest benannten Werten. GameState.QUESTION ist kein Text und keine Zahl, sondern ein Wert dieses Typs.

Der Gewinn ist der Compiler. Schreibst du GameState.QUESTIN, wird die Zeile sofort rot. Mit einer Zahl oder einem Text merkst du den Tippfehler erst beim Laufen, und dann passiert einfach nichts.

A4Die Methode setzt alle Bereiche.

Ersetze den Rumpf von showState durch das hier:

private void showState(GameState state) {
    svQuestion.setVisibility(state == GameState.QUESTION ? View.VISIBLE : View.GONE);
    llResult.setVisibility(state == GameState.RESULT ? View.VISIBLE : View.GONE);

    Log.d(TAG, "showState " + state);
}

Das Fragezeichen und der Doppelpunkt

Bedingung ? a : b ist ein if in einer Zeile, das einen Wert liefert. Es liest sich als Frage: stimmt die Bedingung? Dann a, sonst b.

// diese zwei Zeilen bedeuten dasselbe
svQuestion.setVisibility(state == GameState.QUESTION ? View.VISIBLE : View.GONE);

if (state == GameState.QUESTION) { svQuestion.setVisibility(View.VISIBLE); }
else { svQuestion.setVisibility(View.GONE); }

Nimm ihn nur dort, wo genau ein Wert von genau einer Bedingung abhängt. Für alles Grössere bleibt das normale if lesbarer.

Der Kern des Auftrags steht in diesen zwei Zeilen. Jede von ihnen entscheidet über einen Bereich, und zwar bei jedem Aufruf. Kein Bereich bleibt aus Versehen stehen, weil niemand an ihn gedacht hat.

Vorher standen vier Zeilen an zwei Stellen, und du musstest bei jeder Änderung beide finden. Jetzt gibt es genau eine Stelle. Wer wissen will, was gerade zu sehen ist, liest diese zwei Zeilen und sonst nichts.

So prüfst du Teil A.

  • Die App verhält sich wieder genau wie vorher. Frage, Ergebnis, Liste, alles am richtigen Ort.
  • In deiner ganzen GameActivity gibt es keinen einzigen setVisibility-Aufruf mehr auf svQuestion oder llResult ausserhalb von showState.
  • Die zwei Zeilen mit btnNext stehen unverändert da.
  • Im Logcat steht bei einer Runde zuerst showState QUESTION und am Schluss showState RESULT.

B5Der dritte Zustand. Eine Zeile.

Im enum, als erster Wert:

Und in showState, als erste Zeile im Rumpf:

llCategory.setVisibility(state == GameState.CHOOSE_CATEGORY ? View.VISIBLE : View.GONE);

Das war es. Ein ganzer neuer Zustand, und er kostet dich eine Zeile an einer Stelle.

Rechne durch, was er dich ohne Teil A gekostet hätte. Drei Bereiche, jeder muss bei jedem Wechsel gesetzt werden, das sind neun Zeilen, verteilt auf drei Methoden. Und bei jeder Änderung suchst du sie alle wieder zusammen.

B6Die Runde entsteht aus der Auswahl.

Die neue Methode, direkt über startRound:

/**
 * Stellt die Runde aus der gewählten Kategorie zusammen und startet sie.
 *
 * Gemischt wird eine Kopie des Bestands, nicht der Bestand selbst.
 */
private void onStartClicked() {
    selectedCategory = (String) spnCategory.getSelectedItem();
    categoryQuestions = QuestionBank.byCategory(selectedCategory);

    List<Question> pool = new ArrayList<>(categoryQuestions);
    Collections.shuffle(pool);

    int count = Math.min(QUESTIONS_PER_ROUND, pool.size());
    roundQuestions = new ArrayList<>(pool.subList(0, count));

    Log.d(TAG, "category=" + selectedCategory + ", bank=" + categoryQuestions.size()
            + ", round=" + count);

    startRound();
}

Und startRound stellt jetzt keine Fragen mehr zusammen, es startet nur noch. Die Zeile mit subList darin fällt weg:

private void startRound() {
    // Eine neue Runde macht das alte Ergebnis ungültig, bis sie fertig ist.
    setResult(RESULT_CANCELED);

    currentIndex = 0;
    score = 0;

    showQuestion();
    showState(GameState.QUESTION);

    Log.d(TAG, "round started");
}

Drei Zeilen ganz am Schluss von onCreate ändern sich. Der Aufruf startRound(); fällt weg, dafür kommt:

showState(GameState.CHOOSE_CATEGORY);

Und der Knopf Nochmals spielen führt zurück zur Auswahl statt direkt in eine Runde:

btnRestart.setOnClickListener(v -> showState(GameState.CHOOSE_CATEGORY));

Warum eine Kopie gemischt wird. Collections.shuffle mischt die Liste, die du ihm gibst, an Ort und Stelle. Gibst du ihm categoryQuestions, ist danach dein Bestand durcheinander.

Sichtbar wird das im Ergebnisbereich: die Liste aller Fragen stünde bei jeder Runde in einer anderen Reihenfolge. Ein Bestand hat aber eine feste Ordnung, sonst findet man nichts wieder.

Math.min ist kein Zierrat. Er sorgt dafür, dass eine Kategorie mit weniger als fünf Fragen nicht abstürzt. Heute hat jede genug, aber am Tag 4 legen die Benutzer selbst Fragen an, und dann garantiert das niemand mehr.

So prüfst du Teil B.

  • Der Spielbildschirm startet mit der Frage Welche Kategorie willst du spielen?, einer Auswahlliste und einem Knopf.
  • Die Auswahlliste hat fünf Einträge, Alle zuoberst, danach Sport, Technologie, Geographie, Geschichte.
  • Runde starten öffnet eine Runde mit Frage 1 von 5.
  • Wähl Geschichte. Alle fünf Fragen sind aus der Geschichte, und unter dem Ergebnis stehen sieben Zeilen.
  • Wähl Alle. Unter dem Ergebnis stehen dreissig Zeilen.
  • Spiel dieselbe Kategorie zweimal. Die fünf Fragen kommen in anderer Reihenfolge.
  • Nochmals spielen führt zur Auswahl zurück, nicht direkt in eine Runde.
  • Im Logcat steht pro Runde showState CHOOSE_CATEGORY, showState QUESTION, showState RESULT.

Teil C, die Kommentare nachziehen 4 Minuten

C1Der Klassenkommentar stimmt nicht mehr.

Lies den Javadoc-Block über public class GameActivity. Er stammt aus 05A und 05B. Zwei Sätze darin sind seit heute falsch, und einer fehlt ganz.

Der Rahmen, den Inhalt formulierst du selbst:

/**
 * Der Spielbildschirm der Quiz-App.
 *
 * (DER TEIL AUS 05A UND 05B BLEIBT STEHEN)
 *
 * (WEG: der Satz über die verstreuten setVisibility-Aufrufe.
 *  Seit Teil A gibt es genau eine Stelle)
 *
 * (WEG: der Satz, dass der Fragenbestand in dieser Klasse liegt.
 *  Er wohnt seit Teil B in QuestionBank)
 *
 * (HIER: die drei Bereiche und wer über ihre Sichtbarkeit entscheidet)
 *
 * (HIER: was diese Klasse vom Bestand überhaupt noch hält)
 */

Danach prüfst du die neuen Stellen. Jede davon braucht ihre Javadoc-Zeile, und die meisten hast du beim Eintippen schon geschrieben:

WasSteht ein Kommentar dort?
enum GameStateeine Zeile, welche Zustände es sind
llCategory, spnCategory, btnStartje eine Zeile
selectedCategory, categoryQuestionsje eine Zeile
showStateder Block mit @param, samt dem Satz über alle drei Bereiche
onStartClickedder Block mit dem Hinweis auf die Kopie

Lies deine Kommentare am Schluss ganz durch. Ein Rest wie das Wort HIER, das Wort WEG oder eine leere Klammer fällt in einem Javadoc-Block nie auf, weil nichts ihn meldet.

Warum das ein eigener Schritt ist und keine Fleissarbeit. Kommentare veralten still. Kein Compiler warnt, die App läuft, und alles sieht in Ordnung aus.

Genau hier ist es besonders bitter: der Satz über die verstreuten setVisibility-Aufrufe beschreibt den Zustand, den du heute beseitigt hast. Wer ihn stehen lässt, hat einen Kommentar, der das Gegenteil dessen behauptet, was der Code tut. Ein falscher Kommentar ist schlimmer als gar keiner, denn wer ihn liest, glaubt ihm.

So prüfst du Teil C.

  • Im Klassenkommentar steht nichts mehr von verstreuten setVisibility-Aufrufen.
  • Im Klassenkommentar steht nichts mehr davon, dass der Fragenbestand in dieser Klasse liegt.
  • Der enum, die drei neuen Views, die zwei neuen Felder und die zwei neuen Methoden haben je einen Kommentar.
  • Nirgends steht mehr das Wort HIER, das Wort WEG oder eine leere Klammer.

Übungen 5 Minuten

Ohne Vorlage. Die Lösungen findest du im Material 05C Lösung - Drei Zustände und die Kategoriewahl.

Übung 1, die Kategorie im Ergebnis nennen

So prüfst du: Nach einer Runde in Geographie steht dort das Wort Geographie. Und dein neuer Text steht nicht im Java-Code.

Übung 2, das Original mischen

Misch testweise categoryQuestions direkt, statt eine Kopie zu machen. Spiel dieselbe Kategorie zweimal und schau beide Male auf die Liste im Ergebnisbereich. Danach stellst du es wieder zurück.

So prüfst du: Die Liste steht beim zweiten Mal in einer anderen Reihenfolge. Danach wieder in ihrer eigenen.

Übung 3, erklären

Erkläre einem Lerngspänli, warum showState auch die Bereiche setzt, die sich gar nicht ändern.

So prüfst du: Dein Gegenüber kann sagen, was passiert, wenn man es weglässt, und zwar mit dem Beispiel aus A3.

Keine Musterlösung. KI darfst du benutzen, aber du musst deine Lösung erklären können.
