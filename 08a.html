08A Startbestand und Fragenliste

Modul 335 Mobile Applikationen, Tag 4 Nachmittag. Zeitbudget 45 Minuten. Version 1 vom 20.08.2026.

Die Zeitangabe ist ein Richtwert. Sie sagt dir, wie lange der Kursersteller gerechnet hat. Brauchst du deutlich länger, melde dich. Bist du deutlich schneller, nimm die Zusatzaufgabe.

Heute füllst du deine Datenbank zum ersten Mal, und du baust den Bildschirm, der ihren Inhalt zeigt.

Warum dieser Auftrag der Anfang des Prüfungszweigs ist. Eine Liste, die den Inhalt einer Datenbank zeigt, ist das Muster, das in der Leistungsbeurteilung wiederkommt. Das Thema ist dort ein anderes. Der Bau ist derselbe.

Und der Startbestand ist mehr als eine Bequemlichkeit. Jede App, die mit einer leeren Datenbank startet, braucht entweder Daten von aussen oder einen leeren Zustand, der etwas taugt. Heute baust du beides.

Diese Zeile erzeugt einen ViewHolder, sie ruft nicht onCreateViewHolder nochmals auf. Der Unterschied in einem Satz: onCreateViewHolder bekommt den RecyclerView und liefert eine Zeile. Der Konstruktor QuestionViewHolder(...) bekommt die fertige Zeile und merkt sich ihre zwei TextViews.

Eine Frage hat so etwas nicht. Sie steht in einer Liste, aber ihre Stelle darin bedeutet nichts. Was sie hat, ist eine id, und die vergibt die Datenbank.

Der rvQuestions ist heute ein Feld, in 06C war er eine lokale Variable. Der Grund steht weiter unten: das Umschalten des leeren Zustands braucht ihn in einer zweiten Methode.

Die Regel: ein Feld nur für das, was mehr als eine Methode braucht. Alles andere bleibt lokal, sonst behauptet der Code etwas, das nicht stimmt.

In onCreate, nach dem Insets-Block:

Das this beim Adapter verlangt etwas von deiner Klasse. Sie muss das Interface umsetzen, sonst ist die Zeile rot. Schreib also in die Klassenzeile implements QuestionAdapter.OnQuestionClickListener und lass Android Studio die Methode ergänzen.

B2Lesen und einlesen. Die Schleife schreibst du selbst. 11 Min

Zeilen, die du schon hast, nicht ein zweites Mal eintragen. TAG, DB_NAME und instance stehen seit 07C da. Es kommt nur ASSET_NAME dazu.

Zweitens das Lesen aus assets. Das ist der neue Mechanismus, darum steht er vollständig da:

/**
 * Liest den Startbestand aus dem Ordner assets.
 *
 * assets ist kein res-Ordner. Was dort liegt, wandert unverändert in
 * die App und bekommt keine R-Nummer. Gefunden wird es über den
 * Dateinamen, und darum meldet auch kein Compiler einen Tippfehler
 * darin.
 *
 * Fehlt die Datei, liefert diese Methode ein leeres Array. Die App
 * läuft dann weiter und zeigt den leeren Zustand. Im Logcat steht der
 * Grund.
 *
 * @param appContext der Context der App
 * @return der Inhalt der Datei, oder ein leeres JSON-Array
 */
private static String readAsset(Context appContext) {
    StringBuilder builder = new StringBuilder();

    try (BufferedReader reader = new BufferedReader(new InputStreamReader(
            appContext.getAssets().open(ASSET_NAME), StandardCharsets.UTF_8))) {

        String line;
        while ((line = reader.readLine()) != null) {
            builder.append(line);
        }

    } catch (IOException e) {
        Log.e(TAG, "asset not found: " + ASSET_NAME, e);
        return "[]";
    }

    return builder.toString();
}

Die runde Klammer nach try ist kein Tippfehler. Was du dort öffnest, wird am Ende automatisch geschlossen, auch wenn ein Fehler auftritt. Ohne sie bräuchtest du einen finally-Block mit einem zweiten try darin.

StandardCharsets.UTF_8 ist keine Zierde. Ohne die Angabe nimmt Java, was das Gerät gerade für richtig hält. Auf einem Gerät stünde dann Geographie, auf einem anderen etwas Kaputtes.

Und im Fehlerfall kommt "[]" zurück und nicht null. Ein leeres JSON-Array ist gültiges JSON. Damit läuft der Rest der Methode ohne Sonderfall durch, es wird einfach nichts eingefügt. Der Grund steht im Logcat.
