Lösungsmaterial zum Auftrag 01C. Modul 335 Block 01.

Wie du das hier benutzt. Nicht abtippen. Vergleichen. Zu jeder Lösung steht eine kurze Begründung. Die Begründung ist der eigentliche Inhalt, der Code ist nur der Beleg dazu.

Punkt 4 ist der wichtigste. Er ist der einzige in der Liste, bei dem deine App trotzdem startet und erst beim ersten Klick abstürzt. Wenn du nur einen Punkt prüfst, dann diesen.

Variante 2, die fertige MainActivity.java

Der Stand am Ende von Teil 4. Das ist der Stand, der zählt, wenn nach dem fertigen Code gefragt wäre.

package ch.wiss.m335.buttons;

import android.os.Bundle;
import android.util.Log;
import android.view.View;
import android.widget.Button;
import android.widget.EditText;
import android.widget.TextView;
import android.widget.Toast;
import androidx.activity.EdgeToEdge;
import androidx.appcompat.app.AppCompatActivity;
import androidx.core.graphics.Insets;
import androidx.core.view.ViewCompat;
import androidx.core.view.WindowInsetsCompat;

public class MainActivity extends AppCompatActivity
        implements View.OnClickListener {

    private static final String TAG = "M335";

    private EditText etName;
    private TextView tvOutput;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        EdgeToEdge.enable(this);
        setContentView(R.layout.activity_main);

        ViewCompat.setOnApplyWindowInsetsListener(findViewById(R.id.main), (v, insets) -> {
            Insets systemBars = insets.getInsets(WindowInsetsCompat.Type.systemBars());
            v.setPadding(systemBars.left, systemBars.top, systemBars.right, systemBars.bottom);
            return insets;
        });

        // keine Typangabe. Sonst entstehen neue lokale Variablen.
        etName = findViewById(R.id.etName);
        tvOutput = findViewById(R.id.tvOutput);

        findViewById(R.id.btnGreet).setOnClickListener(this);
        findViewById(R.id.btnCount).setOnClickListener(this);
        findViewById(R.id.btnClear).setOnClickListener(this);
    }

    @Override
    public void onClick(View v) {
        int id = v.getId();
        String name = etName.getText().toString();

        if (id == R.id.btnGreet) {
            Log.d(TAG, "Greet clicked. Name: " + name);
            tvOutput.setText("Hallo " + name + "!");
            Toast.makeText(this, "Hallo " + name + "!", Toast.LENGTH_LONG).show();

        } else if (id == R.id.btnCount) {
            Log.d(TAG, "Count clicked.");
            tvOutput.setText("Dein Name hat " + name.length() + " Zeichen.");

        } else if (id == R.id.btnClear) {
            Log.d(TAG, "Clear clicked.");
            etName.setText("");
            tvOutput.setText("");
        }
    }
}

Die häufigste Fehlerquelle steht in einer einzigen Zeile. In onCreate heisst es etName = findViewById(...) und nicht EditText etName = findViewById(...). Mit der Typangabe entsteht eine neue lokale Variable, das Klassenattribut bleibt null, und die App stürzt beim ersten Klick ab. Beim Start läuft sie noch, das macht den Fehler tückisch.

Antworten zu den Denkfragen

Diese drei Fragen kommen im 01C Wissenscheck als Quizfragen wieder. Hier steht die längere Begründung dazu.

Frage 1, woher weiss ein Button, dass er angeklickt wurde?

Er weiss es nicht. Das System merkt die Berührung und ruft den Zuhörer auf, der beim Button angemeldet wurde. Der Button wird benachrichtigt, er prüft nichts.

Warum das zählt: Wer denkt, der Button frage dauernd nach, denkt noch in Schleifen. Eine App wartet nicht in einer Schleife, sie meldet sich an und gibt die Kontrolle ab. Dasselbe Muster ist der Block mit dem Pfeil aus 01B.

Frage 2, drei Zuhörer oder einer?

Beides geht. Drei eigene wie in Teil 2 und 3, oder ein einziger für alle wie in Teil 4.

Warum das zählt: Genau das ist die Frage, die dieser Block beantwortet. Es gibt keine richtige Antwort, nur eine begründete.

Frage 3, warum steht der Code nicht einfach in onCreate?

Weil er zu diesem Zeitpunkt noch nicht laufen soll. In onCreate wird er nur angemeldet. Ausgeführt wird er später, vielleicht oft, vielleicht nie.

Warum das zählt: Der Unterschied zwischen Anmelden und Ausführen ist der Kern der ganzen Ereignisverarbeitung. Ohne ihn wirkt es wie Zauberei, dass Code später von selbst läuft.

Teil 4, die Entdeckung aus 4.2

Warum werden etName und tvOutput rot?

Weil sie in onCreate als lokale Variablen deklariert waren. Eine lokale Variable lebt nur in ihrer eigenen Methode. Die Methode onClick steht ausserhalb von onCreate und sieht sie nicht.

Damit beide Methoden dieselbe Referenz sehen, muss sie der ganzen Klasse gehören. Also ein Klassenattribut.

Wenn deine Vermutung anders lautete. Häufige und nachvollziehbare Fehlvermutungen sind "der Import fehlt" oder "die id stimmt nicht". Beide wären bei anderen roten Stellen richtig. Der Unterschied: hier ist nicht der Typ unbekannt, sondern der Name. Android Studio sagt "cannot resolve symbol", nicht "cannot resolve class". Diese zwei Meldungen auseinanderzuhalten lohnt sich für den Rest des Moduls.

Teil 5, der Vergleich

FrageAntwort
Bei welcher Variante siehst du schneller, was ein Button tut? Bei Variante 1. Der Code steht direkt bei der Anmeldung des Buttons
Welche Variante bei zwanzig Buttons? Beide Antworten sind vertretbar, solange sie begründet sind. Variante 1 macht onCreate sehr lang. Variante 2 hält onCreate kurz, macht aber aus onClick eine lange if-Kette. Beide stossen an Grenzen. In echten Projekten trennt man die Logik deshalb in eigene Methoden aus
Was passiert, wenn du in Variante 2 einen Button anmeldest, ihn aber in onClick vergisst? Nichts. Kein Fehler, keine Warnung, kein Absturz. Der Button reagiert einfach nicht. Genau das macht Variante 2 fehleranfällig
Welchen Nachteil hat es, dass der Code weit weg vom Button steht? Man muss zwischen zwei Stellen hin und her springen, um zu verstehen, was ein Button tut. Bei Variante 1 steht alles beisammen

Beim Korrigieren. Es gibt hier keine richtige Wahl. Wertvoll ist die Begründung. Wer "Variante 2, weil kürzer" schreibt, hat den Nachteil nicht gesehen. Wer "Variante 2, weil onCreate übersichtlich bleibt, dafür muss ich in onClick suchen" schreibt, hat beides.

Lösungen der Übungen

Übung 1, eine Zeile mehr im Log

Im Zweig für btnGreet eine Zeile ergänzen:

Log.d(TAG, "Name length: " + name.length());

Begründung: Der Bildschirm bleibt unverändert, weil Log.d nur ins Logcat schreibt. Das ist der ganze Punkt der Übung: Log und Anzeige sind zwei verschiedene Kanäle. Debug-Informationen gehören in den Log, niemals in einen Toast.

Übung 2, der Toast wird kürzer

Toast.makeText(this, "Hallo " + name + "!", Toast.LENGTH_SHORT).show();

Begründung: Es gibt nur zwei Werte, LENGTH_SHORT und LENGTH_LONG. Eine freie Zeitangabe ist nicht vorgesehen. Wer versucht, eine Zahl in Millisekunden einzusetzen, bekommt keinen Fehler, aber auch nicht die erwartete Dauer. Das ist ein gutes Beispiel dafür, dass eine API manchmal absichtlich weniger erlaubt, als man möchte.

Übung 3, erklären

Eine mögliche Erklärung: In Variante 1 steht der Code, der etName benutzt, innerhalb derselben Methode onCreate. Eine lokale Variable reicht, weil sie genau dort lebt, wo sie gebraucht wird.

In Variante 2 steht der Code in einer anderen Methode, nämlich onClick. Eine lokale Variable aus onCreate existiert dort nicht mehr. Damit beide Methoden dieselbe Referenz sehen, muss sie der ganzen Klasse gehören.

Begründung: Das ist der Gültigkeitsbereich von Variablen. Er kommt im ganzen Modul wieder, besonders am Tag 3 bei den mehreren Bildschirmen und am Tag 4 bei Room.

Übung 4, der vierte Button. Gehört zur Hausaufgabe 1

Im XML einen vierten Button nach btnClear einfügen:

<Button
    android:id="@+id/btnReverse"
    android:layout_width="match_parent"
    android:layout_height="wrap_content"
    android:text="Umdrehen" />

In onCreate anmelden, in onClick einen Zweig ergänzen:

findViewById(R.id.btnReverse).setOnClickListener(this);
} else if (id == R.id.btnReverse) {
    Log.d(TAG, "Reverse clicked.");
    tvOutput.setText(new StringBuilder(name).reverse().toString());
}

Begründung: Wer StringBuilder nicht kennt, darf auch eine Schleife bauen. Beides ist richtig. Der Punkt der Übung ist nicht das Umdrehen, sondern dass ein neuer Button an zwei Stellen ergänzt werden muss: Anmelden und Zweig. Wer nur eine der beiden macht, erlebt genau den Fehler aus Teil 5.

Zur Zusatzaufgabe

Dazu gibt es hier bewusst keine Lösung. Die Frage bleibt offen, das ist ihr Zweck. Sie ist der Einstieg in die Eingabevalidierung, die in Quiz-Stufe 5 richtig unterrichtet wird.

Hinweise für die Lehrperson

  • Der wichtigste Moment ist Schritt 4.2. Dort werden etName und tvOutput rot. Lass die Klasse selbst darauf kommen, warum. Das ist der Gültigkeitsbereich von Variablen, und den brauchen sie im ganzen Modul. Die Vermutung steht auf dem Notizblatt und muss vor dem Weiterlesen geschrieben sein.
  • Häufigster Fehler in Teil 4: Die Typangabe bleibt in onCreate stehen. Das Klassenattribut bleibt null, die App stürzt beim ersten Klick ab, nicht beim Start. Sehr lehrreich. Lass sie die Drei-Schritte-Regel aus 01B anwenden, statt die Stelle zu zeigen.
  • Der Filter im Logcat auf den Tag M335 ist Gold wert. Ohne ihn ersaufen sie in Systemmeldungen. Zeig es einmal vorne.
  • Fünf Imports, nicht vier. EditText, TextView, Button, Log und Toast. Das wird regelmässig falsch gezählt.
  • Die Reihenfolge ist bewusst umgedreht gegenüber dem Original-Notizbuch. Dort wurde zuerst die Interface-Variante gebaut. Weil das Template bereits ein Lambda enthält und jede KI sofort eines liefert, erleben die Studierenden den Nachteil jetzt selbst, statt ihn zu erraten.
  • Das Layout aus Teil 1 fehlt im Original-Notizbuch vollständig. Der alte Auftrag verweist auf ein Unterrichtsmittel, das es dort nicht gibt. Ohne dieses Layout ist er nicht durchführbar.
  • Beim Zippen: einmal nach Teil 3 als Zwischenstand und Notlösung für Nachzügler, einmal am Schluss als Lösungsdatei.
